# 实现机制库、任务持久化与 RAG 分层

- 讨论日期：2026-09-23。
- 状态：**想法／待评估，未承诺实施**。
- 适用目标：分析成果逐渐积累，未来支持跨任务复用和语义查询。
- 本次沉淀范围：记录讨论中的判断、数据边界和逻辑表草案；不创建数据库、不执行迁移、不接入检索服务，也不改变分析流程。
- 阅读边界：下文的“建议”“可以”“优先”表达讨论倾向，不是已经批准的实施要求。

## 1. 问题是如何变化的

最初讨论的是：多份子 Agent 报告如何整合，是否应让模型按需读取材料，再提交局部语义决定。

随后关注点变成：当前四库是否需要增加实现机制库；如果数据持续增长，是否适合引入数据库和 RAG；不同内容是否应该采用不同保存范围。

这两个目标需要分开评估：

1. **本次任务整合**：保证当前报告和候选得到必要处理，保留分歧，维护引用与版本。
2. **长期知识复用**：从历史机制、特征案例和实验中找到对新任务有帮助的材料。

仅为小规模报告去重，不一定需要新增全局知识库或向量检索。明确需要持续积累和跨任务语义查询后，独立机制实体和长期知识层就有了更充分的理由。

## 2. 讨论时核对的实现事实

以下来自 2026-09-23 的工作区源码核对，包含当时尚未提交的文件；不是发布版本保证，也没有在本次记录中运行模型或验证实际整合效果。后续实现可能变化。

- [exploration.py](../apps/shader_deep/src/shader_deep/analysis/exploration.py) 中，`PossibilityLibrary` 的四个顶层部分是 `elements`、`sketch_library`、`feature_library` 和 `relation_library`。
- 机制并非缺失：`Feature.candidates` 和 `Relation.candidates` 中的 `Candidate` 已包含 `id`、`mechanism`、`reasoning` 和 `requires`。
- [library.py](../apps/shader_deep/src/shader_deep/analysis/library.py) 的 `_index` 为候选建立库内唯一身份索引，同时记录其拥有者；`_merge_candidates` 要求候选拥有者及前提一致。
- `FinalSketch` 保存组成文字，并通过特征、关系及候选引用表达整体方案。
- 默认分析入口使用 [ManagedIntegrationSession](../apps/shader_deep/src/shader_deep/analysis/managed_integration.py)，已有候选发现与局部比较分工；[controlled.py](../apps/shader_deep/src/shader_deep/analysis/controlled.py) 分开定义外观和机制比较标准，`LibraryStore.apply_integration` 检查提交身份、材料版本和修改范围。

因此，引入机制库应是提取、明确已有机制实体的职责，而不是再维护一份与 `Candidate` 重复且可能失配的机制正文。

## 3. 对“确定性管线 + 语义微工单”的判断

值得保留的分工：后端维护工作身份、版本、引用、范围和提交；模型负责有界的语义判断。

但不能把这一分工推导成以下绝对结论：

- 模型按需读取材料不必然是反模式。读取与检索权限、语义修改权限、事务执行权可以分别设计。
- Blocking 或向量初筛能够减少比较量，但仍可能漏项。初始元素归属错误、跨元素效果或检索表述偏差，都可能造成遗漏。
- 局部判断合法，不代表整体一致。`A≈B`、`B≈C`、`A≠C` 需要冲突检查，不能简单通过传递闭包全部合并。
- 无状态调用不等于确定性纯函数。单工单上下文可控，也不自动保证总调用成本更低。
- 单包重试、断点续传与安全并发需要持久化台账、幂等提交和版本冲突处理，不能仅靠任务拆小获得。
- `NEED_INFO` 应区分观察不清楚和机制不可辨识。裁剪可以帮助观察边界，却未必能区分产生相似图像的不同实现；应允许有限复检后保留未决项。

多个独立判决可以并行计算；涉及共享节点的提交仍需要检查冲突。结构正确、语义可信和渲染有效属于不同证据层级。

## 4. 是否引入独立机制库

### 4.1 当前讨论倾向

**在持续积累、按语义查询和跨任务复用的目标下，建议评估独立机制库。** 它的价值不只在于跨特征共享，还在于统一身份、集中查询、来源管理和实验积累。

应支持两种访问路径：

- 从特征出发：这个外观有哪些机制候选？
- 从机制出发：这个机制能解释哪些现象，适用什么条件，在哪些案例中尝试过？

### 4.2 分开机制知识、应用假设和实验记录

| 层次 | 例子 | 数据职责 |
| --- | --- | --- |
| 可复用机制 | 通过距离场控制透明度衰减，形成软阴影 | 原理、可产生效果、通用条件、限制、参数与实现说明 |
| 当前应用假设 | 本图卡片底部暗区可能由这种机制形成 | 当前目标、支持理由、局部前提、适用范围与不确定性 |
| 实验记录 | 某组参数下底部接近参考，但侧边过宽 | 输入、代码与渲染条件、制品、结果及失败原因 |

现有 `Candidate.reasoning` 和 `requires` 有大量任务上下文，不能原样提升为全局通用知识。提取机制实体时，应保留这些局部应用关系。

`Requirement` 当前具有“单项候选至少满足一个，多项须全部满足”的语义；后续建模不能把这样的条件简单压成无分组的依赖边。

### 4.3 独立存储不等于自动合并

同一特征可以保留多个机制，一个机制假设也可能解释多个特征。一个折射场可能同时解释背景位移、边缘变形和局部色散。

但“使用同一种算法”不等于“同一个机制实例”。卡片阴影和背景光晕都可能使用高斯模糊，却拥有不同输入、参数和 Pass。应区分机制知识的复用与具体实现实例的共享。

语义相似度可以提出比较候选，不能直接证明机制等价，更不能据此删除不同前提或不同实现的候选。

## 5. 按生命周期划分五类数据

**是否持久化与是否进入长期知识库是两个问题。** 任务结束后不参与通用召回的内容，仍可能需要保存以便恢复和追溯。

| 数据 | 任务／项目层保存 | 长期知识层 | 当前讨论倾向 |
| --- | --- | --- | --- |
| 草图 | 本次组成、候选范围、引用、依赖和未决问题 | 可在未来提炼成熟的整体方案 | 先随任务持久化，不默认进入跨任务 RAG |
| 元素 | 当前对象身份、范围、实例组和定位 | 经典元素的实现配方或模板 | 先保留任务数据；可复用实现暂考虑 skill、代码模板 |
| 特征 | 当前图的实际观察、位置和依据 | 可复用外观模式、识别线索和案例 | 适合积累与检索，但要分清实例与模式 |
| 关系 | 当前端点、方向、范围、组织与依赖 | 可复用关系模式及条件 | 先保证结构查询，语义检索按需求增加 |
| 机制 | 本次提出和尝试的实现假设 | 原理、效果、限制、条件和应用案例 | 优先评估独立实体与检索能力 |

skill 适合承载经典元素的实现步骤、代码和注意事项。数据库适合管理具体任务、元数据、证据、版本和关联；可以引用 skill 的路径、版本或内容哈希，不必再复制一份正文。

某张图中的观察不应直接成为通用规律。长期沉淀需要保留来源、适用条件和证据状态；尚未验证的假设也可以保存，但不应因此被标记为已验证知识。

## 6. 哪些库适合 RAG

RAG 是检索材料并将其用于模型判断或生成的流程，不要求每个业务库分别部署检索系统。

| 数据 | 适合程度 | 候选检索方式 | 建议顺序 |
| --- | --- | --- | --- |
| 机制知识 | 高 | 效果描述与机制正文的语义检索，加条件过滤 | 第一批 |
| 特征知识／案例 | 高 | 外观语义召回，再沿关联读取机制与实验 | 第一批 |
| 成熟草图／方案案例 | 中到高，取决于是否有完整案例 | 整体需求检索，加组成和引用展开 | 第二批，当前任务草图不自动进入 |
| 关系模式 | 按场景决定 | 关系类型和端点角色过滤，必要时语义检索 | 后续评估 |
| 元素实例 | 当前较低 | 按身份、任务、范围精确查询 | 暂不单独做语义索引 |

### 6.1 特征与机制联合召回

新需求通常先给出外观，而不是算法名称。例如：“半透明面板内部背景变形，边缘还有彩色分离。”

可以采用两条互补路径：

```text
当前外观 → 相似历史特征 → 关联机制与实验
当前外观 → 机制记录中的可产生效果 → 候选机制
```

合并两路候选后，再按纹理输入、Pass 能力、时间输入等当前约束筛选或分组，读取完整正文与必要依赖。

检索文本应包含效果、原理、条件和限制，不能只索引“SDF”“UV distortion”之类的名称。必要上下文应保留，避免孤立片段失去适用范围。

### 6.2 本次任务覆盖与历史检索分开

- 历史知识可以只召回相关部分。
- 本次必须处理的报告、候选和缺口需要后端台账管理，不能因为未进入 Top-K 就视为已经处理。
- 相似度高不等于同一对象、机制等价或当前任务可用。
- 可以先形成独立视觉观察，再引入历史知识，降低旧方案对新观察的牵引。

### 6.3 回存实验而不制造虚假确定性

一种待评估的长期循环是：

```text
独立观察当前图片
→ 召回相关机制与历史案例
→ 按当前条件组装竞争方案
→ 生成与渲染实验
→ 保存输入、条件、制品与结果
→ 选择性整理为长期知识及检索材料
```

“模型提出”“资料支持”“代码已实现”“在特定案例中渲染有效”应分开记录。复刻有效不证明原图采用了该机制；一次失败也不证明机制普遍无效。

## 7. 数据库边界与逻辑表草案

五个业务库不需要五个数据库。可以先使用一个关系型数据库，通过表或视图组织任务数据、知识数据和检索材料。

PostgreSQL 是本次讨论中的一个候选，不是已确认选型。以下是逻辑草案，不是可直接执行的完整 DDL；字段类型、约束、迁移、并发和恢复协议需要在实施任务中细化。

### 7.1 起步表设计

| 表 | 主要字段 | 职责 |
| --- | --- | --- |
| `projects` | `id, name` | 项目归属 |
| `tasks` | `id, project_id, status, reference_uri, reference_hash` | 任务身份、状态和固定参考图 |
| `task_snapshots` | `task_id, revision, payload, created_at` | 任务内完整对象、候选、引用与处理状态 |
| `knowledge_items` | `id, version, kind, scope, project_id, title, content, status` | 可复用特征、关系与机制的统一记录 |
| `knowledge_links` | `source_id, source_version, target_id, target_version, link_type, qualifiers` | 知识条目之间的解释、依赖等关联 |
| `task_knowledge_refs` | `task_id, snapshot_revision, local_id, item_id, item_version, purpose, bindings` | 任务如何使用某个知识版本及其局部绑定 |
| `sources` | `id, task_id, source_type, uri, content_hash` | 原始报告、资料、代码和实验制品的来源记录 |
| `knowledge_sources` | `item_id, item_version, source_id, source_pointer, evidence_role` | 知识条目与具体依据的对应关系 |
| `retrieval_documents` | `id, item_id, item_version, text, content_hash, embedding_model, index_status` | 面向检索的派生文本与索引元数据，向量字段或外部索引引用后续确定 |

这九张表只是起步边界，不要求最终固定为九张。实验检索需求增多时，可再引入专用实验表；不能把一条 `sources` 记录视为完整实验管理已经实现。

### 7.2 统一知识记录与分类内容

一种候选设计是：

```text
knowledge_items.kind  = feature | relation | mechanism
knowledge_items.scope = project | shared
```

三类知识共享身份、版本、范围、来源与生命周期字段；`content` 按 `kind` 使用不同 Schema 校验：

- 特征：外观描述、识别线索、容易混淆的现象。
- 关系：关系类型、参与者角色、方向、适用条件。
- 机制：原理、效果、输入要求、限制、参数与实现说明。

特征库、关系库和机制库可以先由查询视图或服务接口呈现。若以后出现大量专用索引、约束或查询，再拆专用表。

经常过滤的类型、范围、身份和版本应是明确列；变化较快的结构化内容可以放 JSON。若跨类型内容约束主要在应用层执行，应明确这一限制，不能宣称数据库已经验证全部语义。

### 7.3 任务快照的取舍

草图、元素和本次候选可以先放进 `task_snapshots.payload`，减少初期拆表与迁移成本。

代价是快照内的局部引用主要依赖应用层校验，数据库外键不会自动检查 JSON 中每个 ID。以后需要频繁查询、局部更新或并发处理单个对象时，再考虑独立任务实体表。

任务快照必须包含或绑定恢复业务处理所需的进度、判决回执和版本信息。保存业务快照并不自动等于恢复完整模型会话或实现断点续传。

### 7.4 任务使用知识的例子

```text
长期知识：M17 / v3，距离场软阴影机制
任务：T42
快照：revision 5
局部候选：C2，解释卡片底部暗区
引用：M17 / v3
用途：待尝试机制
局部绑定：方向、尺度、颜色、适用区域和不确定性
```

其他任务复用 M17 时新建引用，不把自己的参数或解释理由覆盖到通用机制正文。知识版本升级后，旧任务仍能指向当时使用的版本。

### 7.5 两种“关系”不能混淆

- **业务关系知识**：如“物体在承接面上形成投影”，需要端点角色、方向、条件与机制解释。
- **数据库关联**：如“机制 M17 可以解释特征 F8”，连接具体知识记录。

前者是 `knowledge_items.kind = relation` 的内容；后者进入 `knowledge_links`。任务内的真实端点绑定与长期模式中的角色占位也需要分别表达。

### 7.6 建表时需要进一步落实的约束

- 为任务快照设置 `(task_id, revision)` 唯一身份；知识记录可以采用 `(id, version)` 复合身份，或拆分身份表与版本表，具体方式待定。
- 关联、来源和任务引用应通过外键绑定明确知识版本，而不只保存不受约束的 ID 字符串。
- 版本内容不静默覆盖；如何选择当前可检索版本需要明确规则。
- `scope = project` 的归属与 `scope = shared` 的提升条件需要校验；访问范围不能只靠提示词或界面过滤。
- 合并需要保留来源、旧身份与重定向。别名表、合并事件表是否独立建立尚未确定，九表草案并未完整覆盖此协议。
- 业务提交、幂等回执与必要进度应有明确事务边界；并发判决需要检查输入版本。
- 检索材料是可重建派生数据。权威记录提交成功、检索索引待更新和索引完成应分别表示；新版本、删除或重定向后要处理过期索引。
- 嵌入模型、配置和内容版本需要可追溯；不同模型配置的索引兼容与重建策略待定。

## 8. 入库与召回的一种候选流程

1. 原始报告、观察和候选先进入任务层，保留来源与任务身份。
2. 整理值得复用的特征、关系和机制，保留未知项及其适用条件。
3. 检查已有知识，区分新增条目、新版本、关联已有机制或暂缓归并；相似度不自动触发合并。
4. 以事务写入知识、来源和必要关联；保留任务对具体版本的引用。
5. 生成检索文本并标记索引状态，异步更新或重建检索索引。
6. 新任务按范围、条件与语义召回，读取权威版本，补齐前提、关联案例和证据。

是否整理为项目知识、何时提升为共享知识、哪些状态默认可参与召回，均需进一步讨论。这里不假定所有模型输出都会自动进入高可信知识集合。

## 9. 如果未来实施，可以怎样验证

以下是验证方向，不是待办承诺：

| 问题 | 可观察证据 |
| --- | --- |
| 独立机制实体是否改善复用 | 同一机制被多任务引用，局部参数和前提没有互相覆盖 |
| RAG 是否找回有用方案 | 有代表性的查询中，相关且可运行的候选能被召回；同时抽查漏项 |
| 检索材料是否足够 | 必要前提、具体版本、来源及关键依赖实际进入模型上下文 |
| 是否保留竞争假设 | 相似外观下的不同机制没有被相似度直接吞并 |
| 持久化是否可靠 | 中断恢复、重复提交、旧版本引用和索引失败后重建有明确结果 |
| 是否改善实际任务 | 与不用历史检索的基线比较渲染结果、调用成本、延迟和错误率 |

一种可能的分阶段顺序是：先任务持久化和知识身份／来源，再特征与机制联合检索，最后按案例积累情况评估成熟草图与关系模式检索。是否采用这一顺序仍取决于真实数据规模和当前主要瓶颈。

## 10. 尚未确定的问题

- 实际数据量、并发需求和部署形态是否需要服务端数据库；具体产品如何选择？
- 元素、特征和机制的粒度如何定义，何时是新条目、变体或新版本？
- 独立候选与通用机制之间如何迁移，如何保留旧引用和条件语义？
- 哪些知识只属于项目，哪些可以共享；提升依据是什么？
- 原始实验与成熟配方的边界是什么，是否需要独立实验表和 skill 索引？
- 草图何时值得整理成复用模板，如何避免任务专属细节污染通用方案？
- 检索需要多少结果、采用怎样的过滤与重排，如何评估漏召回和旧知识偏置？
- 去重的全局一致性、拆分与撤销合并如何处理？

## 11. 讨论参考
