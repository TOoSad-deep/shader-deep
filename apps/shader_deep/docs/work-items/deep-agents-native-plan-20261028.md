# Deep Agents 原生优先实施方案

> 历史记录: 下文保留当时的实现、命令与验证结果. 旧分析执行和回放已退出当前包, 最新范围见[清理记录](analysis-legacy-cleanup-20261028.md).

- 日期: 2026-10-28.
- 状态: 已实施; 原生切换验证见第 10 节. 随后用户授权删除全部旧执行和回放支持, 最新范围见[清理记录](analysis-legacy-cleanup-20261028.md).
- 目标: 尽量使用 Deep Agents 原生能力, 减少自维护代码、概念数量和阅读跳转; 有明确需求缺口后再定制.
- 决策方向: 采用 `create_deep_agent` 和 SDK 子 agent 派发, 不继续推进上一版“统一改为 create_agent”的建议.
- 范围: Shader Deep 当前分析链. 生成与渲染不在本轮重写范围内.

## 1. 实施原则

1. 角色通过框架的提示词、tools、skills 和 subagents 定义; 不再要求新增角色先理解应用自己的循环继承体系.
2. 采用框架能力时退出对应自定义实现, 不把原执行器整体包装进 SDK 后宣称完成迁移.
3. 应用只保留框架不理解的业务: 固定图片与目标、独立探索、五库校验、结果汇集和文件包交付.
4. 默认接受框架的工具循环、上下文管理与 skill 读取方式. 偏离默认时必须说明具体业务理由.
5. 不以性能、token 或删行比例为验收目标; 以“增加工具/修改角色需要理解和修改哪些代码”为验收依据.

本方案会调整部分旧执行承诺, 不是完全保持行为的目录重构. 第 4 节列出变化; 实施时一并更新旧设计与应用 AGENTS, 避免新旧规则同时被当作当前要求.

## 2. 目标流程

```text
Python / CLI 入口
  → 固定原图, 创建本轮业务记录与独立输出目录
  → create_deep_agent 创建主角色
      → 框架发现并按需读取编排 skill
      → 主角色登记元素、冻结目标与本批方向
      → 原生 task 调用本批独立探索子 agent
      → 业务提交工具校验并保存探索产物
      → 程序汇集为 V0
      → 原生 task 调用整合子 agent
      → 程序校验合并建议, 发布 V1 或保留 V0
      → 主角色结束
  → 程序根据实际产物计算状态并发布文件包
```

SDK 负责执行子 agent, 程序负责判断有没有合法结果. 模型说“完成”、task 返回普通文本或写出一个文件, 都不直接算业务提交成功.

本轮保留一批两个或三个探索方向. 框架可以并发执行本批调用, 也可以串行调用; 不再由应用自建线程池保证执行时序. 整合必须等待本批各方向形成成功或失败结果, 不能用少派任务冒充全部完成.

## 3. 框架能力与最小业务适配

### 3.1 主角色与子角色

主角色使用 `create_deep_agent(model=..., tools=..., skills=..., subagents=...)`. 使用项目实际安装的 Deep Agents 0.7.13 / LangChain 1.4.0 / LangGraph 1.2.11, 不升级依赖或修改 SDK.

探索槽位按固定配置创建为 `explorer-1`、`explorer-2`、可选 `explorer-3`; 主角色冻结方向后, 每个槽位只绑定其中一个方向. 整合为独立 `integrator`. 这些名字用于 SDK `task(description=..., subagent_type=...)`, 不注册第二套派发协议.

普通角色优先用声明式 `SubAgent`. 本应用探索需要真实图像绑定、独立输入和权威结果回执, 首版允许使用官方 `CompiledSubAgent` 承接如下窄适配:

```text
绑定当前槽位的业务输入
  → create_deep_agent 构造的角色图
  → 从已接受提交生成 task 回执
```

这三个步骤使用框架 Runnable 组合即可. 中间必须是真正的框架 agent, 不能调用旧 `run_role`、旧任务调度或旧外层重试循环. 声明式方式若能更直接满足同一合同, 可采用声明式方式; 不为支持两种表示维护一套自建工厂体系.

`CompiledSubAgent` 返回值保留 SDK 要求的 `messages`, 可以通过 `structured_response` 提供简短回执. 回执从程序已接受记录生成, 不解析子模型最后一段自然语言来决定状态. 不向主角色回传子图完整状态.

### 3.2 只保留三类应用适配

| 适配 | 必要内容 | 明确不承担 |
| --- | --- | --- |
| 固定输入 | 按槽位提供原图、要求、目标、范围、方向; 整合读取固定 V0 | 继承主角色全文、兄弟草稿、额外调度 |
| task 准入 | 检查已冻结计划、槽位身份、是否已启动/结束、整合前置条件 | 另建线程池、递归恢复、执行 SDK 内部循环 |
| 业务提交 | 校验 F/R/M/S 或合并建议, 保存合法结果, 返回稳定引用 | 让模型写文件直接成为权威报告 |

task 准入作为一个小的工具中间件包围 SDK `task` 的实际执行. 校验与槽位状态变更在同一锁内完成, 防止同批重复调用; 重复已完成任务只返回已有回执. 失败也形成记录, 不再次启动同一方向.

输入适配不信任父模型自由填写的 description 作为目标真相. description 可以说明本次调用意图, 业务输入始终从已冻结计划构造. 禁用 fork, 不复制父角色文件状态或额外自定义状态. 编译子图的输入和输出均按允许字段投影, 因为 SDK isolated 本身仍可能转交非消息状态.

图像以真实多模态消息提供. 使用少量请求材料注入保持固定原图可用, 不要求模型从路径猜测图片内容. 现有取证工具继续负责裁剪/数值证据与来源引用; 这些是业务能力, 不重写为通用文件操作.

### 3.3 skills、文件和上下文

- 使用 SDK `skills=`、backend 和 `read_file`, 删除自定义 `read_skill` 工具和“完整读取 skill 后才开放所有业务工具”的状态机. 编排方法由 skill 与提示词指导, 业务前置条件由具体工具校验.
- 主角色和每个探索角色使用各自的框架文件状态; 首版优先用 `StateBackend`, 用 SDK 支持的文件数据格式预置对应 skill. 图像和已接受报告由应用自己的材料工具提供.
- 子图不继承父图的笔记文件, 不向主图合并自己的 scratch files. 若采用其他 backend, 必须保持每角色 scratch 区域独立, 不能让探索角色读取兄弟报告目录.
- 框架文件工具只操作 scratch/skill 工作材料; 权威产物由应用提交工具写入独立位置, 防止通用 `write_file` 绕过领域校验.
- 接受 SDK 的上下文压缩、工具输出外置和工具历史整理; 外置回执必须在该角色自己的 backend 中可回读. skill 和业务工具说明需要告诉模型按需读取全文, 不把预览视为完整业务证据.
- 程序权威记录不依赖摘要或 todos. 模型忘记某项时可通过业务读取工具重新获得固定输入、已接受产物和缺口.

SDK 自动附带的 general-purpose 子 agent 不属于本批业务角色. 优先使用实际版本支持的 profile 配置关闭它; 若模型 profile 匹配方式不适合当前客户端, task 准入仍须明确拒绝未注册角色. 不新增全局角色注册系统, 不假设 `subagents=[]` 会自动关闭默认子 agent.

探索和整合子图本身不开放继续委派. 使用 CompiledSubAgent 包装 `create_deep_agent` 时, 也要处理子图自动附带的 general-purpose 能力, 不能只限制主角色的 task.

## 4. 保留和调整的行为

| 内容 | 原生方案 |
| --- | --- |
| 固定原图、目标和单批方向 | 保留硬校验; 工具不能改写已冻结输入 |
| 独立探索, 不看兄弟结论 | 保留; 由子图输入投影与独立材料能力保证 |
| 五库字段、引用、草图含义 | 保留现有领域模型与校验 |
| 整合失败 | 保留合法 V0, 如实标记 partial 与缺口 |
| 恢复决策 agent | 新流程退出; 无恢复角色、无 recovery 子任务链 |
| 子任务重新派发 | 新流程不自动重派; 工具参数错误可在当前框架会话内修正, 正常结束仍无合法提交则记录失败 |
| 跨进程恢复 | 首版不承诺继续中断的任务或模型会话; 保留已落盘产物与诊断, 再次执行创建新运行 |
| 主角色结束条件 | 不再自建 `while not done` 补问循环; 框架结束后程序核查产物, 缺少必要阶段则 partial/failed |
| skill 已读证明 | 删除自定义门禁; 使用框架读取方式, 不把它当作业务成功条件 |
| 自动摘要与通用 scratch 工具 | 接受框架机制; 权威输入和结果仍与 scratch 隔离 |
| 调用限制 | 优先用现有版本的框架调用限制/递归限制; 不再实现跨角色、跨恢复的持久共享配额 |
| 分析到生成 | 继续由用户显式选择合法报告/草图, 不自动接续生成 |

普通网络恢复沿用模型传输适配器已验证的策略, 选择一个有限重试责任方, 不叠加 SDK 与应用两套额外重试. 原始工具参数、流式完整性和 OpenRouter reasoning 回传有真实服务依据, 初版继续复用; 不借迁移同时重写协议适配.

调用上限使用实际框架中间件, 明确限制的是某个 graph 的模型节点调用, 不宣称它自动覆盖所有子图与框架摘要请求. 真实试运行仍用外部明确的运行范围与时间上限约束, 无需重建原配额系统.

公开 Python 函数名、核心图像/任务参数、CLI 结果索引及报告格式优先保持. 对旧的恢复、共享额度等高级参数逐项列兼容表: 能等价映射的映射, 不能等价的显式说明并拒绝不支持值, 不默默忽略或偷换含义. 公共签名或参数语义变化须在切换说明中明确列出.

## 5. 业务状态和保存

新流程只需要一个本轮业务记录: 固定输入、冻结计划、各槽位状态与结果引用、V0/V1 和最终缺口. 不保存第二份模型消息历史, 不新增 Attempt 代次与恢复关系.

模型消息、todos、scratch 文件和摘要由 SDK 管理; 业务记录只负责应用事实. 第一版不配置跨进程 checkpointer. 将来真有继续会话的需求, 先评估 LangGraph checkpointer, 不重新扩展现有 TaskStore 为完整会话数据库.

成功提交先经过领域校验再保存, 相同槽位不能用另一份报告覆盖已接受结果. V0/V1 与文件包复用现有领域操作和存储格式, 不需要为了退出 TaskStore 改五库报告 schema. 草稿、已接受结果与最终交付保持区别.

现有文件包发布中依赖 TaskStore 的部分只抽出“从选定合法产物写包”的能力, 不把 commit.json、generation、attempt 和封存恢复协议整套带到新记录里. 切换后的新运行保存简短 manifest 与结果; 旧运行目录只按旧格式读取, 不声称可以原地续跑.

## 7. 实施顺序

### 阶段 1: 最小原生子 agent 链

- 在显式实验入口构造一个主 Deep Agent 和一个探索子 agent, 使用真实的 SDK task.
- 子角色通过固定输入适配收到图片, 用原五库领域校验提交报告; 父角色收到程序生成的回执.
- SDK 管理工具循环和文件状态; 验证无父会话/兄弟文件泄漏、无旧 run_role/任务执行器依赖.
- 在此阶段确定声明式 SubAgent 是否足够; 使用 CompiledSubAgent 时仅允许输入/回执适配.

退出条件: 熟悉 Deep Agents 的开发者能从一处装配定义看懂角色与工具; 业务校验通过的产物可读取. 不把“把旧执行器接进 task”算作完成.

### 阶段 2: 接入固定批次与整合

- 扩展为两个或三个探索槽位, 加入计划冻结和窄 task 准入.
- 接入程序 V0 汇集、整合子 agent、合并校验及 V1/V0 交付选择.
- 无合法提交的方向记失败; 整合不能改写草图或伪造缺失方向.
- 主角色正常返回即进入程序最终核查, 不增加外层模型追问循环.

退出条件: 一条 SDK 子 agent 链覆盖规划、独立探索、整合和交付; 失败有明确结果, 不再调用旧线程池/恢复角色.

### 阶段 3: skills、上下文与公开入口收敛

- 编排 skill 改为指导原生 task 与当前业务工具, 删除旧派发工具和读取门禁说明.
- 确定各角色可用 skills 和独立 backend, 接受原生 scratch 与外置回读方式.
- 将必要观察/证据能力接到新角色, 保留实际图像与数值证据的有效性检查.
- 更新公开入口和配置兼容表, 新默认流程不再加载旧执行器. 更新架构说明、应用 AGENTS 与相关 ADR, 将第 4 节变化明确记为新决定.

退出条件: 角色不再重复解析配置、装配预算回调或维护自己的消息循环; 对外不兼容项有明确说明, 未保留两套并行演进的默认方案.

### 阶段 4: 删除替代代码并收尾

- 按实际调用清单移除新默认链不再需要的旧实现; 仍被历史流程调用的代码隔离, 不回流到新链.
- 已无调用且不属于需保留公共入口的内部实现直接删除; 旧四库公开支持的退出范围单独列明, 不凭“当前没用”擅自删除用户数据或外部入口.
- 复用报告包读取和生成交接, 验证构建出的 wheel 包含所需 skills 和入口.
- 收口实验入口: 切换成功后只保留一个当前默认实现; 回退使用迁移前代码版本, 不长期在生产中维护双工厂和双调度器.

退出条件: 第 6 节每项都有“已替代并退出 / 仅历史兼容保留 / 仍有业务必要性”的记录. 保留项必须说明谁在使用.

## 8. 适量验证与验收

优先复用领域、报告包和证据测试, 不复制一套覆盖框架内部行为的测试. 旧恢复测试可以继续保护旧兼容实现, 但不能强迫新流程重新实现已明确退出的行为, 也不能把它们计作新流程验收.

新链仅重点验证:

1. 原生 task 能启动指定子角色, 实际模型请求收到正确原图和固定方向, 没有兄弟材料.
2. 重复/越界槽位和提前整合被拒绝; 不新增第四个探索方向.
3. 业务提交校验和结果保存有效, 模型普通文本或 scratch 文件不能伪装为已接受报告.
4. 子角色失败保留缺口, 合法 V0 可交付; 整合保持 F/R/M/S 的既有语义.
5. skill 与大正文可通过该角色的框架 backend 回读; 报告包仍能被生成入口读取.

不为角色类名、文件布局、中间件顺序配置值新增镜像测试. 实施末尾执行项目要求的 `make check` 和一次 wheel 检查; 只在图像/渲染交接有实际变化时补对应集成验证.

真实模型只做小规模端到端冒烟, 不做工厂性能竞赛. 运行前写清样本、主/子角色数量、时间与调用范围; 服务故障保留记录, 不无限重跑求成功. 用户已允许真实模型, 无需因普通冒烟重复询问, 但需遵守确定的运行上限.

最终验收用三个开发问题走读: 新增普通工具是否只改角色工具定义; 修改一个角色是否只看该角色和公共业务合同; 运行流程是否直接对应 Deep Agents 的主/子 agent 概念. 如果仍必须先理解一套自建调度框架, 本轮简化没有完成.

## 9. 当前交付边界
