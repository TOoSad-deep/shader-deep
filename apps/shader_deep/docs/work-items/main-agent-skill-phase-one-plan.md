# 主 Agent + 编排 skill 改造方案

日期: 2026-10-01. 状态: 已实施, 无网络验证和五图派发前实测通过; 真实探索/整合及视觉质量未验收.

本文替代上一版“第一阶段”方案, 将目标收敛为复用 Deep Agents 完成主 Agent 编排改造. 五库职责、单批探索和交付约束继续遵循[架构设计](../analysis-architecture-design.md); 先前提出的测试专用暂停配置、暂停业务状态和额外调度框架不纳入本次实现.

## 1. 改造目标

使用现有 `create_deep_agent`, 为主 Agent 配置编排 skill 和业务工具. 同一个主 Agent 根据工具回执持续推进元素拆分、探索派发、结果读取、整合和交付.

```text
主 Agent 读取编排 skill
  → 划分并登记元素
  → 收到登记回执, 选择目标并派发探索
  → 等待内部恢复处理结束, 读取子 Agent 最终结果
  → 请求整合: 程序汇集并保存 V0, 再启动独立整合 Agent
  → 根据整合结果请求交付
```

skill 描述工作方法, 主 Agent 选择工具并组织流程, 程序负责执行、校验和保存结果. 元素登记与派发是两次业务操作, 主 Agent 收到第一步回执后再进行第二步. 允许读取 skill 和错误修复产生额外模型调用.

## 2. 实现方式

### 创建主 Agent 并接入 skill

复用 Deep Agents 的模型—工具循环, 沿用现有模型客户端. 增加一份应用内的 `analysis-orchestration/SKILL.md`, 内容覆盖:

- 从原图识别元素, 给出具体名称与范围, 不提前填入共同特征或机制结论.
- 登记元素并处理工具反馈, 再选择一个已登记目标、制定本轮独立探索方向.
- 派发探索, 根据真实结果及错误反馈继续执行.
- 委派独立整合 Agent, 最后请求程序校验和交付.

配置可读取的 skill 来源, 确认完整方法内容实际进入模型上下文. 系统提示词只保留角色职责、工具权限等稳定要求, 易调整的方法放在 skill 中.

### 将现有业务能力封装成工具

以下名称为建议, 优先复用已有函数和数据结构:

| 工具 | 作用 |
| --- | --- |
| `submit_elements` | 校验并保存元素列表, 返回已登记元素及引用信息; 不结束主会话 |
| `dispatch_exploration` | 接收已登记目标的引用和探索方向, 校验后执行探索及现有有限恢复链, 返回各任务最终状态、错误与结果引用 |
| `read_analysis_result` | 按需读取已接受的结果和必要状态 |
| `dispatch_integration` | 检查探索任务及恢复处理已经结束, 汇集有效报告并保存合法 V0, 再调用现有独立整合 Agent |
| `finish_analysis` | 请求现有交付逻辑计算状态、保存文件包并结束主会话 |

派发时从已登记记录装配原图、用户要求、目标与范围, 避免重新提交另一份目标定义. 一个目标、一批探索、配置数量的独立方向等约束继续由现有业务代码校验.

派发工具内部等待任务及有限恢复处理结束, 然后返回最终状态与结果引用; 具体正文由读取工具按需提供. 等待沿用现有线程池和状态补查, 不通过主模型轮询任务进度. 不为每个内部步骤新增工具或模块.

### 元素登记与派发必须跨模型轮次

每次发送主模型请求时固定该轮允许调用的工具集合. 元素登记前不开放 `dispatch_exploration`; 对应的成功登记回执进入后续主模型请求后, 才开放派发. 执行工具时同时检查请求时的工具集合和当前业务前置条件, 不因同一响应中的前一个工具刚改变状态而临时放行原本未开放的工具.

如果同一模型响应同时包含 `submit_elements` 和 `dispatch_exploration`, 可以接受合法的元素登记, 但必须拒绝其中的派发且不启动 worker. 主 Agent 收到两个工具的回执后, 在下一轮重新制定派发调用. 登记失败时仍不开放派发.

首版沿用主 Agent 图的 `max_concurrency=1`, 使修改共享状态的工具串行执行. 这个设置不等于跨模型轮次的约束, 不能替代上述权限检查. 探索子 Agent 仍由派发工具内部的线程池按 `max_parallel` 并行执行. 独立只读工具的并发优化可以以后按实际需要引入.

### 任务恢复保留在派发工具内部

沿用现有网络重试、任务内修复、一次自动重派及独立 recovery 角色决定最后一次重派的处理链. 重试仍绑定原任务身份、原始输入和持久计数; 永久错误与尝试耗尽按原规则结束, 不改变合法次数或新增探索方向. 整合任务也沿用现有有限恢复行为.

持续主 Agent 接收这条处理链结束后的最终成功/失败状态、错误和有效结果引用, 再决定请求整合或结束并报告失败. 本次不要求持续主 Agent 接管每一次任务重试决定, 不增加 `resolve_failed_task` 工具. 这里的独立 recovery 角色是已有执行能力, 不是新建第二套业务编排流程.

### V0 准备归入整合工具

`dispatch_integration` 不要求主 Agent 事先提供 V0 正文, 而是从本轮持久任务记录读取所选目标和已接受报告, 在程序内部完成以下步骤:

1. 检查探索任务及其恢复处理均已终结; 存在 `pending` 或 `running` 任务时拒绝启动整合, 返回未结束的任务信息.
2. 复用 `collect_explorations` 和 `exploration_mappings`, 汇集有效报告、建立引用映射, 保留失败任务造成的缺口.
3. 复用 `_integrate` 中的 V0 发布、独立整合执行、合并校验及 V1 发布逻辑. 正文与引用由程序处理, 主 Agent 只发起业务请求.
4. 返回选定版本、状态和结果引用. 无合法基线时明确失败, 不启动整合或发布空包; 整合失败时保留合法 V0, 返回 `partial` 与缺口.

这段逻辑由现有 `_stages` 与 `_integrate` 迁移到整合工具的程序实现中, 不增加单独的“生成 V0”工具. 重复调用沿用已有任务身份与不可变版本校验, 不重复启动已完成的整合任务或覆盖既有版本.

### 调整应用入口与角色结束条件

当前[角色循环](../../src/shader_deep/runtime/runner.py)已经调用 `create_deep_agent`, 需要适配现有封装:

- 主 Agent 在中间工具成功后继续运行, 最终交付或明确失败后才结束.
- 调整 `role_prompt_only`、工具白名单和进展判断, 保证 skill 可读、有效多步操作不会被误判为停滞.
- 分析入口调用持续主 Agent, 将原 `_stages` 自动触发的业务动作改为主 Agent 的工具调用.

现有探索和整合 Agent 保持独立上下文. TaskStore、模型传输、日志、并发执行、引用校验、V0/V1 与文件包交付优先沿用; 只修改实际阻碍上述连接方式的部分, 保留公开入口兼容性.

## 3. 修改范围与实施顺序

主要改动集中在主 Agent 组装、编排 skill、业务工具封装和原入口接线. 不预设必须新增一套会话框架、工作流状态机、目录版本系统或通用调度服务.

1. 创建主 Agent, 接入 skill, 跑通元素登记与派发的跨模型轮次调用, 验证同轮夹带派发会被拒绝.
2. 将现有探索及内部恢复、结果读取、V0 准备、整合和交付能力接入主 Agent 工具循环.
3. 完成针对性验证和真实样例检查, 再切换默认分析入口.

这是实施和验证顺序. 完整改造的交付目标覆盖正常分析流程, 不以“派发准备完成”作为系统功能的结束位置.

## 4. 测试安排

### 验证正常行为

检查同一主 Agent 实际读取 skill, 元素登记回执进入后续请求, 再发起探索; 中间提交不结束主会话. 针对本次明确的契约补充以下可观察行为验证:

| 场景 | 预期结果 |
| --- | --- |
| 同一响应同时调用元素登记和派发 | 合法登记可以接受, 派发被拒绝, worker 启动数为零 |
| 后续模型请求已包含成功登记回执 | 允许合法派发; 登记失败、无效目标引用时仍拒绝 |
| 主 Agent 工具串行, 一批包含多个独立探索任务 | 子 Agent 仍可在 `max_parallel` 限制内并行, 不被主图的串行工具设置变为逐个执行 |
| 探索任务经历内部重试或 recovery 决策 | 保留原身份、输入与计数, 主 Agent 收到最终状态后继续编排; 重复派发不重新执行已完成任务 |
| 探索已有有效报告, 调用整合工具 | 程序产生合法 V0 后启动整合, 保留缺口及引用映射; 子上下文仍只接收允许材料 |
| 探索尚未终结、没有合法基线或整合失败 | 分别拒绝提前整合、明确失败、保留 V0 + partial; 不隐藏失败任务 |

保留既有合法交付、取消、迟到提交和重复提交的必要回归验证. 实现后运行应用既有 `make test`、`make lint` 和 `make repository_check`.

### 五图派发前测试

使用上次相同的五张图片和既有模型配置. 测试侧在“派发参数已经校验、即将启动 worker”的位置替换执行入口, 捕获参数并结束本次测试调用. 主 Agent 与业务工具真实执行, 实际 worker 使用测试替身.

测试装置负责保存元素输出、登记回执、派发参数、模型交互和日志, 并核对子 Agent 启动次数与模型调用次数均为零. 报告明确标记“真实模型规划 + 执行器替身”, 不把它当作完整流程成功.

测试优先利用已有函数替换点; 如需提取执行函数, 保持职责自然、改动局部. 不增加生产 `stop_before_worker_start` 配置、暂停业务状态或测试专用的主 Agent 指令.

五图测试检查前半程. 完整交付还需验证探索、整合及最终报告路径. 流程行为和元素内容质量分别报告, 不通过人工补写模型输出制造成功结果.

## 5. 完成标准

- 主 Agent 通过实际加载的 skill 和工具组织正常分析流程, 替代固定阶段串联.
- 元素登记和派发跨模型轮次完成, 同一主 Agent 根据登记回执继续工作; 同轮夹带派发不能启动 worker.
- 子 Agent 内部有限恢复处理结束后, 主 Agent 根据最终结果继续编排; 独立探索保持并行能力.
- 整合工具负责程序侧 V0 准备, 五库校验、V0 回退与交付复用现有能力, 必要失败路径仍有效.
- 派发前截停仅存在于测试装置, 正常系统可以继续执行到交付.
- 保存验证证据, 如实列出未通过项; 本节为验收条件, 实际完成状态与未验证范围以第 6 节记录为准.
