# 单观察 Agent 草稿与局部修订实施方案

日期: 2026-11-11. 状态: 已实施并完成离线验证与两图真实流程验证, 结果见文末记录. 本文是本次草稿改造的维护入口; 已有运行行为仍以源码为准.

## 1. 目标与范围

一个 Agent 首次生成完整观察草稿, 后续回读原图与草稿、局部修改, 最后由程序从冻结版本发布 scene_observations_v1 报告. 解决重复输出全文造成的内容丢失, 同时保留现有结构校验与有限调用预算.

继续使用现有 E/F/R 数据结构、run_analysis / run_analysis_task 公开入口、历史报告读取与生成输入限制. 模型可见工具合同会改变: 移除当前 submit_scene_observations, 增加首次保存和完成工具. 不增加独立 review Agent、M/S、证据图、数据库、通用版本管理或跨进程模型会话恢复.

首次保存、每次编辑及完成都是同一原生图中的工具动作. SDK 管理消息、摘要与工具循环; 应用只维护业务文件、版本、诊断及结束条件.

## 2. 唯一草稿来源与模块职责

```text
run/
├── reference.png
├── draft/
│   ├── observations.json          # 唯一可编辑草稿
│   └── history/<sha256>.json       # 修改前的不可变字节快照
├── results/observations.json       # finish 接受时的冻结结果
├── manifest.json                  # 运行诊断
├── result.json / run.json          # 最终索引
└── report/                        # 由冻结结果派生的正式包
```

保存、读取、编辑与完成共用一个 DraftStore. 不在 StateBackend 和 AnalysisSession 各存一份可编辑正文. 草稿存在磁盘, revision 为其原始 UTF-8 字节的 SHA-256; 版本号无需独立文件维护. 接受后的对象是不可变交付结果, 不再是可编辑草稿副本.

| 模块 | 职责 |
| --- | --- |
| infrastructure/storage/observation_draft.py (新增) | DraftStore: 固定路径、内容读取、唯一替换、快照、原子写入与版本核对 |
| agents/analysis/draft_backend.py (新增薄适配) | 将 SDK read_file/edit_file 映射到同一个 DraftStore, 保留 SDK 文件工具接口 |
| agents/analysis/native.py | 工具白名单、响应批次检查、实际请求/回读回执关联、工具反馈增强 |
| workflows/analysis/session.py | 同一实例的操作锁、状态、请求版本、已见版本、完成前置条件与接受快照 |
| domain/scene_observations.py | 复用字段合同与完整校验; 补可定位诊断, 不增加业务字段 |
| workflows/analysis/entry.py | 保持从已接受冻结结果发布报告及发布失败处理 |

复用 SDK CompositeBackend: 默认 StateBackend 承载现有 skill、conversation_history 和 large_tool_results; 仅 /draft/ 路由到草稿适配器. 模型只可读写 /draft/observations.json, history 与正式报告不开放编辑. 草稿不写入 SDK files 通道, 结束时也不再从另一份图状态同步覆盖磁盘.

新增薄适配的必要性: 当前 FilesystemBackend.edit 使用读后截断写回, 没有业务快照、结构校验或版本保护; 当前 StateBackend 写入图状态, 不自动持久化为业务草稿. 不修改上游 SDK.

## 3. 固定工具合同

| 工具 | 输入 | 成功反馈 | 失败/重复调用 |
| --- | --- | --- | --- |
| save_observation_draft | report: 现有 SceneObservationSubmission 字段结构 | created=true, path, revision, 字段/引用校验结果; 不接受终态 | 已有草稿返回 created=false 和现有路径/版本, 不覆盖; 字段结构不合法则不创建 |
| read_file | SDK 原签名; 草稿仅允许固定路径 | 文本、实际行范围、版本; 程序记录实际送入请求的范围 | 路径非法或文件不存在返回工具错误 |
| edit_file | SDK 原签名; 固定路径、old_string、new_string; replace_all 只接受 false | saved=true, before/after revision, 修改片段与结构变化摘要、当前业务诊断 | 过期、非唯一匹配、语法/字段错误或提交前 IO 失败, saved=false 且原稿不变 |
| finish_analysis | 无参数 | 冻结当前版本并返回 accepted=true、accepted_revision、结果路径 | 前置条件或完整校验失败时 accepted=false, 会话仍可修改 |
| stop_analysis | reason: 非空字符串 | 结束并保留现有草稿与诊断 | 终态后不得重新打开会话 |

首次保存只负责创建, 不是 upsert. 工具参数本身无法通过字段校验时仍返回参数错误, 无论草稿是否存在都不覆盖已有内容. 再次调用不得通过传入全文覆盖草稿. 普通写入工具 write_file、delete、execute、task 均不开放; 可见工具与执行准入同时限制.

工具返回区分“写入成功但业务检查未通过”和“动作失败”. 前者明确 saved=true、validation.valid=false, 提示继续修订; 后者使用 ToolMessage.status=error, 并返回稳定错误码、路径和简短说明. 不再让 accepted=false 的拒绝仅表现为 LangSmith 的普通成功节点.

结构变化摘要按文档路径定位, 有效且唯一时附 E/F/R ID; 包括新增、删除、修改与引用变化. 重复 ID 存在时不能用 ID 字典折叠对象. 摘要服务于回看, 不声称能够自动判断语义损失.

## 4. 校验层次: 明确允许与拒绝的错误

首版直接复用 SceneObservationSubmission 做字段结构校验, 不新增一套宽松模型. 保存和每次编辑均要求 JSON 顶层结构、字段类型、必填项、非空文本、E/F/R ID 基本格式符合现有模型. 类型错误、缺少必填字段、额外字段或非法 ID 格式在写入前拒绝. 这类初次工具参数错误仍可能需要重提初稿, 因为尚未产生可编辑的合法字段结构.

重复 ID、悬空引用、同一关系重复参与项、参与项指向错误类别等跨条目业务错误允许暂存. 例如两个元素中分别出现 F1, 或关系引用 E2-F1, 都可先留存草稿. 保存/编辑后返回问题定位, finish 前必须修复. 暂时留有悬空引用, 允许把重命名与引用修正分成几次局部编辑.

edit_file 先严格解析修改后的 JSON: 拒绝重复对象键、NaN/Infinity 与无法解析的文本, 再执行上述字段结构校验. 校验不重排或重新序列化已编辑文本, 避免未触及部分发生格式漂移. 初次保存由程序统一输出缩进 JSON, 已存在的可选列表显式保留.

finish 使用现有完整领域校验, 不降低正式报告标准. 合法报告有 gaps 仍可接受为 partial, 无 gaps 为 completed; 这些状态仍不等于视觉验收.

## 5. 精确定位与 ID 修复

错误反馈至少包含错误码、JSON 路径、相关 ID 与所有冲突位置. 例如 duplicate_id F1 同时位于 /elements/0/features/0/id 和 /elements/1/features/0/id. 引用错误定位到具体 relations/索引/participants/索引, 或问题列表 refs 的索引. 路径仅用于诊断, 不改变模型提交字段.

不自动将歧义引用映射到任意 F1. 不全局替换所有相同字符串. Agent 使用包含对象上下文的唯一 old_string 修改对应 ID, 然后修正实际相关的引用. 所有未编辑关系继续保留在文件中. 只有在图像复查后确认某项不必要时才主动删除, 删除会出现在反馈摘要中.

诊断尽量合并独立错误, 避免逐个报错反复重提; 不能为了继续校验而猜测错误对象. 字段结构验证失败时返回结构位置, 不继续做依赖该结构的领域校验.

## 6. 写入原子性、版本与并发

每个运行只有一个应用内操作锁, save/edit/finish/stop 在同一串行准入下执行. 首版为单草稿、小文件, 相关本地文件操作处于该临界区; 模型请求、网络与正式包发布不持有锁. 这是对现有 session “IO 不在锁内”约定的明确局部调整, 实施时同步其说明.

每次主模型请求派发时, 程序绑定 DraftStore 最近一次成功提交的 revision 为 request_base_revision, 关联到该响应所属调用. 读取磁盘发现 hash 不一致时报告 external_draft_change, 不把外部写入悄悄当成应用已提交版本; 首版须结束本次运行后再处理外部修改. 工具执行时从这条响应的调用上下文取预期版本, 不让模型传或记住版本参数. 执行前重新计算当前文件 hash; 与预期版本不一致则返回 stale_draft 并要求回读. 不在编辑完成后修改旧响应绑定的版本.

2026-11-11 回归后调整批次合同. 同批工具按模型声明顺序执行, save/edit/read 可以连续调用. 每次编辑仍独立原子提交, 后一步基于同批前一步实际提交版本. 终态后拒绝剩余操作, 非预期执行异常中止后续步骤. finish 必须满足正文已进入后续主模型请求, 因而同批刚读取的内容不能立即作为已见回执. 同步与异步路径采用相同顺序规则.

edit 的顺序固定如下:

1. 在锁内核对运行状态、固定路径与请求版本.
2. 读取当前字节; 要求 old_string 非空且恰好出现一次, replace_all=false. 若其去掉外侧空白后等于完整文档, 返回 whole_document_replace, 要求选择局部片段.
3. 在内存应用一次替换, 严格解析并校验字段结构. 失败不写文件.
4. 将修改前字节保存为 history/<旧 hash>.json; 已有同名快照须核对内容. 快照失败则拒绝编辑.
5. 将新字节完整写入同目录唯一临时文件, 再原子替换 observations.json. 替换是提交点.
6. 返回新 hash、实际差异与业务校验结果. 清理临时文件. 无内容变化不产生新版本或重复快照.

历史快照先写、当前文件后替换, 不是跨文件事务. 快照供人工恢复与排查, 首版不开放模型回滚工具, 也不因草稿业务校验未通过而自动撤销一次成功编辑. 替换前失败时原稿保持; 替换成功后即为已提交, 后续诊断写入失败不得伪称编辑未发生或自动覆盖回旧稿. 当前文件的真实字节决定版本, 不依赖另一份 metadata 文件.

首版不支持多个进程同时编辑该草稿. 检测到不经工具发生的外部修改时返回版本冲突, 不悄悄采用为已审阅版本. 原子替换保证不会把半写内容作为当前草稿, 不宣称完整操作具备跨进程事务性.

## 7. 回看与完成的可观察前置条件

“进入了后续模型请求”与“模型理解正确”分开记录. 首版采用容易验证的结束条件: finish 前, 当前完整草稿版本必须经 read_file 回读, 且已实际送入产生 finish 调用的主模型请求或之前的主模型请求. 只读路径、摘要、修改次数或局部 diff 都不算完整草稿已见.

草稿回读的版本、行范围、是否截断由程序记录. 多页读取只在同一 hash 下合并覆盖; 实际返回被 SDK 截断的部分不能算已见. 回执只有在实际主模型请求装配成功包含这些内容、并收到该次模型响应后才生效. 校验依据实际请求而非仅检查 StateBackend 中存在文件. SDK 摘要回读不单独充当完整正文回执.

任何内容编辑都会使 seen_revision 对当前版本失效. Agent 可以依据目标片段和编辑反馈连续修正数处, 不强制每次编辑都全文回读; 但最后必须回读完整最新版本再 finish. 这会增加完整稿的输入成本, 不要求模型重新生成完整稿. 首版不引入“根据多轮 diff 推导全文已审阅”的复杂逻辑.

普通无修改路径至少为: 保存初稿 → 回读文件 → 下一轮复查并 finish. 有修改路径为: 保存 → 回读/复查 → 一次或多次局部编辑 → 回读最终版本 → finish. 复查关注原图、关键关系、重复目标、必要缺口以及本轮修改影响.

程序能保证相应材料曾进入模型请求, 不能把 seen_revision 解释为语义通过或用户视觉验收. 新版 skill 需明确这个工作步骤, 不要求额外提交一份 review 全文.

## 8. 生命周期与失败交付

继续使用 running / accepted / stopped; 草稿是否存在、当前 revision、seen_revision、accepted_revision 是程序诊断事实. 不增加模型维护的生命周期字段.

| 当前情况 | 动作 | 结果 |
| --- | --- | --- |
| running, 无草稿 | save 成功 | running, 草稿存在 |
| running, 有草稿 | save 再次调用 | 返回已有路径, 不覆盖 |
| running, 有草稿 | edit 合法 | running, 更新 hash, 旧 seen_revision 失效 |
| running | edit/finish 校验或前置条件失败 | 保留文件, 返回错误, 可继续修订 |
| running, 最新全文已见且完整校验通过 | finish | 冻结结果保存成功后才 accepted |
| running | stop / 预算耗尽 / 运行异常 | stopped, 保留已有草稿与原因 |
| accepted 或 stopped | 写入或完成工具 | 拒绝, 不重开 |

finish 在锁内读取同一版本、校验并保存现有 results/observations.json 冻结结果, 成功后才接受. 后续正式发布只读取该冻结结果, 不重新读取可编辑草稿. 接受后禁止所有草稿修改.

图结束后的 entry 发布流程保持现有责任: 发布失败输出 failed, 不登记成功结果; 冻结结果与草稿保留. 未 finish 的草稿即使碰巧合法, 也不能自动注册为 completed/partial; 索引可以附 draft_path 和 draft_revision 供排查, report_dir 仍为空. 中断保留原始中断语义.

若 finish 保存冻结结果失败, 不设置 accepted. 草稿保持可排查; IO 异常按现有运行失败路径处理, 不伪装成可修的字段问题. 无草稿时调用 finish 返回 draft_missing, 不进入终态.

## 9. 权限、上下文与预算

草稿读写仅开放规范化的 /draft/observations.json. backend 与执行门禁均验证固定目标, 拒绝路径穿越及指向受保护文件的别名. 正式报告、历史快照、参考图和 skill 不允许模型编辑. `edit_file` 是新开放能力, 不顺带开放 SDK 其他写入或 shell 工具.

原图继续请求级注入; SDK 管理其余模型历史. 程序只保存草稿版本、工具回执与错误, 不维护第二套模型对话. full read 的结束前置条件不承诺跨进程恢复; 新运行仍使用独立 run 目录.

沿用有限 max_model_calls, 不因为加入局部编辑就自动增加默认上限. 预算前置检查覆盖 read/edit/finish 所需模型轮数; 用尽时保存草稿并失败交付. 实测须报告各阶段调用量与未完成原因, 再单独决定是否调整预算, 不能通过外置补问规避上限.

真实校准沿用现有 LangSmith 项目并核对写入. 追踪记录 save/edit/finish 的版本与业务结果, 能区分 saved-but-invalid、rejected、accepted 与 publish_failed. 不写入凭据.

## 10. 实施顺序与验证

1. DraftStore 与薄后端: 共享读取、首次创建、唯一替换、快照、原子提交、诊断及冲突定位.
2. 接入角色与 session: 新工具白名单、响应批次门禁、请求版本绑定、全文回读回执、finish 冻结接受.
3. 更新 skill 与相邻 README: 保存初稿、回看、局部修订、完成; 移除旧全文重提要求. 保持公共 Python 入口和最终包格式.
4. 离线行为测试及 make check; 核对安装包资源. 只运行与本次改动有关的集成检查.
5. 启用 LangSmith 做受控真实修复实验; 保留旧报告与全部失败尝试. 先核对一例追踪再批量运行.

| 验收场景 | 可观察标准 |
| --- | --- |
| 重复 F1、错误关系引用的初稿 | 初稿保存成功, 所有关系内容留存, 返回明确冲突路径 |
| 局部修改编号与引用 | 未修改 F/R 字节保持, 引用问题随修订消失 |
| 再次保存完整报告 | 当前文件 hash 不变, 不发生全文覆盖 |
| 修改结果不满足 JSON 或字段结构 | saved=false, 原文件与版本不变 |
| 暂时存在悬空引用 | edit 可成功; finish 拒绝, 修复后可再完成 |
| 同批依赖编辑、读取与完成 | 按顺序执行, 读取可见最新编辑, 完成仍检查已见版本; 同步/异步一致 |
| 旧响应尝试修改新版本 | stale_draft, 当前草稿不变 |
| 多处匹配、replace_all=true 或整份文档替换 | 拒绝并要求更精确局部片段 |
| 快照失败、临时写入失败、替换失败 | 原稿保留, 不假报已提交 |
| 替换已成功但后续诊断失败 | 不声称未修改, 磁盘 hash 与版本一致 |
| 保存后立即 finish 或修改后未回读 | 不满足 seen_revision, 会话仍运行 |
| 分页、截断或旧版回读 | 仅当前完整内容进入请求后可完成 |
| 完成校验失败后修订 | 不提前终态, 后续合法 finish 可接受 |
| 接受后编辑、预算耗尽、用户中断 | 不重开会话, 保留既有文件与正确失败状态 |
| 发布正式包失败 | failed, 不登记成功报告, 冻结结果可查 |

粉圆的实际首稿与编号错误可用于行为回放: 验证修复后不会因为工具合同要求而省略整份 relations. 原有三条关系并非正确答案, 不将保留条数视作语义验收. 另测结构正常且无需修改的场景, 确认不会强迫无意义编辑. 实际语义质量仍用十图原有评价项, 不按 E/F/R 固定条数判断.

## 11. Review 问题闭环与实施边界

| Review 缺口 | 本方案决策 |
| --- | --- |
| 图状态与磁盘可能双写 | DraftStore 为唯一可编辑来源, 独立 CompositeBackend 路由 |
| 原生 edit 缺少业务保护 | 复用工具接口, 薄后端负责检查、快照与原子提交 |
| 全量覆盖与并发丢更新 | create-only、批次顺序执行、串行锁、请求版本绑定 |
| 草稿校验边界不明 | 复用现有字段合同, 允许跨条目错误, finish 严格校验 |
| 复查可以跳过 | 当前完整版本回读并进入后续请求才能 finish |
| 文本编辑可能误改 | 唯一匹配、禁止 replace_all、结构路径诊断与差异反馈 |
| 未完成草稿与正式产物混淆 | 仅冻结接受版本发布, 保留失败与草稿路径 |

文件接口本身仍不能自动证明视觉正确或保证模型只改必要目标. 本方案不引入通用语义合并器; 明确的全文重建请求不属于首版工具流程. 上述工具与测试已实施, 验证范围与结果见文末实施记录.
