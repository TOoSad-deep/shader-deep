## 背景与问题

讨论从用户对“程序控制流程与硬约束”的追问开始：这是否意味着固定流程？Codex 此前的解释没有区分程序执行约束与路径是否固定，于是先解释两种流程，再应用户要求用粉色圆形的多视角分析作图比较。[T001](sources.md#t001)、[T002](sources.md#t002)、[T003](sources.md#t003)

随后用户提出“主 agent + skill”，并进一步澄清其目标：多视角分析仍交给具有独立上下文的子 agent，在 Orchestrator–Worker 架构下用 skill 指导主 agent 的流程编排，方便以后优化。这是讨论由“固定或动态流程”转向“编排方法如何模块化”的关键转折。[T005](sources.md#t005)、[T008](sources.md#t008)

## 议题一：程序控制是否等于固定流程

### 双方观点与解释变化

用户提出的是概念澄清问题，没有在此时选择固定或动态方案。Codex 回应：模型可以提出探索方向和补充建议，由程序检查并执行；这种分工既可用于固定阶段，也可用于允许分支的流程。[T001](sources.md#t001)、[T002](sources.md#t002)

按当时的两版建议，区别如下。它们是流程设计示例，并非当前代码运行图。[T004](sources.md#t004)

| 维度 | 固定阶段版 | 允许动态分支版 |
| --- | --- | --- |
| 路径 | 规划 → 一批独立探索 → 整合 → 交付 | 在基本路径上允许“识别缺口 → 申请补充 → 再整合” |
| 模型判断 | 探索问题、观察、机制、草图与未知项 | 除左列外，还提出是否值得补充及具体补充问题 |
| 程序管理 | 范围、派发、结果、失败与交付 | 额外管理补充请求、轮数、重复工作和预算 |
| 主要收益 | 成本较易估计，问题较易定位到阶段 | 有机会在同轮补足初始规划遗漏 |
| 主要代价 | 缺口可能只能留到下一轮 | 可能重复分析、无效循环并增加成本 |

粉色圆形的示例中，如果整合后仍缺少“右下亮斑怎样贴合轮廓”的说明，固定阶段版记录缺口并交付；动态分支版可以提出有明确目标的补充任务，通过程序检查后重新分析。网络重试和格式修复属于执行保障，不等于追加一个新的分析问题。[T004](sources.md#t004)

### 当前结论与边界

Codex 倾向首版先固定阶段，保留以后增加补充分支的接口空间，理由是先缩小范围、跑通系统；同时承认它的适应能力较弱。用户没有明确采纳这一取舍，不能把它写成双方已经决定采用固定流程。[T002](sources.md#t002)、[T004](sources.md#t004)

动态补充也不能自动解决所有未知：程序可以检查请求是否合规，却不能仅凭结构校验证明它有分析价值。必要工作未完成应保留为缺口；已有可用候选但无法判定唯一答案，可以保留业务未知项。上述判定思路是当时的解释，不是实测结果。[T004](sources.md#t004)

## 议题二：“主 agent + skill”是否要替代独立子 agent

### 双方观点与理解修正

用户最初仅询问是否可以采用“主 agent + skill”。Codex 将其展开为两种形式：一个 agent 顺序切换 skills 自己分析，或主 agent 用 skills 组织独立工作者。前一种形式是 Codex 为解释问题提出的备选，不能记录成用户曾主张、后来放弃的方案。[T005](sources.md#t005)、[T007](sources.md#t007)

Codex 认为，同一历史中顺序切换技能虽然简单、交接少，但后一次分析可能受前次结论影响，拆分 skill 文件也不会自动分离上下文。它因而更看好保留独立工作者，并指出独立上下文不要求一定使用不同模型或不同 agent 类。[T007](sources.md#t007)

用户随后明确指出：

> 这种多视角分析的工作，还是使用子agent比较好，而且我觉得是需要独立上下文的

其 skill 设想是在 Orchestrator–Worker 下控制主 agent 的流程编排、便于后续优化。Codex 接受这一澄清，并承认此前将重点放到“主 agent 自己执行多个 skill”，没有准确理解用户意图。[T008](sources.md#t008)、[T009](sources.md#t009)

### 当前结论与边界

双方在方向上对齐：探索由独立上下文的子 agent 执行，skill 用于主 agent 的编排方法。使用 skill 与是否固定阶段属于两个可分别设计的问题；用户选择前者，并没有自动确定后者。[T007](sources.md#t007)、[T008](sources.md#t008)、[T009](sources.md#t009)

Codex 另曾建议主 agent 先兼任规划与整合，等上下文或职责过重时再拆分。但用户尚未明确确认整合角色的归属，也未确认每个工作者都要加载独立 skill。[T007](sources.md#t007)、[T008](sources.md#t008)

## 议题三：skill、程序和独立上下文怎样分工

### Codex 提出的模块边界

在理解修正后，Codex 提出了以下职责划分。它是对用户方向的具体展开，不能将每一行都升级为用户已确认的接口契约。[T009](sources.md#t009)

| 层次 | 建议职责 |
| --- | --- |
| 主 agent | 根据任务与结果决定下一步 |
| 编排 skill | 指导规划、派发、收集、整合与结束条件 |
| 探索子 agent | 在独立上下文内完成指定视角分析 |
| 程序与工具 | 实际执行派发、任务状态管理、预算限制、校验和保存 |

这套建议希望把容易优化的方法留在 skill 中，例如怎样划分视角、怎样识别补充需求、整合时先比较什么；把必须执行的约束放进程序，例如视角上限、目标范围及有效引用。skill 描述最多三个视角与派发工具实际拒绝超限任务，承担不同职责。[T007](sources.md#t007)、[T009](sources.md#t009)

独立上下文方面，Codex 建议首批工作者共享参考图、目标和中性初稿，但不读取兄弟工作者的分析结论；主 agent 接收结构化结果和必要依据，避免汇入全部对话历史。后续针对性补充可以显式选择相关结果，但不能再把它当作首批独立分析。[T009](sources.md#t009)

### 取舍及适用前提

模块化可以使已有工具能力范围内的策略变化主要通过 skill 迭代；新增取消、补充派发或恢复任务等动作，仍需要程序先提供对应操作和状态变化。因此，“便于优化”不等于以后任何流程改变都只修改 Markdown。[T009](sources.md#t009)

用户明确了 skill 编排的目标，Codex 支持并解释了约束边界；具体阶段、工具权限和进入下一阶段的条件尚未逐项讨论完成。六步编排示例没有成为冻结流程，也没有形成运行验证。[T008](sources.md#t008)、[T009](sources.md#t009)

3. **主 agent 是否亲自整合？** 兼任规划和整合只是 Codex 建议，独立整合工作者是否保留未定。[T007](sources.md#t007)
4. **编排 skill 的具体契约是什么？** 包含哪些阶段、每阶段能调用哪些工具、何时继续或结束，以及子 agent 输入和返回内容，尚待细化。[T009](sources.md#t009)
5. **动态补充是否有价值？** 当时指出需要实际案例检验，结构合法不能证明补充必要；没有已完成的效果实验。[T004](sources.md#t004)

Codex 从中提出的设计启示是：隔离分析历史时，要保留工作者身份、任务来源、允许动作和返回契约。它属于此次诊断提出的建议，不应反向描述成此前已经实现的能力，也不能以本次拒绝否定独立子 agent 的整个架构。[T015](sources.md#t015)
