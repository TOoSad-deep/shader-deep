更新日期: 2026-10-01.

状态: 角色职责边界已收口, review 的 R1-R3 已修复为第 8.2 节的正式设计契约. 草图最低产出要求另行讨论. 用户随后授权驱动 subagents 实施; 五库默认链路已接入工作区, 实施与验证范围见[五库实施记录](work-items/five-library-implementation.md). skill 具体加载仍待确定. 当前已实现架构见[架构说明](architecture.md).

本文集中维护分析流程、模块职责、调度策略、Agent/skill 协作与运行状态归属. 五库对象、字段、引用和报告封装由[五库与报告数据设计](analysis-five-libraries.md)维护, 本文通过该数据契约衔接, 不另定义一套字段.

## 1. 已确认的架构与执行约束

1. 先缩小执行范围, 一次围绕一个指定元素进行多视角分析, 优先让小范围流程跑通.
2. 最多三个视角. 视角数量上限不是草图数量上限, 也不是机制数量上限.
3. 各功能需要模块化、解耦, 便于后续单模块优化迭代. 模块边界与接口细节继续讨论, 不将这一目标自动等同于拆分部署或增加 agent 数量.
4. 当前整体架构预设为“中心化调度器—工作者”(Orchestrator–Worker), 作为本轮设计基线; 主 agent 负责需求理解、任务编排和流程管理, 程序执行状态与数据约束. 其他架构的对比优化留到后续, 具体 skill 与工具接口仍待实现.
5. 首版每轮只执行一批独立探索, 本批最多三个视角. 不在收到结果后追加探索方向或开启第二批, 即使本批未用满三个名额. 任务内技术重试与提交修复不等于新探索, 次数按用户授权由助手依据第 7.3 节配置实现; 不通过改写目标、方向或输入材料将追加探索伪装成修复.
6. 最终交付采用“完整五库包 + 短入口报告 + 按草图读取”. 五库完整保留同一交付快照, 按草图读取是该快照上的读取视图, 不将交付包默认裁成单草图小包; 具体数据约定见[数据设计第 8.9 节](analysis-five-libraries.md#89-已确认的交付组合与读取视图).
7. 主 agent 在视觉分析上只拆分元素、确定目标范围, 不生成共同的特征观察初稿, 不提前推演机制. 元素定位与范围不能夹带特征清单、关系观察或机制答案作为共享分析结论.
8. 探索子 agent 独立观察原图, 产出特征、关系、实现机制和草图. 共享业务材料仅包含原图、用户要求、目标元素和范围; 各自另接收自己的任务方向与输出契约, 不传入兄弟报告, 不使用共同特征观察初稿.
9. 整合 agent 只对特征、关系、实现机制中的重复项和相似项提出合并, 不新增机制, 不对草图去重、修改方案或重新组合机制. 元素不进入其语义合并范围.
10. 草图库直接汇集探索子 agent 的产物, 即使草图相似也保留各自产物. 程序依据 ID 映射统一维护五库引用, 包括元素与草图中的引用; 这是引用维护, 不是重新设计方案.
11. 引用更新保持原方案含义. 发生冲突时保留原项或报告冲突, 不擅自选择机制、改变默认组合或创造备选. 草图最低产出要求另行讨论, 本次职责收口不规定任何 worker 必须产出几套草图.

视角数量不等于草图或机制数量; 草图语义和引用规则以[五库数据设计](analysis-five-libraries.md)为准. 确认上述约束不表示具体工具接口、草图最低产出或默认视角数的实现配置已经完成.

## 2. 模块职责与协作关系

已定方向是由中心调度器组织工作者执行任务, 当前先在此架构下讨论最小可运行方案. 后续再比较其他协作架构; 不在本轮预先实现多套架构或通用调度框架.

当前建议的模块划分如下, 具体接口尚待确认:

| 模块 | 建议职责 | 支持的独立迭代 |
| --- | --- | --- |
| 调度模块 | 管理目标与任务生命周期、派发、收集结果, 按规则推进或结束本轮 | 调整任务安排与执行策略, 避免嵌入各角色的分析细节 |
| 工作者模块 | 接收明确选入的任务材料, 在本任务权限内分析并返回结构化结果; 各自管理角色提示词与上下文 | 在契约不变时单独调整提示词、分析方法、模型与角色工具 |
| 五库领域模块 | 维护已定五库语义、引用与范围校验及合法状态变更 | 集中修改业务规则, 避免各工作者分别实现一套校验 |
| 执行与基础设施模块 | 提供模型调用、预算计数、重试、提交修复、存储与追踪能力 | 更换底层实现, 避免业务角色重复处理资源与网络细节 |

模块化的验收重点是依赖和契约: 工作任务的输入、结果和失败可单独检查; 工作者不依赖兄弟工作者的内部对象, 不自行改写共享五库; 调度模块通过领域操作接收结果, 不把所有校验、合并算法和提示词堆入自身. 集中调度不要求每次模型请求携带全部运行历史或完整五库. 这些约束仍为当前建议, 不意味着必须拆分进程或服务.

独立迭代以共同契约为前提. 修改某个工作者的内部策略通常可以局部完成, 但改变输入输出语义仍需要协调消费者和校验规则; 解耦不能消除必要的业务关联. 完成判定与报告投影继续遵循[五库数据设计第 8.7 节](analysis-five-libraries.md#87-报告公共封装-首版字段基线)的程序责任.

**已确认的职责分界.** 主 agent 理解需求并编排任务, 视觉工作限于拆分元素和确定范围; 探索子 agent 独立产出观察与方案; 整合仅提出特征、关系、机制的合并; 程序执行任务状态、引用重写、校验与发布. skill 封装与具体工具接口见第 4 节, 不改变这些职责. 首版只执行一批探索, 动态追加探索不在当前范围内.

[报告校验](../src/shader_deep/domain/library/validation.py)不要求每个视角覆盖初稿全部元素; 全部初稿元素的覆盖门槛位于[运行状态](../src/shader_deep/workflows/state.py)与[最终交付](../src/shader_deep/workflows/delivery.py). 因此单元素改造要同时调整任务绑定、提交范围与最终覆盖义务, 不能只缩短提示词.

2026-09-30 补充核对: 现有[四库存储](../src/shader_deep/domain/library/store.py)已将探索报告按来源纳入未去重并集, 并通过副本校验与版本持久化发布整合结果; [分析入口](../src/shader_deep/workflows/analysis.py)在异常后的最终处理阶段仍会尝试部分交付. 本文 R2 修复的是新五库设计中 V0/V1 的明确契约, 不是认定现有四库完全没有合法基线或异常部分交付能力. 新异步整合及 attempt 终态协议尚未接入.

下表为用户本次收口后的角色职责. 上述源码核对描述既有实现, 不把旧 `VisualOutline` 的共同特征观察带入新设计; 新职责并不表示业务代码已经迁移:

| 角色 | 已确认职责 | 与五库的联系 |
| --- | --- | --- |
| 主 agent | 理解需求、任务编排和流程管理; 视觉工作只拆分元素、确定目标范围 | 提供元素与范围, 不提供共同特征观察初稿或机制推演 |
| 独立探索子 agent, 最多三个视角 | 各自观察原图, 产出特征、关系、实现机制和草图 | 同时维护自身产物的作用对象与引用; 不读取兄弟报告, 不按库分成串行分析角色 |
| 整合 agent | 仅对特征、关系、实现机制做重复项与相似项合并 | 提交这三类对象的合并结果及对应关系; 不新增机制, 不对草图去重或修改方案 |
| 程序, 非新增 agent | 固定输入与任务, 汇集草图, 按映射重写全部引用, 校验并发布 | 维护元素的特征引用及草图等五库中的引用; 计算交付状态与[公共字段](analysis-five-libraries.md#87-报告公共封装-首版字段基线) |

各视角共享的业务材料只有原图、用户要求、目标元素和范围. 每个视角另收自身任务指令, 方向用于组织探索, 不预填共同特征清单或机制答案. 各自的观察、推演与草图在独立上下文中产生. 元素到特征的引用依据探索结果由程序建立与维护, 不要求主 agent 提前观察并填充特征库.

草图中的默认选择、组织方式与备选由探索子 agent 产生. 草图库直接汇集这些产物, 不由整合 agent 去重、改写或拼出另一套组合; 程序对草图做 ID 规范化和引用更新时必须保持方案含义. 草图最低数量、完整性要求与任务验收另行讨论, 不沿用“至少指定一个 worker 必须交完整草图”的建议作为当前基线.

对粉色圆形, 不同视角可以都观察到同一左上亮斑, 分别提出局部遮罩或曲面法线与光照的候选. 整合时可能合并这条观察, 同时保留不同机制与草图. 这是讨论示例, 不预设固定视角名称, 也不要求某个视角必须得出指定机制.

## 4. 主 agent + skill: 方向已确认, 具体加载待实现

2026-10-01 用户再次确认由独立主 agent 按 skill 编排流程, 先拆分元素再派发. 下文保留既有方法封装讨论; 当前实现差距和具体改造提案见第 10 节.

主 agent 的编排职责已经明确, 是否以及如何用 skill 封装仍按本节候选方式细化. 本节按 skill 为可加载的工作流程包理解, 包含说明、参考材料及可选脚本; 不预设迁移到某一产品或框架. [Agent Skills 格式说明](https://agentskills.io/home)与[Deep Agents 的 skill 文档](https://docs.langchain.com/oss/python/deepagents/skills)提供了这类封装及按需加载机制的参考, 不代表本应用已接入 skill 运行能力.

主 agent 可以承担 Orchestrator 的语义规划职责, 用 skill 组织不同阶段的方法; Worker 承载具体任务的执行上下文. skill 与 worker 是不同维度: 同一 skill 可以被多个 worker 使用, 一个 agent 也可以分阶段使用多个 skill.

当前推荐的最小候选组合:

| 方法封装 | 建议执行方 | 作用 |
| --- | --- | --- |
| 编排 skill | 主 agent | 指导需求解析、元素拆分、范围确定与任务编排, 不生成共同观察初稿或机制答案 |
| 探索 skill | 最多三个独立探索 worker | 共享方法与输出契约; 根据原图、用户要求、目标元素和范围, 按各自方向独立产出 F/R/M/S |
| 整合 skill | 独立整合 worker, 具体 skill 和工具接口待落实 | 只提交 F/R/M 的合并结果与对应关系; 引用重写由程序完成, 不处理草图去重和方案设计 |

首批探索 worker 的共同业务材料严格为原图、用户要求、目标元素和范围, 另附各自任务指令; 不复制主 agent 的全部历史、共同特征观察或兄弟结果. 主 agent 在接收结果后安排整合, 不能反向把已知兄弟结论注入仍宣称独立的首批任务.

**支持理由.** 在输入输出契约保持一致时, 规划、探索或整合方法可以分别迭代; 多个探索视角可复用同一探索 skill, 不需要复制整套角色实现. 按需加载有助于控制方法说明的上下文占用, 但不会自动缩短实际分析产物或保证总 Token 下降.

**限制与反例.** 主 agent 在同一历史中依次加载三个 skill, 不会自动产生三个独立工作者; 前一轮结论可能影响后一视角. 若全部由同一上下文串行完成, 应作为单 agent 多阶段方案评价, 不能直接声称满足独立多视角设计. skill 可以指导调用派发工具或脚本, 但执行实例与隔离仍须由运行层提供.

**代码仍需承担的职责.** 最多三个视角、固定目标、启用的预算、工具权限、引用校验及五库发布需要程序执行约束, 不能只写进 skill 文本. 用户提出首版暂不设预算, 其与恢复次数的区别见第 7 节. 通用校验和存储规则保留在领域与基础设施模块; skill 中的脚本可以调用这些模块, 避免每份 skill 复制一套业务规则. 模型提出安排, 程序验证并执行; 五库公共字段和完成状态归属保持[五库数据设计第 8.7 节](analysis-five-libraries.md#87-报告公共封装-首版字段基线)规定.

skill 保存方法与操作规则, 本轮任务进度和结果由运行 state 与登记制品保存, 不依赖主 agent 在自然语言历史中记住进度. 例如主 agent 请求新增第四个探索视角时, 派发工具按本轮视角总数拒绝, 不能只限制同时运行三个; 请求结束时由程序依据实际任务与缺口判定交付状态.

**成本取舍.** 与固定程序顺序相比, 模型主 agent 的调度会增加模型调用、延迟与决策不确定性. 若某一步始终只有唯一合法后继, 可以由程序直接推进; 将模型决策留给确实需要判断的探索方向、材料选择和异常处置建议. 后续应以固定样例检查派发是否遵守范围、失败是否如实保留、引用是否有效及总调用成本, 不因使用 skill 就宣称更加可靠或便宜.

本节仅讨论如何封装已确认职责, 不重新开放“主 agent 是否生成共同特征观察”“整合是否修改草图”等边界. 方法 skill 的加载尚未实现; 当前代码按独立角色与工具契约执行, 授权与验证记录见实施文档.

## 5. 主 agent 的编排职责与工具约束

主 agent 负责需求理解、元素拆分与目标范围确定、任务编排和流程管理. 共享分析输入遵循第 3 节的四类材料, 不由主 agent 扩展为共同观察报告. 以下表格落实该职责, 具体工具名和参数结构仍待实现; 程序维护实际任务与合法状态.

| 动作 | 主 agent 可以提出的决定 | 程序与任务契约的限制 |
| --- | --- | --- |
| 准备目标与规划探索 | 拆分元素、明确目标范围, 安排不同探索侧重点; 用户此前提案为默认三个视角 | 不生成特征观察初稿或提前推演机制; 一个目标、最多三个视角, 原图与范围固定 |
| 派发任务 | 提交本批任务方向, 绑定原图、用户要求、目标元素与范围 | 不接收共同特征初稿或兄弟结果; 校验后登记任务身份与固定输入, 重复请求不能产生重复任务 |
| 读取结果 | 根据任务回执读取已登记结果、问题与必要正文 | 摘要和结果 ID 不能替代具体语义判断所需的完整材料; 未结束或未通过提交校验的草稿不冒充已完成结果 |
| 请求整合 | 在首批任务结束或明确终止后, 委派整合 worker 处理有效结果 | 失败任务继续保留; 少于完整计划的有效结果可整合为部分交付, 不删除失败任务来宣称全部完成 |
| 处理执行问题 | 根据错误提出任务内修复或结束建议 | 网络重试、格式修复由运行层按恢复次数执行, 具体多级建议见第 7 节; 改变探索问题、增加分析范围属于新业务工作, 不能伪装成重试 |
| 申请交付 | 根据已有结果与缺口提出结束本轮 | 程序校验五库并计算 `status` / `gaps`; 主 agent 不能自行覆盖最终完成状态; 没有合法可用报告时明确失败 |

首批独立性的约束也适用于重试: 保留原任务输入, 可以附带本任务的错误和待修复草稿, 不能因其他视角先返回就将其结论作为补充材料注入. 接受其他视角结果的后续分析应明确属于补充或复核工作, 不再作为同一首批独立任务的普通重试.

**已确认: 首版只执行一批独立探索.** 用户明确选择“只执行一批探索”. 本批的方向、数量和初始输入在派发前确定, 收到结果后不再追加探索任务或开启第二批. 即使本批只用了两个视角, 剩余名额也不用于看过结果后的追加探索. 同一批内部的并发或排队不改变批次身份; 具体并行度另由执行配置决定.

这一决定用于先验证“规划—探索—整合—交付”以及五库契约, 让执行成本与失败路径容易检查. 代价是第一批遗漏的重要现象无法在本轮自动补齐, 必须如实保留缺口; 带额度的补充探索留作后续扩展. 网络重试或本任务提交修复继续按原任务身份和输入处理, 不生成新的分析方向, 次数按第 7.3 节由助手配置实现. 单批策略与第 3 节角色职责均已确认, 工具与执行配置的实施状态见实施记录, skill 加载封装继续另议.

是否存在多个解释与是否缺少必要工作分别判断. 例如弧形遮罩和曲面光照都能作为候选时, 可以保留多个草图与 `open_questions`; 若某个必要特征没有可用实现或所需整合尚未完成, 则记录 `gaps` 并部分交付. 不把每项歧义都转成继续调用的理由, 也不把未做完的任务改名为不确定性.

主 agent 的价值在于理解需求、拆分元素并绑定目标范围、组织任务和处理异常. 唯一合法后继的机械推进可以由程序执行. 目标不明确时应请求澄清或返回无法继续的原因, 正常的派发、回读和整合不要求用户逐步确认. 已撤下共同特征初稿及其执行归属的讨论, 草图最低产出与具体接口另行细化.

## 6. 运行状态与业务报告的边界

五库和[报告公共字段](analysis-five-libraries.md#87-报告公共封装-首版字段基线)是本轮业务数据契约. 完整运行 state 还包含各视角任务进度、预算计数与整合进度, 这些管理信息无需全部复制到最终报告. 模型历史、锁和客户端等执行资源继续由各自会话持有.

交付读取权威业务数据生成报告快照, 不维护两份需要双向同步的独立权威状态. `status`、`gaps` 与 `open_questions` 的字段含义及完成判定原则以数据设计文档为准; 本文负责确定由哪些模块执行这些规则. 这些是目标设计约束, 不表示现有 `BlackboardState` 已包含五库报告字段.

## 7. 已确认职责与执行方案细化

用户此前提出主 agent 编排、独立异步整合、五文件按需读取、默认三个视角与多级恢复. 本次进一步确认了各角色的视觉职责及草图保留规则, 见第 7.1 节; 执行接口和恢复实现继续细化. 角色边界确认不等于相关业务代码已经实现.

### 7.1 角色职责与引用维护: 已确认

主 agent 负责需求理解、编排和流程管理, 视觉工作限于拆分元素、确定目标范围. 共同材料不含特征观察初稿或预设机制. 探索子 agent 根据同一原图、用户要求、目标元素和范围各自独立观察, 产出 F/R/M/S, 不读取兄弟报告. “接管”按恢复原任务的调度行为处理, 不借恢复流程让主 agent 改做视觉推演或补充共享观察.

整合 agent 读取已接受报告, 仅识别特征、关系、实现机制中的重复项与相似项, 提出这三类对象的合并结果和 ID 对应. 合并可统一名称、消除重复和整理已有表述, 内容须追溯到输入报告, 不新增机制或补充探索. 元素与草图不属于整合 agent 的合并目标. 探索失败时仅处理已有有效报告, 不伪造第三份报告或隐藏失败记录.

草图库直接汇集探索子 agent 的产物. 整合 agent 不判断两个草图是否应合为一个, 不修改草图方案、重新组合机制或创造备选. 即使两个草图相同或相近, 也按各自产物保留; 程序可为报告本地 ID 分配不冲突的命名空间并据映射替换引用, 这种操作不构成方案设计.

**相似项合并原则.** F/R/M 的相似描述只有在对象范围和关键限定兼容时才合并, 不能仅靠同名判断. 同一亮斑的两份特征描述可以合并, 但“弧形遮罩”和“曲面光照”仍是不同机制. 对特征核对观察范围, 对关系核对参与对象与方向, 对机制核对构造方法与内在条件; 不将外观相近等同于实现相同. 这类判断不扩大为草图去重.

**程序维护五库引用.** 报告本地 ID 先按来源区分, 再建立 F/R/M 合并后的规范 ID 映射. 程序依据映射处理元素的 `feature_ids`、关系参与项、候选机制引用、草图的 `element_id` 及 `default` / `alternatives[].choices` 引用, 以及公共问题与缺口中的引用. 所有替换保持原对象指向和方案含义, 来源映射留在运行记录中, 不向五库新增字段. 整合 agent 提交三类对象的语义合并决定, 具体 ID 重写、完整性校验和发布由程序承担.

正文中的对象引用也纳入同一映射. 按[数据设计第 8.10 节](analysis-five-libraries.md#810-文本中的对象引用-设计契约)的显式标记, 由程序按来源解析和重写; 执行契约见第 8.2 节. 不能只更新结构化字段而保留指向旧对象的草图说明.

程序在发布前模拟引用改写并检查冲突. 例如同一草图原有 `F3:[M3]` 与 `F8:[M4]`, 若 F3/F8 合并后撞成同一个目标, 不能直接改成 `F3:[M3,M4]`, 因为这会把不同选择变成共同采用. 无法保持原方案含义时, 保留造成冲突的原项或报告冲突, 不擅自选择机制、改变默认组合或创造备选. 草图正文中的组织方式也不能因引用更新而被重新解释.

用户报告此前测试中整合复杂度与上下文占用较高, 因此支持独立整合上下文. 独立上下文减少主 agent 承载的材料, 异步调度使主 agent 不必阻塞等待; 二者作用不同, 不据此承诺总 Token 降低或整合耗时缩短. 当前源码中的整合角色已独立, 但[协调器](../src/shader_deep/workflows/coordinator.py)仍同步调用其 `run`, 不把已有角色隔离称为异步任务已接入.

首版在本批逻辑探索任务均已成功或结束恢复后, 由程序建立引用合法的未去重基线, 再启动异步整合. 任务状态先持久化, 完成事件只唤醒等待者; 状态补查与提交终态规则按第 8.2 节执行, 不通过模型调用轮询等待. 交付等待三类对象的合并及程序引用维护完成或明确失败; 整合失败时使用合法基线部分交付. 首版不同时引入探索返回一部分就持续整合的增量流程. 草图最低产出要求留到后续讨论.

### 7.2 五文件存储与按需读取

支持运行时分别维护 `elements.json`、`features.json`、`relations.json`、`mechanisms.json`、`sketches.json`. 业务对象仍按已定 ID 引用, 文件定位与版本解析由程序提供; 不把 `mechanism_refs` 等已定字段改成随意的文件路径. 读取可按库名和 ID 取具体条目及必要依赖, 不因为保存为五个文件就要求模型每次全文读取整个库. 语义比较必须实际读取相关正文, 只有路径或摘要不足以证明机制等价.

五库在同一逻辑版本下读取与发布. 探索 worker 保存各自候选产物, 不并发覆盖共享五库; 整合 worker 只提出 F/R/M 合并, 程序汇集草图并执行映射与引用更新, 检查后发布. 首版先写齐新版本目录中的五文件, 验证后通过提交记录原子发布版本指针; 读者固定所选版本. 这不是五次独立文件替换天然具有事务性, 也不承诺恢复完整模型会话. 版本、任务及来源记录属于运行基础设施, 不是新增业务库.

发布指针、任务状态与提交回执的一致性不能依靠连续写多个可变文件保证. 第 8.2 节规定单协调器管理的原子提交记录, 指向已写齐且校验通过的不可变版本; 新整合版本发布失败时保留旧版本.

用户已确认最终交付采用“完整五库包 + 短入口报告 + 按草图读取”, 原聚合单份 JSON 的建议不再作为必需交付方式. [交付组合与读取视图](analysis-five-libraries.md#89-已确认的交付组合与读取视图)及[文件包入口约定](analysis-five-libraries.md#88-文件包入口与读取约定)由数据设计维护: 首版以 `README.md` 提供短入口, `manifest.json` 保存既有公共字段, 五库文件完整保存. 这是物理布局约定, 不新增业务字段. 架构侧从同一已验证版本发布交付快照, 按草图读取该快照中的对象及依赖, 不另维护可独立修改的第二份权威库.

### 7.3 默认数量、不设预算与多级恢复

支持用户提出的默认三个视角, 保持第 1 节的单批和视角上限. “暂不设预算”在本轮 review 中按不设任务总模型调用次数或 Token 配额理解; 单次请求仍需要超时与失败处理, 不新增隐含的总调用上限. 正常探索多步推理与失败恢复分别处理, 以下次数属于恢复控制建议.

| 层级 | 适用情形 | 次数建议及责任 |
| --- | --- | --- |
| 单次请求自动重试 | 可恢复的网络/服务瞬时错误 | 运行层最多重试两次, 加初次共三次请求尝试; 成功执行过的工具不重放 |
| 提交局部修复 | 格式、缺失必填项或引用校验错误 | 同一逻辑任务合计最多两次修复, 给出具体错误, 跨重派不归零 |
| 自动重派 | 当前 worker 会话已失败, 重新执行同一任务仍可能成功 | 新执行实例恢复原逻辑任务一次, 保持目标、方向与原始输入 |
| 主 agent 介入 | 自动恢复失败, 需要判断是否有可行恢复方式 | 诊断后最多再重派原任务一次; 可以直接结束失败, 不要求用满次数 |

因此每个逻辑任务最多有三次执行实例: 初次、自动重派、主 agent 决定的最后一次重派. 三个视角对应三个固定逻辑任务, 不是最多只允许启动三个执行实例. 替换执行实例不得增加新方向或第二批任务; 主 agent 可以补充本任务错误说明或澄清原执行要求, 不能扩大目标或加入兄弟结论后仍称为独立探索. 整合恢复同样绑定其原输入版本. 计数由程序维护, 更换实例不重置逻辑任务层面的修复或重派次数.

恢复按错误类型选择, 不强制逐级尝试所有操作. 鉴权、配置、无效输入等无法通过重复执行解决的错误直接报告; 没有渲染证据区分两种机制也不等同于任务运行失败. 重派、任务最终失败、取消和运行封存均撤销相应实例的新提交权限, 迟到返回不能覆盖新结果. 已成功提交的幂等查询先于新提交权限检查, 具体顺序见第 8.2 节.

若只是成功回执丢失, 先查询该逻辑任务的提交记录, 已发布的结果直接复用, 不重新执行工具或生成另一份产物. 恢复成功后逻辑任务按成功处理, 早先失败实例保留在运行记录中, 不自动变成最终报告的未完成缺口; 只有仍未恢复的必要工作影响部分交付.

不设总预算仍需避免无进展循环. 建议连续三次模型响应没有新有效读取、被接受的提交或其他可验证任务进展时, 结束当前实例并按上述恢复规则处理; 重复读取相同版本和相同条目、重复同一拒绝以及纯文本自述不重置计数. 单次请求超时不等于整轮总时限. 若恢复耗尽, 保留已成功结果; 必要工作仍缺失则交付 `partial`, 无合法可用报告则明确失败. 不通过删除失败视角或再造新任务取得完成状态.

### 7.4 职责收口后的实施边界

主 agent 定位元素与范围、探索独立产出 F/R/M/S、整合只合并 F/R/M、草图直接汇集、程序保义更新引用的职责分界已确认. “完整五库包 + 短入口报告 + 按草图读取”的数据约定见[数据设计第 8.9 节](analysis-five-libraries.md#89-已确认的交付组合与读取视图). 下一步只细化草图最低产出、任务接口与执行机制, 不重新引入共同特征初稿、草图合并或整合阶段的方案设计.

### 7.5 已确认的读取方向与视觉独立性

**已确认的方向: 按草图读取同一完整快照.** 例如请求某个草图时, 读取该草图及默认方案所需的元素、特征、关系参与项和机制正文; 局部备选的机制正文可以随后按需加载. 读取视图按需缩小进入模型的材料, 完整五库仍保存在交付包中. 当前读取接口为 `read_report_package` 与 `read_sketch`, 实施验证见任务记录; 不得静默丢弃必要引用, 也不把未读的候选当成已经比较或排除.

短入口报告与完整五库包共同交付, 入口内容及公共字段位置遵循[数据设计约定](analysis-five-libraries.md#88-文件包入口与读取约定). 主 agent 的交付回复建议只返回包位置、状态与必要缺口提示, 不再次把五个文件内容和长篇说明全文复制进自己的历史. 完整运行日志、恢复过程与来源细账保存在运行记录中, 交付内容以数据契约为准.

**视觉独立性已确认.** 探索前共享的是原图、用户要求、目标元素与范围, 不设置共同特征观察初稿. 每个探索子 agent 自行观察、建立特征与关系并推演机制和草图; 主 agent 不提供待各视角沿用的观察结论. 先前由主 agent 的规划 skill 生成轻量中性观察初稿的建议已撤下, 也不另设一个 worker 来生成相同的共享初稿.

### 8.2 三项修复设计契约

本节是 R1-R3 的正式设计契约, 后续实现与验收以此为准. 本节先在仅修设计的授权下收口; 用户随后授权实施, 代码与验收证据由实施记录单独维护. 保持已有角色分工、五库字段与单批范围, 草图最低产出仍不在本次决定.

**R1: 引用解析与保义重写.** 文本引用语法集中在[数据设计第 8.10 节](analysis-five-libraries.md#810-文本中的对象引用-设计契约). 领域模块先解析来源报告中的结构化引用与正文标记, 将本地命名空间映射和已接受的合并映射合成为一份映射, 再基于原始内容一次性生成候选结果. 映射保留对象类型, 禁止循环、缺失目标与跨来源猜测. 不循环对文本进行字符串替换, 避免 F1/F10 混淆或 F1→F7→F9 的级联误改.

发布前检查对象类型、所有引用、关系端点和每套草图的默认/备选选择. 对草图额外核对非引用文本未被改写. 不存在的标记或需要澄清的引用返回具体提交修复问题; 合并引起的选择撞键、端点塌缩或无法保持原语义的情况拒绝相关合并, 保留原项. 相互依赖的合并作为一组校验, 发生冲突时不发布半套映射, 不擅自挑选机制或创造备选. 能机械解析不等于能证明自然语言语义, 不把语义兼容性伪装成单靠结构校验即可证明.

**R2: 先保留 V0, 整合成功后再发布 V1.** V0/V1 只是这里说明流程的版本名称, 不是新增业务字段:

1. 首批逻辑探索任务进入终态后, 收集已接受的合法产物; 程序按来源区分 ID, 建立元素与特征关联, 汇集 F/R/M/S 并规范化引用. 只做机械汇合, 不做语义去重, 不丢弃重复草图.
2. 对五库及关联信息完成校验, 将完整不可变的未去重版本记为 V0. 不能形成任何合法可用基线时明确失败, 不发布空包或悬空引用; 有必要任务缺失则保留对应缺口.
3. 整合 agent 基于固定 V0 提交 F/R/M 合并建议. 首版整合内部可分步判断, 但所有修改暂存, 经完整引用与方案保持检查后才一次发布 V1. 探索与整合原始产物继续保留以便追溯.
4. 整合失败、修复耗尽或 V1 发布失败时仍使用 V0, 从同一版本生成短入口和公共字段, 交付 `partial` 并明确记载“整合未完成”等实际缺口. 整合成功也须按全部必要工作判定状态, 不把完成去重自动等同于整个分析完成.

V0 一经发布即保持不可变; 失败的整合暂存目录不能被读作当前版本. 交付包的五库、公共字段和短入口必须指向同一选定版本及其实际完成状态. 恢复整合可以重新尝试产生 V1, 但不能覆盖 V0 或绕过原任务恢复次数; 已交付且封存后不再原地更新文件包.

**R3: 持久状态、幂等提交与终态封存.** 首版按每轮一个协调器写入设计, 不引入分布式调度服务. 任务与 attempt、输入版本、提交身份及内容指纹属于运行记录, 不加入五库业务字段.

- 先写齐并校验不可变结果文件, 再通过一份原子提交记录发布结果指针、相应任务状态与幂等回执. 在同一文件系统内先写提交记录临时文件, 再原子替换当前记录, 作为唯一发布点; 运行快照、日志和通知均从该记录派生, 不另设第二个独立版本指针. 最终提交才将逻辑任务置为成功终态, 临时步骤不宣称任务完成. 文件落盘或提交记录更新失败时保留上一份可见记录; 未被记录引用的暂存文件不视为成功结果.
- 每次提交在同一提交锁内先查相同提交身份的成功记录: 内容指纹一致则直接返回原回执, 即使任务已结束或运行已封存也不重新执行; 同一身份但内容不同则拒绝. 对尚无成功记录的新提交, 继续核对运行未封存、任务仍接受提交、attempt/运行代次有效及输入版本一致, 通过后才发布. 暂存准备可以在锁外完成, 发布前必须重做上述检查; 不能只在长任务开始时检查, 也不能让取消与提交各自写出相互矛盾的终态.
- 任务最终失败、取消、实例被替换或运行封存时, 持久化状态并撤销对应的新提交权. 之后的迟到新结果仅记录审计信息, 不修改交付快照. 原方案或恢复次数不会因迟到回调被重新打开.
- 状态持久化后再发完成事件, 事件只是唤醒信号. 调度器在开始等待、等待超时和恢复时读取任务状态, 用程序侧补查弥补漏通知; 不反复调用主模型询问完成情况. 等待超时仅触发补查, 不直接把正常运行的实例标为失败.
- 状态补查还要辨认没有执行者的 `running`. 首版使用单协调器进程锁与运行代次识别当前所有者. 新协调器取得独占权后先读取成功提交记录, 再将上一代未终结 attempt 标为中断并撤销新提交权, 按原逻辑任务剩余恢复次数处理, 不新增视角或分析批次. 当前活跃协调器根据实际执行句柄发现 worker 异常退出; 拿不到独占权时不得接管仍在运行的协调器. 这恢复的是任务与提交状态, 不承诺恢复旧模型会话或任意中间推理.

| 修复项 | 需要验证的可观察行为 |

| R2 | 整合崩溃或发布失败后仍可读取合法 V0, 交付状态为 partial 且缺口明确; 成功后所有文件读取同一 V1; 无合法基线时明确失败 |


核心源码入口: [公开分析入口](../src/shader_deep/workflows/analysis.py)、[五库协调器](../src/shader_deep/workflows/five_analysis.py)、[角色定义](../src/shader_deep/agents/five_analysis/agent.py)、[提交契约](../src/shader_deep/agents/five_analysis/contracts.py)、[角色循环](../src/shader_deep/runtime/runner.py).

当前角色与工具:

| 角色 | 模型可执行的业务动作 | 何时结束 |
| --- | --- | --- |
| planning | `submit_target_plan` | 有效提交使 planning 任务成为 succeeded |
| exploration | `submit_exploration` | 有效提交本方向 F/R/M/S |
| integration | LibraryReader 提供的读取工具、`submit_merges` | 回读全部必要 F/R/M 后提交合并建议 |
| recovery | `submit_recovery_decision` | 对指定失败任务提交最后一次重派或结束的决定 |

规划提示词明确要求“一次提交目标和两个或三个独立开放探索方向”. `submit_target_plan` 还检查方向数必须等于本轮配置, 默认三个; `TargetPlan` 检查元素 ID 唯一、目标存在、feature_ids 为空、方向非空且文本不完全重复. 这些检查不验证元素名称和范围是否有可用的视觉含义, 也不能证明两个不同文本方向在语义上互补.

**两层循环不能混淆.** `AnalysisLoop.run` 创建 Deep Agent, 框架内部执行模型与工具循环; 对纯文本未提交情况, 外层继续携带返回历史调用同一个角色图. `_run` 的 done 条件却是“本角色任务 succeeded”. 因而规划提交被接受后就退出规划角色, 后续由 `_stages` 接管. 修改工具名或把提示词放进 Markdown 都不会自动产生贯穿整轮的主 agent.

**派发与等待.** `_explore` 根据规划方向构造固定任务 payload, 逐个登记, 再由 `_wait_workers` 创建线程池. 单个角色的图执行使用 `max_concurrency=1`, 独立探索任务在线程池内并行. `_wait_workers` 循环等待完成并补查持久状态; 整合也在独立线程执行, 但上层工作流仍等待它返回. 这不等于主 agent 在整合期间继续自主编排.

**恢复.** `_execute_task` 执行初次和一次自动重派; 需要第三次时, `_decide_last_attempt` 再创建独立 recovery 角色. 它只接收原任务材料和错误, 决定是否最后重派. 这是程序触发的局部恢复决策, 不共享一个持续主 agent 的历史. 逻辑任务最多三个 attempt, 修复次数跨 attempt 持久累计; 网络重试只包模型请求, 不重放已执行工具.

**状态与交付.** `TaskStore.submit` 是任务最终提交, 会结束对应逻辑任务, 不适合直接拿来保存持续主 agent 的每个中间动作. `run.json` 是公开投影, 日志是审计信息; 二者不能成为第二套调度状态. 完整图像上下文和模型会话历史并未持久恢复, 当前恢复能力主要覆盖任务、结果、计数、版本和代次.

**skill 接入现状.** `AnalysisLoop.run` 没有传入 `skills`, 没有装载编排 skill. `_run` 使用 `role_prompt_only=True`, `_with_context` 会把最终 system_message 替换成角色提示词; 请求工具和执行白名单也只保留角色工具. 即使添加 SDK 的 skills 参数, 仍须处理 skill 提示被覆盖及读取工具不可用的问题. 仓库 SDK 支持 `skills` / `SkillsMiddleware`, 最终委托 LangChain `create_agent` 构图; SDK 提供能力不代表应用已经接入.

### 10.3 目标架构: 同一主 agent 按 skill 连续工作

已确认方向:

1. 主 agent 拥有独立上下文和持续执行循环, 正常运行中贯穿本轮业务编排.
2. 编排 skill 描述工作步骤、拆分方法、派发策略、回读要求、异常处置和结束条件; 主 agent 根据 skill 与真实工具回执选择动作.
3. 元素登记与探索派发成为两次独立业务操作, 主 agent 在取得第一步回执后才制定并提交第二步.
4. 探索与整合仍由独立子 agent 执行. 探索只看固定原图、用户要求、唯一目标与范围、自己的方向; 不带主 agent 全部历史或兄弟报告.
5. 程序负责合法动作、执行实例、并发、持久状态、恢复、引用校验与发布. skill 不直接成为状态数据库或线程调度器.

建议目标结构:

```text
CLI / API
  → 分析运行宿主: 输入、模型、TaskStore、执行器、审计
    → MainAgentSession                 [同一主 agent 的模型—工具循环]
      ← 编排 SKILL.md + 所需方法材料
      ← 固定原图、要求、当前权威状态、工具回执
      → 受限业务工具
        → 元素目录登记与版本
        → 受控批次派发 → 独立探索 workers
        → 等待/读取结果 → 原有领域汇集得到 V0
        → 整合派发 → 独立 integration worker → V1 或 V0 回退
        → 申请结束 → 运行层校验、交付与封存
```

MainAgentSession 是建议模块名称, 尚无对应实现. 正常执行的一个主会话可以包含很多次模型调用; “独立 agent”不要求另一个进程、另一款模型或额外规划 agent. 对进程重启, 首版从已接受的工具回执和持久状态重建主上下文, 明确记录恢复事件, 不承诺恢复旧的全部推理或聊天历史.

### 10.4 主 agent 的建议工具与前置条件

以下名称均为提案, 不声称已经存在. 数量按职责分离, 不给主 agent 开放任意任务、Shell 或任意文件写入.

| 建议工具 | 关键输入/回执 | 程序前置条件与副作用 |
| --- | --- | --- |
| `submit_elements` | elements; 回执含 catalog_version、元素 ID、登记结果 | 只接受元素定位与范围, feature_ids 为空; 保存不可变目录版本; 不登记探索任务、不结束主会话 |
| `dispatch_exploration` | catalog_version、target_element_id、directions; 回执含 batch_id、task_ids | 必须引用已接受目录; 本轮一批、配置为二或三个方向; 固定原图/目标/范围由程序装配, 主 agent 不重复提交目标正文 |
| `read_analysis_state` | 本轮索引、阶段事实、任务状态、版本、恢复待办 | 返回 TaskStore 的有限投影, 不隐式回读兄弟正文、不改变业务进度 |
| `wait_analysis_tasks` | task_ids; 返回已完成或需主决策的事件与状态 | 运行层等待/补查, 不消耗模型调用轮询; 无新状态时继续等待, 可响应取消 |
| `read_analysis_result` | 已接受的结果/版本及对象 ID | 按需提供有来源的正文或索引; 主会话不接收子 agent 全部历史 |
| `resolve_failed_task` | task_id、失败 attempt_id、retry 或 end、理由 | 只能处理固定任务的合法恢复待办; 检查代次、次数与状态; 不新增方向、不改输入 |
| `dispatch_integration` | 固定 baseline_version | 探索批次已结束恢复且 V0 合法; 唯一整合任务读取固定 V0, 只提交 F/R/M 合并建议 |
| `finish_analysis` | 交付请求与说明 | 程序核对全部必要任务和选定版本, 计算 completed/partial/failed, 发布与封存; 主 agent 无权自报覆盖最终状态 |

完整元素目录用于本轮规划, 最终分析仍只围绕所选元素. 未选元素不会自动成为待分析任务, 也不冒充全部场景已分析. 首版继续使用现有 Element 字段, 运行目录版本/回执属于控制记录; 若以后改为结构化坐标, 在五库数据设计中单独变更契约.

元素目录在派发前可以基于当前版本提交修订, 通过预期版本校验避免覆盖并发变化; 派发后冻结绑定版本. `submit_elements` 成功只代表登记完成, 主 agent 继续收到回执. 新增中间动作记录不能复用会终结主任务的 `TaskStore.submit`.

**真正保证分两步.** 每个模型请求固定该轮允许调用的工具快照. 第一次登记前不提供派发工具; 同一响应即使同时夹带登记和派发, 后者仍按请求时的权限拒绝, 不能因前一个工具刚改变状态而临时放行. 下一次主模型请求中包含 catalog_version 回执, 再开放派发. 主 agent 工具串行执行, 独立 workers 继续并行.

### 10.5 skill 的职责与实际加载

建议首版增加一个应用内的 `analysis-orchestration/SKILL.md`, 随应用打包. 系统提示词保留主 agent 身份、权限及必须读取编排 skill 的要求; 易迭代的业务方法写在 skill 中. 选择顺序如下:

1. 复用当前仓库 SDK 的 SkillsMiddleware/skills 发现能力, 将 skill 文件映射到只读、限定路径的后端. 记录 skill 名称、内容哈希和本轮使用版本; 运行途中不自动切换文件内容.
2. 主 agent 读取完整编排 skill 后才开放业务操作; skill 缺失或读取不完整时明确失败. 若文件分段, 跟踪实际已呈现部分, 不能仅凭“文件路径进入提示词”视为加载成功.
3. 调整主 agent 专用提示词合成, 避免 `role_prompt_only` 覆盖 skill 元数据/指令; 验证最终送给模型的请求同时包含身份、skill 正文/已读取材料和当前工具.
4. 为 skill 读取开放限定的读取能力, 同时保持模型可见工具与执行白名单一致. 不沿用默认通用委派来绕过应用 TaskStore; 子 agent 仍经专用派发工具执行.
5. 探索和整合的方法 skill 可在后续独立迁移. 第一版优先落实主 agent 编排, 复用现有探索/整合契约.

编排 skill 建议内容:

- 元素拆分: 根据当前图像记录可定位对象和范围; 不夹带共同特征清单或实现机制; 名称与范围必须具有实际描述意义.
- 元素登记: 调用 `submit_elements`, 按回执修复后再进入派发; 不把草稿当作已接受目录.
- 派发: 根据已登记目录选定唯一目标, 制定相互独立的观察方向; 只执行本轮一批.
- 收集: 等待真实状态, 按需读取结果和缺口; 保留失败任务, 不自己补写独立 worker 结果.
- 恢复: 根据指定任务错误处理合法恢复待办, 不改变首批材料或新增探索方向.
- 整合与交付: 委派独立整合角色, 根据回执申请交付; 接受程序计算的 partial/failed.

修改拆分尺度、方向组织、回读策略等方法, 可以主要改 skill. 新增工具、第二批探索、改变权限或状态转换, 仍需程序支持. 首版不因主 agent 接管编排而自动开放多批或多目标.

### 10.6 运行层必须保留与新增的能力

**状态统一.** 继续以同一 TaskStore 提交记录为权威. 增加元素目录版本、业务动作幂等回执、探索批次及待主决策事项; 主 agent 历史只提供上下文. 建议状态事实包括 elements_ready、exploration_prepared、exploring、recovery_required、exploration_settled、baseline_ready、integrating、ready_to_finish. 它们表示动作的合法前置条件, 不由 Python 在到达状态时自动替主 agent 调用下一项业务工具.

**原子派发.** 当前 `_explore` 逐个 register, 需要新增整批校验后一次登记批次及全部任务的能力. `dispatch_exploration` 先持久化派发意图和任务 payload, 再交给执行器启动. 相同 batch/action 身份重放返回既有回执; 不同 tool_call_id 不能绕过本轮唯一批次约束. 崩溃在登记后启动前时可接管 pending; 已成功任务不会重启. 若配置为测试截停, 接管也不得自动启动准备中的任务.

**等待与恢复.** 将 `_wait_workers` 中执行/等待/补查能力下沉为运行工具, 不再由 `_stages` 决定业务后继. 先保留现有网络重试、任务内修复和一次自动重派; 再次失败时持久化 recovery_required 并唤醒同一个主 agent, 由它调用 `resolve_failed_task`. 主 agent 崩溃由宿主恢复并重建上下文, 不递归创建一个新的“主恢复 agent”. 线程句柄、取消、过期 attempt 和迟到提交仍由运行层处理.

**进展和调用计数.** 主会话不能以任意工具成功作为 done, 只在最终交付已确认或明确终止后结束. 进展依据新接受的元素版本、派发/恢复回执、首次有效回读及任务/版本状态变化; 重复读取同一状态不算进展, 程序等待不触发“模型无进展”. 当前通用五库循环的三次空进展判断与任务级两次修复额度不能直接照搬给整轮主会话; 修复按稳定业务动作身份/版本划分并持久化, 重试不能通过换调用 ID 重置. 现有显式总调用预算继续有效, 各角色独立计数; `max_main_calls` 的兼容聚合口径需随迁移明确记录, 不默默扩大或缩小额度.

**五库汇集与发布.** 探索终态后, 程序机械汇集有效结果并发布 V0 可作为运行层后处理; 主 agent 读取 baseline_ready 回执后决定请求整合. 继续复用原 F/R/M 合并、草图保留、引用重写、V1 全量验证、V0 回退、完整文件包和终态封存. 主 agent 接管调度不接管五库语义合并或引用维护算法.

**质量检查.** skill 要求具体名称、可定位范围和开放方向; 程序拒绝空白、明确占位模板、无效引用等可判定错误. 不用字符长度或禁用所有单字符名称冒充视觉质量判断. 真实图片复测中单独审查拆分的覆盖、层级、范围、重叠、是否夹带特征结论和方向独立性. 当前占位输出的提供方/解析来源问题单独留证, 不把架构改造承诺为质量问题已解决.

| `agents/five_analysis/` | 保留探索与整合, 逐步退役旧 planning/recovery 入口; 私有调用方和测试同步迁移 |
| `runtime/runner.py` | 复用传输、审计、白名单等基础能力; 主会话专用进展/结束/skill 合成另行封装, 避免影响旧角色与兼容链路 |
| `workflows/options.py`, `configuration.py`, `cli/analysis.py` | 增加显式派发前截停选项及运行状态表达, 更新帮助和配置校验; 现有公开函数参数签名保持兼容 |
| 相关测试与维护文档 | 按可观察行为更新, 保留引用、恢复、发布和兼容回归 |

推荐四个可验证切片, 每片完成后才扩大范围:

1. **持续主会话 + skill + 两步业务操作.** 加入元素登记和派发回执, 用受控执行器截停在任何 worker 启动前. 证明同一主会话收到元素回执后才发起派发, 同时验证 skill 确实进入请求.
2. **真实探索执行与回读.** 接入现有 worker、单批并行、等待/补查、结果读取、V0 机械汇集; 验证共享材料和上下文隔离.
3. **整合、异常与交付.** 主 agent 发起整合和结束, 接入恢复待办; 保留合法 V0 回退、取消/迟到提交、崩溃恢复与封存.
4. **切换默认入口并复测.** 更新 CLI/API 入口及文档, 移除默认链路对旧 `_stages` 的依赖, 用同样五张图和既有模型配置复测. 逐步放开运行到探索、整合和交付; 不用只跑通前两步声称整套改造完成.

### 10.8 正式截停能力与验收

建议提供运行配置 `stop_before_worker_start` (名称待实施时确定, 默认关闭). 它作用于运行层, 不作为模型提示要求. 正常业务仍只有 `submit_elements` 和 `dispatch_exploration` 两步; 后者内部“接受并持久化派发”与“获得启动许可”之间设置截停点.

测试模式中, 在派发意图和任务已接受后暂停主会话, 记录 `paused_before_worker_start`, 不消耗 worker 调用、不创建 worker attempt, 不发布五库最终包, 不把暂停当 completed 或 failed. 重新启动相同测试记录不自动恢复执行; 显式继续才发放启动许可. 控制信号必须绕过业务失败/自动重派路径, CLI 输出暂停状态与制品位置. 公开 outcome/CLI 状态兼容需随选项一并验证.

| 验收维度 | 可观察证据 |
| --- | --- |
| 同一主 agent 持续编排 | 元素回执出现在下一次主模型请求; 两步共用主会话身份; 登记成功后主会话仍未结束 |
| 阶段工具约束 | 未登记、错误目录版本、同一响应夹带派发都不会启动任务; 校验错误回到主 agent 修复 |
| skill 实际生效 | 完整内容/所需参考材料出现在实际请求材料中, 记录版本哈希; 不被 role_prompt_only 覆盖; 未读完则不执行业务动作 |
| 派发截停 | 五图逐次保存元素提交、回执、派发指令、模型输出、日志和状态; worker attempts/model_calls 均为零 |
| 幂等与恢复 | 重复派发、登记后崩溃、启动后崩溃均不形成第二批或重复已完成任务; 测试暂停不会被接管自动执行 |
| 子 agent 隔离 | 实际 worker 请求只含允许材料和自己的方向, 不含主会话历史/兄弟结果 |
| 等待与预算 | 无新结果时无模型轮询; 正常多步进展不被三轮停滞机制错误中止; 修复计数按动作持久化 |
| 交付与失败 | 整合失败仍有合法 V0 + partial; 无合法基线 failed; 不隐藏失败任务或未完成整合 |
| 元素质量 | 单独记录名称/范围可用性、覆盖和拆分层级; 字段通过率与人工语义评价分别呈现 |

实施时执行应用 `make test`、`make lint`、`make repository_check`; 五图真实服务复测属于额外证据, 不能由固定模型测试替代. 本节仅为设计核对, 不宣称上述新增验收已经通过.
