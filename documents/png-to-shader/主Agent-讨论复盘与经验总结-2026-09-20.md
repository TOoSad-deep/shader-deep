## 1. 讨论背景与文档关系

此前已形成[探索型子 Agent 输入输出规范](探索型子Agent-输入输出规范-2026-09-20.md)和[子 Agent 讨论复盘](探索型子Agent-讨论复盘与经验总结-2026-09-20.md)：子 Agent 的价值是独立探索组成方式，而不是确认一个唯一正确答案。

本次继续讨论：在这一定位下，主 Agent 应负责什么，如何控制输入输出的复杂度，以及首次视觉分析和最终整合如何衔接。

本次对上一轮文档有两项实质更新：

1. 原图元素由主 Agent 首次视觉分析统一确定；子 Agent 不再各自输出和重新划分 `elements`，正常探索输出改为三个候选库。
2. 主 Agent 整合维护可能性库，合并重复项、整理适用范围和优先级；不根据主观认可程度淘汰不同候选。

涉及上述职责和输出边界时，以本次讨论为准。此前文档保留为讨论演进记录，其中子 Agent 输出四库、跨报告合并元素和自行重新分类的表述不再是当前目标设计。未冲突的候选、关系和依赖语义继续沿用。

本次没有运行新设计，没有统计实际 token 开销，也没有验证质量改善。不能把结构上的精简预期写成已测得的收益。

## 2. 主 Agent 的角色：组织探索和整理可能性

主 Agent 的核心工作收束为四项：

| 工作 | 需要回答的问题 | 产物 |
| --- | --- | --- |
| 首次视觉分析 | 原图由哪些视觉元素组成，有哪些显著特征和可见关系？ | 统一视觉初稿 |
| 组织探索 | 哪些不同切入点值得探索？ | 独立探索方向 |
| 整合结果 | 哪些条目重复，哪些机制不同，哪些候选适用于什么范围？ | 整理后的可能性库 |
| 判断是否继续 | 下一次探索能补充什么，还是已经需要编码和渲染？ | 新问题或分析交付 |

主 Agent 可以提出跨报告的新组合，但应将其作为新增候选，不能写成子 Agent 已共同支持或已验证的事实。记录其来源属于后端追踪责任。

## 3. 第一次关键纠正：整理不等于排除候选

讨论中曾提出：主 Agent 可以排除不适用候选，使其不进入最终交付集合。

用户纠正了这一前提：外部需要维护的是可能性库。某个候选不适用于某张草图或某个实例，不代表它不应存在于库中；优先级较低、主观上看起来不太可能，也不代表它不是一种可能实现。

因此需要分开三个层次：

| 层次 | 含义 | 不应混淆的结论 |
| --- | --- | --- |
| 可能性库 | 保留有实质区别的组成和机制候选 | 不是只存主 Agent 最认可的方案 |
| 适用范围 | 某张草图或某个元素、实例组关联哪些候选 | 未关联不等于被全局否定 |
| 优先级 | 在当前目标和范围内建议先尝试什么 | 低优先级不等于不可实现 |

重复候选可以合并成一个条目，保留来源。这种去重没有删除独特机制，也不等于淘汰方案。

格式错误和悬空引用仍需修复；“保留可能性”不意味着接受不可解析的数据。结构修复也不应被用来暗中进行机制淘汰。

## 4. 适用范围和优先级属于使用情境

以条带亮边为例，候选库可以同时保留：

- A：横向颜色渐变。
- B：沿边缘叠加细亮线。
- C：曲面法线变化产生高光。

平面草图可以引用 A、B；空间草图可以引用 A、B、C。两者共享库中的候选正文，各自维护引用数组。

同一候选在不同草图或实例组中的尝试价值不同，因此建议把优先级放在使用处，不给候选贴全局高低标签。具体的优先级枚举、排序方法和草图级排序字段仍是待定接口细节。

还应区分“值得先尝试”和“更像原图的真实成因”。人工画出的亮边未必符合物理成因，却可能更容易复现图像。优先级理由可以涉及实现成本、关键外观覆盖和验证价值，不应伪装成概率。

数组未引用某个候选，仅说明当前未建立该适用关联，不能据此自动推导它绝对不兼容。已知的选择前提仍由 `requires` 表达，优先级不能覆盖这些前提。

## 5. 第二次关键纠正：元素统一确定，不重复拆图

此前曾设想让子 Agent 各自输出 `elements`，再由主 Agent 合并、对齐这些元素。

用户指出，`element` 指组成原图的视觉元素。主 Agent 第一次视觉分析已经能够确定这些分析对象，多角度分析没有必要重复做同一步。

这里必须区分：

| 对象 | 例子 | 由谁负责 |
| --- | --- | --- |
| 原图视觉元素 | 背景、条带，以及两组条带实例 | 主 Agent 首次视觉分析 |
| 候选中的实现部件 | 遮罩、曲面、亮线、局部暗色区域 | 子 Agent 在草图或候选中探索 |

实现部件出现在某个候选中，不意味着原图中已经确认存在同名独立元素。不能因为一个候选采用曲面、另一个采用遮罩，就为同一条带建立两套视觉元素身份。

正常流程因此改为：

1. 主 Agent 建立统一元素表和必要实例组。
2. 各子 Agent 引用这些元素 ID，探索组成、特征形成方式和关系机制。
3. 主 Agent 整合三个候选库，直接沿用元素身份。
4. 最终交付仍有四库，但元素库不是跨报告合并的产物。

如果初稿确实遗漏元素或分类妨碍解释，允许子 Agent 提出具体问题，由主 Agent 决定是否修订。该例外不应变成每个子 Agent 必须重新拆图的常规流程；反馈字段及修订后的版本处理尚未确定。

## 6. 两步输入输出的职责划分

### 6.1 首次视觉分析

输入是用户要求和完整原图。输出 `visual_outline`，包含统一元素、必要实例组、显著特征和可见关系。

这一步回答“需要解释什么”，不预先输出物理成因或实现草图。探索方向在后续派发时制定，不强行塞入视觉初稿。

### 6.2 主 Agent 整合

输入是用户要求、完整原图、统一视觉初稿，以及子 Agent 输出的草图、特征和关系库。

主 Agent 回看原图，判断不同报告是否在描述同一现象；不能仅凭名称相同就合并。相同现象的不同机制保留为不同候选，真正重复的表达才去重。

最终输出为统一元素表和三个整理后的库，不再另写一套重复的观察、假设、实现建议和候选摘要。

## 7. 最终数据结构与模型提交接口不是一回事

最终制品需要完整的四库结构，但不等于主 Agent 必须重新生成所有正文。

讨论中建议：没有变化的条目可以直接引用，主 Agent 只生成有意义的合并判断、范围调整和必要新增内容，由后端组装完整结果。

这仍是接口方向建议。完整提交、分批整合或增量操作尚未选定，不应提前把某套编辑协议写成已确认方案。

模型负责语义判断；后端负责命名空间、持久化、来源记录、机械引用替换和结构校验。后端不能凭名称相似自动认定两个机制相同。

## 8. 独立探索不能被整合结果反向引导

主 Agent 可以根据报告发现缺口，并提出新的探索方向，但不能把既有机制结论改写进视觉初稿，再当作中性输入发给新的子 Agent。

例如，可以描述“交叉附近存在暗部”，不能在没有依据的情况下改成“上层条带投下阴影”，再要求子 Agent 独立探索。

视觉初稿服务于共同定位；候选库保存已经探索出的解释。二者不能在后续派发中混为一份标准答案。

## 9. 结束条件与未解问题

结束分析不要求消除所有分歧，也不要求选定唯一草图。需要继续探索的理由应是重要缺口，例如关键元素尚无可信组成方式，或某草图的重要依赖未被解释。

如果剩余问题需要编码和渲染才能区分，应该保留候选并交付。继续增加看同一原图的子 Agent 不自动产生新证据。

重要现象暂时没有形成候选时也不能丢失。已有草图可用 `unresolved` 记录；没有对应草图时，如何在最终制品中保留未解释现象，还需补充协议，不能为了满足字段要求编造候选。

## 10. 本次讨论的经验

1. **先确定要维护的对象。** 如果目标是可能性库，默认筛选和淘汰就不是合适的整合策略。
2. **把存在、适用和优先级分开。** 它们回答三个不同问题，不能用一个状态或分数代替。
3. **统一视觉对象，开放机制探索。** 固定元素身份能够减少重复拆分，不应同时固定其物理解释。
4. **合并表达，不抹去机制差异。** 去重应减少冗余，不以多数意见替代证据。
5. **按角色承担必要工作。** 子 Agent 不重复拆图，主 Agent 不重写全部正文，后端不代替模型作语义判断。
6. **最终结构与生成方式分开设计。** 完整制品可以由后端组装，不必要求模型一次输出所有内容。
7. **用户纠正应落实到接口变化。** 不能口头认同统一元素，数据结构却继续要求子 Agent 输出元素表。
8. **明确未决项。** 具体字段名、优先级格式、异常反馈和增量协议仍需讨论，不能把助手建议写成已实现事实。

## 11. 已确定与尚待确定

已确定的方向：统一视觉元素、子 Agent 三库探索、主 Agent 合并重复项、保留不同可能性、按草图或实例范围维护候选引用、优先级不代表淘汰、最终四库交付。

待确定的细节：优先级具体格式及草图级排序、单实例是否需要独立标识、未解现象与初稿异常反馈字段、简单元素组成的存放位置、完整或增量提交方式、测量输入扩展、实际 Schema 与旧结果迁移。

本次只沉淀文档，不代表上述设计已经接入分析运行流程。
