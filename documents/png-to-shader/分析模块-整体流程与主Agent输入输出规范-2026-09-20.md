# 分析模块：整体流程与主 Agent 输入输出规范

日期：2026-09-20  
状态：目标业务契约与字段建议稿；尚未实现或通过真实运行验证。  
范围：整体分析流程、主 Agent 首次视觉分析、主 Agent 整合及最终可能性库。  
设计依据：[主 Agent 讨论复盘与经验总结](主Agent-讨论复盘与经验总结-2026-09-20.md)。

本文区分已确认的职责与语义、用于表达这些语义的建议字段、尚未确定的接口细节。文中的约束属于目标设计，不表示现有代码已经执行这些检查。本文不提供已接入运行时的 JSON Schema。

## 1. 与此前子 Agent 规范的关系

此前的[子 Agent 输入输出规范](探索型子Agent-输入输出规范-2026-09-20.md)继续提供草图、特征、关系、候选和 `requires` 的基础语义。本次更新以下边界：

| 此前设计 | 本次目标 |
| --- | --- |
| 子 Agent 各自输出 `elements`，允许常规重新分类 | 主 Agent 首次确定统一元素；子 Agent 正常流程只引用这些元素 |
| 子 Agent 输出四库 | 子 Agent 输出 `sketch_library`、`feature_library`、`relation_library` 三库 |
| 主 Agent 需要跨报告对齐元素 | 主 Agent 沿用统一元素身份，主要整合三个候选库 |
| 整合可以被理解为取舍候选 | 合并重复项，保留不同可能性，维护适用范围和优先级 |

发生冲突时以上述新边界为准。此前文档未在本次改写，因此不能直接将其旧版完整示例作为新子 Agent 的最终协议。

## 2. 整体流程

```text
用户要求 + 完整原图
        ↓
主 Agent 首次视觉分析
  确定元素类别、实例组、显著特征和可见关系
        ↓
主 Agent 制定不同探索方向
        ↓
多个独立子 Agent
  使用同一元素身份，探索组成、特征和关系候选
        ↓
主 Agent 整合
  去重、汇集不同可能性、整理适用范围与优先级
        ├─ 存在重要且可由原图继续探索的缺口 → 新的独立探索任务
        └─ 已可交付，剩余区别需要实现或渲染 → 完整可能性库
                                                        ↓
                                         后续选择组合、编码、渲染和比较
```

这两个主 Agent 步骤是职责阶段，不要求新增两个独立 Agent，也不要求每步只能调用一次模型。上下文如何切换、是否分开执行调用，留待实现设计。

分析阶段不默认运行渲染，不承诺发现原作者的唯一机制，不把结构校验通过视为视觉验收。

## 3. 首次视觉分析：输入

| 材料 | 内容 | 要求 |
| --- | --- | --- |
| `user_request` | 用户原始要求及明确约束 | 不把模型判断改写成用户要求 |
| 完整原图 | 实际图像内容 | 独立多模态图像块；路径不能代替图像 |
| 图像尺寸说明 | 原图宽高，必要时提供 | 属于图像说明，不要求输出运行记录 |

文本业务输入可表达为 `{"user_request": "用户要求"}`，另附完整图像。首次分析不需要子报告、候选库、历史任务列表或预设视角目录。

## 4. 首次视觉分析：输出 `visual_outline`

输出由 `elements` 和 `relations` 两个数组组成。

### 4.1 元素

`element` 表示原图中的视觉分析对象，不表示已经选定的 Shader 图层、物理材质或实现部件。

| 字段 | 类型 | 要求 | 含义 |
| --- | --- | --- | --- |
| `id` | string | 必填 | 后续流程共用的元素身份 |
| `name` | string | 必填 | 中性视觉名称 |
| `scope` | string | 必填 | 原图中的区域或实例范围 |
| `salient_features` | string[] | 必填，可为空 | 首次观察的显著外观，不强制编造特征 |
| `instance_groups` | `{id, description}[]` | 可选 | 表达关系或有意义差异时需要的实例组 |

以类别描述重复元素；不因有二十根条带就生成二十份相同分析。必要时用两组朝向不同的实例表达关系。首版使用元素和实例组定位；是否增加单实例 ID 尚未确定。

### 4.2 可见关系

| 字段 | 类型 | 要求 | 含义 |
| --- | --- | --- | --- |
| `participants` | `{element_id, group_id?}[]` | 必填 | 涉及的元素或实例组 |
| `description` | string | 必填 | 可见排列、接触、交叉、疑似遮挡等 |

初稿关系不要求生成机制候选。存在歧义时在描述中保留，不直接写成物理因果。它与后续 `relation_library` 用途不同：前者提示可见组织，后者表达组织或依赖的形成可能性。

### 4.3 示例

以下是假想条带图的示例，不是对真实图片的测量结论。

```json
{
  "elements": [
    {
      "id": "E1",
      "name": "背景",
      "scope": "覆盖画面，在条带空隙中可见",
      "salient_features": ["近似均匀的深色"]
    },
    {
      "id": "E2",
      "name": "条带",
      "scope": "沿两个方向延伸的重复长条",
      "salient_features": ["边缘较亮", "部分交叉位置附近存在暗部"],
      "instance_groups": [
        {"id": "G1", "description": "从左上向右下延伸的一组"},
        {"id": "G2", "description": "从右上向左下延伸的一组"}
      ]
    }
  ],
  "relations": [
    {
      "participants": [
        {"element_id": "E2", "group_id": "G1"},
        {"element_id": "E2", "group_id": "G2"}
      ],
      "description": "两组条带交叉，交叉处呈现疑似交替的前后层次"
    }
  ]
}
```

### 4.4 输出边界

- 首次确定的是“有哪些视觉元素”，不是“每个元素的唯一组成机制”。
- 不在初稿中填写实现草图、候选优先级或物理成因。
- 探索方向属于后续派发指令，不是视觉初稿字段。
- 初稿不需要完整枚举所有特征；子 Agent 可以发现新的特征或关系，并关联到既有元素。
- 若后续发现元素遗漏或分类问题，由主 Agent 决定修订；不要求每个子 Agent 重新输出元素表。异常反馈格式与修订迁移规则待定。

## 5. 多角度探索的衔接契约

子 Agent 继续接收用户要求、完整原图、`visual_outline` 和 `exploration_direction`。每次探索独立，不传递其他子 Agent 的报告或完整聊天。

正常探索的业务输出改为恰好三个库：

```json
{
  "sketch_library": [],
  "feature_library": [],
  "relation_library": []
}
```

这里的空数组只展示顶层形状，不代表空报告即可被认定为成功完成。

元素 ID 和实例组 ID 引用主 Agent 的初稿；草图、特征、关系及候选 ID 可以是报告局部 ID，由后端隔离不同报告命名空间。

草图中的遮罩、曲面和亮线是候选组成部件，不自动登记为新的原图元素。子 Agent 不需要对其他报告去重、建立全局优先级或判断最终采用方案。

原有子 Agent 规范中简单元素的 `composition` 原本位于其输出 `elements` 中。移除子 Agent 的元素输出后，这部分应迁移到哪里尚未确定；不能未经讨论要求所有简单元素都生成复杂草图。

测量和裁剪是否成为子 Agent 可选输入仍未确定。本文不授权删除现有测量实现。

## 6. 主 Agent 整合：输入

| 材料 | 作用 |
| --- | --- |
| `user_request` | 判断与用户目标有关的差异和尝试价值 |
| 完整原图 | 回看报告是否描述同一视觉现象，核对新增观察 |
| `visual_outline` | 提供统一元素和实例组身份、初始视觉观察 |
| 各子 Agent 的三个库 | 提供组成草图、特征与关系候选，以及引用和前提 |
| 必要的来源句柄 | 由后端附带，用于读取、引用具体报告条目 |

不默认传入子 Agent 聊天过程、全部任务记录、日志、重试计数和提交版本。运行控制与错误修复按需提供简短信息，属于控制反馈，不扩展业务输入对象。

上述材料可以按需读取，而不必同时塞入一个请求。读取草图时应能取得其关联特征、关系、候选和前提，避免只给孤立 ID；具体读取接口尚未确定。报告索引需要让主 Agent 有机会发现独特候选，不能只保留多数意见摘要。

## 7. 主 Agent 整合：语义规则

### 7.1 去重和保留

- 同一现象的同义表达可以合并；仅名称相同不能作为合并依据。
- 同一机制的重复候选可以合并，后端保留所有来源。
- 形成方式、整体组成或关键依赖存在实质差异时，保留不同候选或草图。
- 不按票数、主观可信度或优先级淘汰候选。
- 同一元素可以由多张草图解释；多张草图可以共享局部候选，不展开所有局部候选的笛卡尔积。

### 7.2 适用范围

每张草图通过引用数组维护相关特征、关系及保留候选。必要时进一步限定到元素或实例组。

未被某张草图引用的候选仍保留在库中。没有建立关联不等于已经证明不兼容；适用范围可以随后续分析更新。

引用数组中的多个候选表示备选，不代表全部同时执行。如果确需叠加机制，应明确建立组合候选。

### 7.3 优先级

优先级表达具体范围内的尝试建议，不代表机制为真的概率。低优先级候选仍保留，未排序也不自动等同于低优先级。

排序理由可以涉及实现成本、关键外观覆盖和验证价值；不能将“优先尝试”改写成“已经选定”。建议在引用处记录局部优先级，避免给共享候选设置全局标签。

### 7.4 依赖与选择前提

关系库中的 `dependency` 表达对象之间的影响；候选的 `requires` 表达选择前提。两者继续分开。

合并或跨报告组装后仍需保留依赖和前提。优先级不能覆盖前提，引用存在也不代表全部候选组合已经验证兼容。

## 8. 主 Agent 整合：最终输出

最终业务对象保留四个顶层数组：

| 字段 | 来源与职责 |
| --- | --- |
| `elements` | 沿用主 Agent 确定的元素 ID、名称、范围和实例组 |
| `sketch_library` | 合并重复草图，保留不同组成，维护适用候选引用 |
| `feature_library` | 整理特征外观，合并重复形成候选，保留不同机制 |
| `relation_library` | 整理组织与依赖关系，保留形成候选和选择前提 |

最终元素条目至少保留 `id`、`name`、`scope`，必要时保留 `instance_groups`。不从子报告中重建元素身份，也不在最终结果中整段复制初稿中的特征和关系正文。

初稿仍由后端保存，用于追溯和核对覆盖情况。重要但尚未解释的现象不能丢失：已有草图可以使用 `unresolved`；没有草图承载时的最终表达字段尚待补齐。在该问题解决前，不能以“去重复”为由删除唯一的未解现象记录，也不能伪造机制满足候选数组要求。

其他基础字段沿用子 Agent 规范：

| 结构 | 基础字段 |
| --- | --- |
| 草图 | `id`、`name`、`element_ids`、`composition`、可选 `feature_refs`、`relation_refs`、`unresolved` |
| 特征 | `id`、`name`、`element_ids`、`appearance`、`candidates` |
| 关系 | `id`、`name`、`kind`、`participants`、`description`、`candidates` |
| 候选 | `id`、`mechanism`、`reasoning`、可选 `requires` |

不另设淘汰列表、唯一结论、候选处置台账或重复摘要。后端运行包装不属于这四个业务字段。

## 9. 适用引用与优先级：建议字段

以下是讨论中提出的字段草案，不是已经确定的运行时 Schema。它扩展此前只有 `candidate_ids` 的草图引用，使局部排序有明确存放位置。

```typescript
type ElementScope = {
  element_id: string;
  group_id?: string;
};

type CandidateRef = {
  candidate_id: string;
  priority?: "high" | "normal" | "low";
  priority_reason?: string;
};

type FeatureChoice = {
  feature_id: string;
  applies_to?: ElementScope[];
  candidate_refs: CandidateRef[];
};

type RelationChoice = {
  relation_id: string;
  applies_to?: ElementScope[];
  candidate_refs: CandidateRef[];
};
```

建议语义：

- `candidate_refs` 非空，候选属于被引用特征或关系。
- `applies_to` 如提供应非空，组 ID 属于对应元素，只收窄当前条目与草图的相关范围。
- 省略 `applies_to` 时沿用条目在当前草图中的范围，不表示适用于全库所有对象。
- 不同实例组需要不同候选范围时，可用多条明确区分范围的引用；重叠范围如何校验仍待确定。
- 优先级只在对应使用情境内比较；具体枚举和是否改用顺序数组待定。
- 草图本身的优先级也需要比较范围，不能直接照搬候选优先级字段作为跨对象总榜；该接口待定。

候选的 `requires` 继续使用 `{kind, id, candidate_ids}` 表达前提：单项内至少满足一个，多个前提项全部满足。它不因使用处改为 `candidate_refs` 而改变含义。

### 9.1 局部引用示例

假设特征 F1 为条带亮边，库中保存 F1-A 渐变、F1-B 细亮线、F1-C 曲面高光。下面仅展示平面草图中的一条特征引用，不是一份完整最终输出。

```json
{
  "feature_id": "F1",
  "candidate_refs": [
    {
      "candidate_id": "F1-B",
      "priority": "high",
      "priority_reason": "优先尝试直接控制窄亮边"
    },
    {
      "candidate_id": "F1-A",
      "priority": "normal"
    }
  ]
}
```

空间草图可以同时引用 A、B、C，并根据自身条件采用不同优先级。C 不在上述数组中不代表已被移出特征库；如它要求曲面相关前提，实际组合仍需满足这些前提。

## 10. 完成条件与后续探索

完成分析应围绕是否已形成可供后续尝试的候选结构，而不是是否消除全部分歧。

值得追加探索的情况包括重要元素尚无可信组成方式、关键外观缺少解释、草图的重要依赖尚不清楚。追加任务必须提出具体问题，保持独立探索，不通过复述旧报告引导确认。

需要编码、渲染或额外输入才能区分的问题保留到后续阶段。没有草图不表示元素已经解释；允许明确保留缺口。预算耗尽和执行失败由后端如实表达，不靠编造候选完成结构。

测量可以作为主 Agent 按需取证的方向，但本次没有确定新的工具契约、必做测量或证据传递规则。

## 11. 生成接口与后端职责

完整四库是最终制品格式，不等于主 Agent 必须一次重新输出全部内容。讨论建议保留直接引用已有条目、只生成必要合并和修改的可能；实际选择完整提交、分批提交或增量操作仍待确定。

| 主 Agent | 后端 |
| --- | --- |
| 判断条目是否语义重复 | 隔离报告局部命名空间，维护统一引用 |
| 判断草图、特征和关系的关联范围 | 按明确映射组装结果、替换引用 |
| 提出优先级和必要的新候选 | 保存来源、原报告和运行状态 |
| 发现重要缺口 | 校验结构、引用归属及直接选择前提 |

后端不能仅凭名称自动合并不同机制；主 Agent 也不需要生成完整来源台账。合并后旧 ID 的来源关系应保留，库中未被当前草图引用的候选不能被当作垃圾自动删除。

结构校验不判断物理真实性或视觉正确性。局部前提检查不等于求解全部组合，关系反馈和候选前提也不能混为一个图后简单禁止环。

## 12. 待确定与实施边界

| 未决项 | 当前边界 |
| --- | --- |
| 初稿遗漏与修订 | 由主 Agent 处理；具体反馈字段和版本迁移待定 |
| 简单元素组成 | 原先位于子输出 `elements.composition`，移除该输出后的承载位置待定 |
| 无对应草图的未解现象 | 必须保留；最终字段设计待定 |
| 适用范围 | 已有元素和实例组；单实例寻址及重叠范围规则待定 |
| 优先级 | 语义已明确；枚举、排序格式和草图级比较范围待定 |
| 模型提交接口 | 完整结果与增量生成分开考虑，尚未选择协议 |
| 测量及裁剪 | 不默认扩展子输入，也不删除现有能力 |
| 实际实施 | Schema、工具、提示词、Context Builder、校验、旧结果兼容和运行验证均需另行落实 |

本次产物是设计文档。没有修改现有分析流程，也未实测输入输出大小、探索覆盖或候选整合质量。
