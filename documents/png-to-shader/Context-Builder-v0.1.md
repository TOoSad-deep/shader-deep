# PNG → Shader：Context Builder 设计草案

V0.1 · 2026-09-10 · 待实现、待细化。

本文件保留为历史草案；当前版本请阅读 [共享黑板与 Context Builder V0.2](Context-Builder-v0.2.md)。

本文承接 [三 Agent 架构与分层生成流程 V3](分层生成流程.md)，将本轮讨论整理成可供评审的上下文构造方案。任务边界、交接方式和角色分工沿用已讨论方向；材料选择、压缩顺序和实现步骤是本稿提出的默认方案。本文不代表相关能力已实现或验证。

## 1. 核心设计

Context Builder 负责在每次模型调用前，根据角色、当前任务和任务内历史，选择并组织本次模型可见的信息。

首版采用一套公共构造流程，加分析、生成、评审三个角色的材料选择规则。Context Builder 是本项目的职责名称，具体函数和框架接入方式在实现时确定。

上下文以一次明确任务为边界：任务内延续工作过程；跨任务通过任务包、结果记录和制品交接。完整历史保留供回查，项目认识通过实验记录持续积累。

| 组成部分 | 负责的内容 |
| --- | --- |
| LangGraph 主图 | 派发任务、核对目标和基线、维护预算、执行状态更新、暂停与恢复 |
| Context Builder | 选择材料、加载必要图像、整理历史、控制输入大小、构造本次模型请求 |
| 三个角色的 Agent | 在任务范围内分析、生成或评审，使用配置的工具，返回业务结果 |
| 工具与制品存储 | 执行文件操作、编译、真实渲染和检查，保存对应代码、图像与日志  |

逻辑流程如下；各部分可以是同一应用内的函数或节点：

```text
主图核对状态并派发任务
          ↓
        任务包 ─── 相关实验记录与制品
          ↓                ↓
       Context Builder ← 任务内历史
          ↓
        模型调用
          ├─ 调用工具 → 保存制品与工具结果 → 再次构造上下文
          └─ 结束任务 → 返回结果记录 → 主图核对并安排下一任务
```

## 2. 需要分开的三类数据

| 数据 | 保存什么 | 如何进入模型上下文 |
| --- | --- | --- |
| 项目状态与制品 | 用户目标、版本、实验、候选、预览、评审、采用和接受记录 | 根据任务选择内容，加载必要制品 |
| Agent 任务历史 | 该任务内部的消息、工具调用、工具结果和工作摘要 | 保留当前工作所需的有效历史 |
| 本次模型上下文 | 角色指令、任务信息、选定材料、有效历史和工具定义 | 作为本次模型调用的实际输入 |

任务包中保存文件引用。模型需要看图时，必须实际加载图像；需要理解代码时，必须直接提供相关代码或允许通过工具读取。文件路径本身只起定位作用。

用户要求、工具测得的结果、视觉观察、模型假设和已执行决定分别表达。材料中的推测不能在摘要后变成用户要求或已确认事实。

## 3. 上下文生命周期

| 角色 | 一次任务的边界 | 任务内 | 跨任务 |
| --- | --- | --- | --- |
| 分析与实验规划 | 完成一次目标整理、问题诊断、实验规划或结果综合 | 延续分析、资料查阅和工具结果 | 从最新任务包与相关实验记录重新构造输入 |
| Shader 生成与优化 | 完成一个明确实验，产出候选检查点 | 延续代码读取、修改、编译修复、渲染与小步优化 | 新实验重新构造；同一实验暂停后继续时恢复有效历史 |
| 独立视觉评审 | 对指定版本完成一次局部或整图比较 | 延续看图、裁剪和区域检查 | 新的比较任务重新构造输入 |

新任务不直接继承其他 Agent 的完整聊天历史。需要追溯时，从结果记录定位并读取相关片段。

任务包固定该任务的目标和起始基线；任务内允许更新当前候选、工具结果和剩余预算。原型、局部工作版、整图保留版、用户接受版分别标记用途。

恢复任务或收回并行结果时，由主图重新核对版本。目标或基线变化后，主图刷新任务并安排必要的重新渲染、评价；Builder 不把新基线与旧任务历史悄悄拼在一起。

## 4. 任务包：开始时交代什么

以下是逻辑字段，最终命名和存储格式在实现时确定。

| 信息 | 最少内容 |
| --- | --- |
| 身份 | 任务 ID、角色、阶段；属于某个实验时附实验 ID |
| 目标 | 用户要求、目标版本、输出约束和相关用户反馈 |
| 问题 | 当前需要解决的偏差、待验证假设或需要作出的判断 |
| 起点 | 起始版本及用途、代码与预览引用、捕获条件；必要时同时提供局部工作版和整图保留版 |
| 范围 | 作用元素或组合、允许修改范围、关联依赖、保护项 |
| 资源 | 可用工具与资源、剩余执行预算、结束条件 |
| 材料 | 参考图、相关实验和评审记录、必要实现资料的引用 |
| 返回要求 | 本次需要的业务结果、制品及未完成事项说明 |

首次分析尚无 Shader 基线时，直接提供参考图和需求。目标尚未整理完成时，明确哪些是用户原始要求、哪些是分析待澄清项。

## 5. 三个角色的材料选择

所有角色每轮保留角色职责、当前任务目标、目标和基线标识、工作边界、保护项、结束条件及返回要求。关键字段直接来自本任务的有效状态，避免依赖聊天摘要恢复。

| 角色 | 开始任务时直接提供 | 按需补充 | 默认留在历史或制品中 |
| --- | --- | --- | --- |
| 分析 | 原参考、当前整图（如有）、用户目标、问题与依赖摘要、与本次判断有关的最新评审、相关实验结论 | 具体候选图、局部裁剪、失败实验细节、实现片段、机制研究资料 | 无关元素的详细日志、其他 Agent 的完整聊天 |
| 生成 | 实验要求、相关参考与基线预览、基线代码入口、场景结构摘要、修改范围和依赖、保护项 | 实际修改所需代码、被影响的光照或倒影实现、相关历史尝试、必要技术资料 | 其他候选的整套实现、无关实验、已解决的旧报错全文 |
| 评审 | 原参考、本次比较所需的基线与候选图、版本用途、目标问题、保护项、捕获条件和验证缺口 | 带位置标记的裁剪、区域检查结果；确需诊断时读取实现细节 | 生成者宣称优劣的解释、候选排名、与本次比较无关的评审结论 |

材料选择先使用任务、问题、元素及候选之间的明确关联。开始时提供相关记录摘要和可读取引用，再根据任务需要展开；首版采用这些直接关联完成检索。

评审先依据图像形成观察，再按需诊断原因。生成者报告的真实限制和未验证内容应提供给评审，但与“本版更好”等自我评价分开处理。

## 6. 每次调用如何构造上下文

1. **读取有效任务。** 取得任务包、当前任务进度和主图维护的剩余预算。
2. **装入稳定指令。** 提供角色职责、工作方式与结果要求，并配置该角色当前可用工具。
3. **装入任务信息。** 提供当前问题、目标、版本、范围、保护项和结束条件；刷新已有任务信息，避免每轮重复追加。
4. **选择角色材料。** 根据第 5 节规则加入相关业务记录与必要制品，标明来源、版本及观察或假设属性。
5. **整理任务历史。** 保留近期完整的工具调用与结果、未解决问题和仍然有效的工作摘要。
6. **检查输入大小并调用模型。** 为模型输出留出空间；必要时按第 7 节缩减材料，再发送请求。

建议的逻辑顺序是：稳定角色指令 → 当前任务 → 相关证据 → 历史摘要 → 近期工作过程。工具定义使用模型接口对应的工具字段；图像与其说明一起提供。具体消息类型和框架 hook 留到接入时核对。

工具返回后，把必要结果放入下一次调用的有效历史。任务结束后，主图提取业务结果和制品引用，形成下一角色的任务包。

### 视觉材料的特殊处理

- 图像标明参考、基线或候选身份，并关联代码、资源、参数、尺寸和时间等捕获条件。
- 局部裁剪附原图位置；局部任务也保留理解构图与保护项所需的整图视野。
- 视觉判断调用应能看到本次比较所需图像。纯编译修复调用可以优先携带代码和错误信息，重新进行视觉判断前加载有效图像。
- 过期预览只作为明确标注的历史材料。不能用旧预览代表新代码，也不能将尚未加载的文件视作已观察证据。
- 图像缺失或比较条件不一致时，返回证据缺口，由执行流程补齐后再评审。

## 7. 上下文预算与压缩

上下文预算控制一次模型输入的大小；执行预算控制实验次数、调用或时间等资源消耗，两者分别管理。

可用输入空间根据所用模型的上下文限制、输出预留及余量确定，并计入工具定义和图像成本。V0.1 先规定优先级，具体数值在模型和调用方式确定后配置。

输入过大时，按以下顺序处理：

1. 去除重复材料和与当前问题无关的历史展开内容。
2. 将已解决的报错、旧代码全文和大日志外置，保留结果摘要与回查引用。
3. 压缩较早的任务过程，保留尝试条件、观察结果、选择理由和未解决问题。
4. 缩小非必要资料的展开范围，保留继续读取的入口。

保留当前任务约束、有效版本、尚未解决的错误和近期完整工具交互。裁剪时保持工具调用与结果配对；工作摘要不能把失败写成成功，或把原因假设写成观察事实。

如果必需代码、图像和约束仍超出容量，则显式报告容量不足，调整任务范围或调用配置后再继续。视觉比较所需图像不能被无提示删除。

## 8. 结果记录：结束时留下什么

每份结果绑定任务、目标版本和实际使用的起始版本。

| 公共部分 | 内容 |
| --- | --- |
| 完成情况 | 完成、部分完成或无法继续，附具体原因和未解决事项 |
| 制品与证据 | 代码、预览、工具报告等引用，以及彼此对应的版本和条件 |
| 发现与限制 | 事实或视觉观察、原因假设、验证缺口和不确定性分别表达 |
| 后续建议 | 建议动作、作用范围及依据；必要时给出关联候选 |

| 角色 | 核心业务结果 |
| --- | --- |
| 分析 | 目标或拆解建议、问题诊断、假设变化、下一实验任务、采用或回退建议 |
| 生成 | 候选版本、实际改动、编译与渲染结果、实验记录和实现限制 |
| 评审 | 可定位的差异、目标改善、保护项退步、整体观感和判断不确定性 |

工具负责保存真实运行结果，Agent 的总结引用这些证据。主图记录核对后的采用决定；“建议采用”与“已采用”分别保存。整图保留与用户最终接受沿用 V3 的流程。

跨任务使用的实验摘要至少保留：当时的问题与假设、目标和起点、实际改动、证据、结论及其适用范围、未解决问题。重要摘要附证据引用，便于下一任务核查。

## 9. 示例：倒影偏宽

以下版本号和结果仅为设计示例。

| 步骤 | 交接内容 |
| --- | --- |
| 分析制定实验 E8 | 在目标 T2、整图基线 B7 上，验证横向扰动过强是否导致倒影偏宽；允许调整倒影扰动，保护主体轮廓、水线和色调 |
| 生成执行 | 保留同一任务内的读代码、修改、编译和渲染过程；提交候选 C12 与可对应的真实预览 |
| 评审比较 | 查看参考、B7 和 C12，记录“边缘更平滑，但整体宽度仍偏大”；未观察到指定保护项变化，原因尚不确定 |
| 分析再次启动 | 读取当前有效状态、评审及 E8 摘要；判断原假设受到削弱，建议检查倒影基础映射范围 |
| 主图处理 | 保存检查后的决定及所选版本，再构造下一任务；C12 是否成为起点由实际决定明确指定 |

跨任务留下的记录可以是：

> 在 T2/B7 条件下，E8 通过降低横向扰动生成 C12。评审观察到边缘变平滑，但整体宽度问题仍存在，因此“扰动过强是主要原因”的假设受到削弱。下一步可检查基础映射范围。附 B7、C12 和评审引用；采用状态以主图记录为准。

该记录提供后续判断依据，原始历史仍可回查。历史结果在目标或基线变化后需要重新判断适用性。

## 10. 首版实现范围与待定项

首版应用层需要四项能力：任务包与结果记录、按角色选材的公共 Builder、任务内历史整理、制品加载与引用解析。持久化位置和框架接入方式复用项目实际能力后再确定。

建议先用一个具体实验走通“分析 → 生成 → 评审 → 再分析”，保留每次调用实际包含的材料清单，检查以下行为：

- 同一生成任务能接着最新错误修复，跨任务能使用相关实验结论。
- 需要视觉判断时实际加载正确图像，预览与代码版本相符。
- 评审先获得目标和图像证据，生成者自我评价不默认进入首次评审。
- 主图实际决定与 Agent 建议分别记录，刷新任务后使用正确基线。
- 输入缩减仍保留当前约束、有效工具交互及未解决问题。

实施前还需确定：

| 待定项 | 确定依据 |
| --- | --- |
| 各角色的输入预算、图像尺寸和历史保留阈值 | 实际模型限制、图像调用方式与样例任务大小 |
| 代码直接注入的范围及摘要触发时机 | 单文件或多 Pass Shader 的实际规模、现有历史管理能力 |
| 消息存储、制品访问与每次调用的接入位置 | 当前应用代码、已安装框架版本及其真实请求链路 |

这份草案先确定信息流和构造规则。接入实现前需要核对上述运行时细节；本文未进行代码或模型调用验证。
