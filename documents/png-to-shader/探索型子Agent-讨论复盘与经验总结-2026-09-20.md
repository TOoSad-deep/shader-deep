# 探索型子 Agent：讨论复盘与经验总结

日期：2026-09-20  
状态：设计讨论结论，尚未据此修改运行代码、工具或 Schema。  
范围：分析模块中子 Agent 的定位、输入、输出和职责边界。  
配套文档：[探索型子 Agent 输入输出规范](探索型子Agent-输入输出规范-2026-09-20.md)。

## 1. 讨论起点与真正的问题

最初的问题是分析提示词难读，因此对提示词进行了标题、列表和主题分块。随后发现，更大的问题是 Agent 的输入输出过大、结构繁杂。

提示词分块改善了阅读，但没有减少模型需要处理的信息种类，也没有改变模型被要求承担的工作。此次讨论因此转向：子 Agent 到底负责什么，它完成这项职责最少需要什么材料，又应交付什么结果。

本次没有对真实请求做 token 统计，也没有通过新旧运行对比验证分析质量。本文对冗余、注意力分散和探索趋同的判断属于设计分析，不能写成已实测的收益。

## 2. 最重要的定位修正：子 Agent 负责探索

用户明确指出，子 Agent 的核心作用是探索，而不是给出一个所谓正确的回答。

这意味着子 Agent 的价值在于：

- 从原图中寻找可解释元素、特征和关系的不同组成方式。
- 提出主 Agent 尚未想到的可能性，允许质疑初步视觉拆分。
- 保留目前无法区分的候选，不为了完成报告而选定唯一机制。
- 将探索组织成后续能够比较和尝试的结构。

它不需要证明候选就是原作者使用的机制，也不需要输出已经验证的生成参数。但探索仍需区分可见现象与候选解释，不能把猜想写成已观察到的事实。

主 Agent 负责比较不同子 Agent 的产出、整理分歧、取舍和决定进一步验证方向；后端负责运行控制、持久化和结构校验。这是本次讨论中的职责分工，不表示相关改造已经落地。

## 3. 为什么旧输入看起来每项都有用，却仍然过重

讨论初期曾把输入分成三个目的：

1. 让子 Agent 分析：用户要求、原图、任务目标、视角、初步判断。
2. 让多个 Agent 协作：对象对齐、报告传递、共享证据、复核。
3. 让程序验证和追踪：任务 ID、结果 ID、预算、提交版本和修复状态。

用户进一步指出：第二类并不是探索任务天然需要的，第三类大部分应当由后端承担。由此得到两个重要修正。

### 3.1 解释已有字段的用途，不等于证明字段值得保留

报告传递服务于“阅读其他分析并复核”的流程。但当前希望子 Agent 独立探索，因此这种流程不是默认前提。

本次确定：子 Agent 不接收其他子 Agent 的报告，也不继承此前探索任务的聊天。主 Agent 可以提出新的探索问题，但不能借任务说明大段转述既有报告，变相把独立探索改成确认已有答案。

### 3.2 后端需要保存，不代表模型需要读写

任务 ID、结果 ID、调用计数、状态、提交版本和日志归后端。模型只在必要时接收简短的收尾指令或具体字段错误。

模型输出中的局部 ID 有不同用途：它们连接同一报告里的草图、元素、特征、关系与候选，是表达探索结构所需的引用，不是运行追踪信息。

## 4. 输入的最终边界

核心材料是用户要求、完整原图和主 Agent 的初步视觉元素分析。本次探索方向用于区分切入点；2D、3D、美学等预设只作参考，不要求子 Agent 套入固定结论。

初步视觉分析只描述：

- 有哪些元素，分为哪些类别。
- 各类元素或实例组在哪里。
- 有哪些显著的可见特征。
- 有哪些可见组织关系；不确定的关系保留不确定性。

初稿不应预先规定物理材质、成因或实现方法，也不是子 Agent 必须接受的标准答案。

每次探索保持独立任务边界。任务内部允许模型根据自己的分析和格式反馈继续处理；不继承其他任务的分析历史。这里的“原子性”不意味着强制单次模型调用或禁止本任务内纠错。

测量与裁剪是否可以作为额外输入，讨论中曾被单独提出，但没有形成最终启用规则。因此本次规范的标准输入不默认加入它们，也不据此要求删除当前程序中的测量能力。

## 5. 分类优先，避免重复实例重复分析

用户指出，旧分析容易把同一种元素的多个实例分别展开，重复解释公共组成原理。

本次确定以元素类别为主要分析单位：

- 先解释同类元素的公共组成。
- 将位置、朝向、尺度、裁切等记录为实例差异。
- 只有差异足以影响组成解释时，才拆分类别或单独讨论。
- 为表达关系而需要区分两组实例时，建立实例组，不必逐个登记所有实例。

例如，二十根交织条带通常可以归为一个条带类别、两个朝向组。公共截面、重复方式和亮边形成方式分析一次即可。

“同类共享组成原理”是优先探索的假设，不是不可推翻的事实。外观相似不保证成因相同；子 Agent 有权发现例外并重新分类。

## 6. 从平铺解释转向草图与共享候选库

最初提出的自然语言报告以“视觉拆分修正、候选解释、未解问题”组织。用户认可总体方向，但指出粒度和结构仍不足，尤其需要表达复杂元素的多个组成草图，以及草图内部特征、关系各自的多种可能性。

最终形成四部分：

| 部分 | 职责 |
| --- | --- |
| `elements` | 记录元素类别、位置、实例组和差异；简单元素可直接说明组成 |
| `sketch_library` | 记录复杂元素或多个元素共同参与的整体组成方案 |
| `feature_library` | 记录需要解释的可见特征及其形成候选 |
| `relation_library` | 记录元素、特征及跨层关系与依赖的候选 |

草图指结构化组成草案，不要求生成图片或编写 Shader。

### 6.1 控制分支粒度

- 整体部件划分、组织方式或关键依赖有实质差异，才增加一张草图。
- 只是亮边由渐变还是窄亮线形成，可以留在同一草图下，作为特征的候选。
- 一张草图允许保留多个局部候选，不要求分析时选定。
- 不把局部候选做笛卡尔积，展开成大量完整草图。
- 简单元素和简单关系不需要为了格式而编造多个方案。

### 6.2 草图独立成库

一张草图可能解释多个元素共同形成的效果。例如透明物体、背景与折射外观，无法自然归入单个元素内部。

因此草图独立存放，通过 `element_ids` 指向相关元素；元素不同时维护反向 `sketch_ids`。后端可反查，避免模型维护两套映射。

独立存储不意味着每张草图都扩张到整图。默认围绕有实际解释价值的局部或元素类别，确实需要跨元素时才扩大范围。

## 7. 特征、关系和选择依赖的边界

这是讨论最后补充的重要区分。

### 7.1 特征不自动包含依赖

“交叉处存在暗部”描述的是特征；“上层条带位置改变会使暗部位置改变”描述的是依赖。前者不自动表达后者。

关系库允许表达：

- 元素之间的排列、连接、遮挡与相互影响。
- 特征之间的依赖，例如某候选中局部曲率影响亮边分布。
- 跨层依赖，例如条带前后关系影响交叉暗部。

有方向的依赖需要区分影响源和受影响对象。普通并列或排列关系不强加因果方向。

### 7.2 依赖不能默认升级为事实

如果暗部来自人工绘制，它未必服从空间投影规律。某种影响关系通常只在特定草图或候选中成立，应由适用的草图或候选明确引用。

### 7.3 `requires` 与图像中的依赖不是一回事

| 概念 | 示例 | 用途 |
| --- | --- | --- |
| 现象或机制中的依赖 | 条带相对高度影响暗部范围 | 解释对象如何影响彼此，放在关系库 |
| 候选选择前提 | 采用空间投影候选，需要采用空间前后关系候选 | 约束候选组合，用 `requires` 表达 |

不能只保留 `requires` 就认为已经描述了全部依赖。反过来，也不需要为每句自然语言解释创建一个复杂的约束求解问题。

## 8. 为什么使用 JSON，以及它不能解决什么

JSON 便于后端解析、检查引用、索引对象和交给后续阶段。稳定结构应进一步通过 Schema 固定；仅把自然语言放进 JSON 外壳，并不能获得可靠接口。

因此需要明确：字段类型、必填与可选项、局部 ID、候选归属、实例组身份、引用范围和依赖语义。

但结构合法不证明视觉判断正确、机制可行或渲染效果被接受。校验不能变成强迫探索任务提供唯一答案的评分器。

## 9. 本次讨论得出的经验

1. **先定义角色价值，再裁剪接口。** 如果角色负责探索，就不应沿用以复核、对齐和证明正确为中心的全部要求。
2. **不要以已有实现反推需求。** 一个字段在当前协议中被使用，不代表新定位下仍然必要。
3. **把后端状态与模型表达分开。** 运行追踪由程序维护，模型只维护表达探索结构所需的局部关联。
4. **按类别解释共性，按差异处理例外。** 实例数量不应直接决定报告长度。
5. **分开整体方案和局部候选。** 共享候选库保留探索宽度，避免整体方案数量爆炸。
6. **明确关系端点与适用条件。** 不把元素关系、特征依赖和候选兼容混成一类文本。
7. **独立性要落实到实际输入。** 新建任务但仍传递旧报告，不能实现希望保留的独立探索。
8. **结构化应服务理解与后续选择。** 不因方便校验而不断增加模型要填写的字段。
9. **讨论时要说明分歧，而不是快速附和。** 此次关键改进来自用户对“协作材料天然必要”“子 Agent 应回答正确”等前提的纠正。

## 10. 已确定与尚待实施的事项

已确定：探索角色、预设仅参考、分类与关系初稿、任务独立性、四部分输出、草图保留局部候选、关系库支持跨层依赖、JSON 交付、后端与模型分工。

配套规范对字段名、端点类型、方向和引用校验作出最小落地约定。这些约定用于把讨论整理成可实现的设计，不代表讨论期间已经逐字段完成实现或测试。
