## 审查结论

在本次阅读和现有测试覆盖的范围内，没有确认需要立即修复的功能缺陷。当前目录职责能够支撑已经实现的单个生成 Agent，适合保留现有分层，并在第二个角色实际接入时增加对应模块。

这不代表多 Agent 系统已经实现：`schemas.py` 定义了 analysis、generation、review 三种角色，但当前应用实际运行的是 `agents/generation.py`。分析、评审 Agent 及其调度流程尚未接入。

可以用三个问题记住核心边界：

| 问题 | 对应模块 | 具体责任 |
| --- | --- | --- |
| 有哪些任务、候选与结果？ | `schemas.py`、`blackboard.py` | 记录业务事实、来源和引用关系 |
| 本次模型应该看到什么？ | `context/`、`middleware.py` | 选材、读文件、构造消息并加入请求 |
| 模型提出的动作怎样执行？ | `tools/`、`rendering/` | 检查预算、执行渲染、记录结果和释放资源 |

`blackboard.py` 应保持独立。工具需要向它写入结果，各 Agent 的 Context 需要从它读取材料，把它归入 `context/` 会模糊这一共享职责。

## 一次运行的调用链

```text
cli.main
  └─ run_shader：根据 PNG 与提示词创建初始目标和任务
      └─ run_generation：验证材料、建立 RenderSession
          └─ _execute：组装并运行 Deep Agent
              ├─ Context middleware：从最新黑板构造任务资料
              ├─ Loop middleware：提供剩余次数、限定工具
              └─ 模型提出工具调用
                  ├─ render_shader
                  │   └─ 专用线程 → render_candidate
                  │       └─ WebGL2Renderer → webgl2.js
                  │           └─ 保存 GLSL/PNG、更新黑板与快照
                  │               └─ 下一轮 Context 加载新预览或错误
                  └─ finish_shader
                      └─ 检查本轮渲染/预览资格 → 记录选择
                          └─ 返回已选文件中的源码并关闭资源
```

`agent.invoke` 本身会运行模型与工具之间的图循环。应用外层的 `while` 用来处理模型只回复文字、图已结束但尚未选择候选的情况；它仍受同一个会话的模型轮数预算限制。

## 关键实现的审查结果

| 检查项 | 当前实现与证据 |
| --- | --- |
| 工具定义 | `RenderSession.tools()` 使用 LangChain `tool(name)(method)` 包装绑定方法。名称显式指定，描述来自 docstring，参数 schema 从类型注解推断；会话不需要模型传入。 |
| 最新材料 | Context middleware 每轮通过 getter 读取最新 `session.state`，因此能获得上一轮工具新登记的候选和错误。现有测试验证刷新及原始历史不被改写。 |
| 图片交付 | Context 读取真实文件字节并组装 `image_url` 内容块。集成测试检查生成 PNG 的 Base64 内容确实进入后续模型请求。 |
| 次数限制 | 渲染次数和模型轮数分别计数，编译失败也消耗尝试次数。测试覆盖反复渲染、只回复文字和预算耗尽的停止情况。 |
| 选择资格 | 必须是本轮成功渲染且已将预览加入后续请求的候选。同一批调用中刚渲染就结束会被拒绝，已有测试覆盖。 |
| 工具范围 | 模型请求只提供本轮允许的工具，执行阶段再检查工具名称。测试覆盖猜测调用内置写文件工具时被拒绝。 |
| 历史记录 | 黑板登记函数返回新状态，拒绝相同 ID 覆盖；候选生成或结果提交不会自动改变任务原始基线。相关测试通过。 |
| 资源生命周期 | 会话让浏览器初始化、渲染和关闭都在同一个工作线程中执行。Python 用 ExitStack 释放浏览器资源，JavaScript 用 finally 释放每次编译的 Shader/program。线程与真实浏览器测试通过。 |
| 最终交付 | 最终源码从已选定候选文件读取，避免输出另一段未渲染的模型文本。测试验证无额外模型调用、CLI 输出及未完成时保留制品。 |

### 理解这些结果时需要保留的边界

- `successful` 表示工具成功生成了 PNG；`presented` 表示预览进入后续模型请求。两者都不能证明模型作出了正确的视觉判断。
- `finish_shader` 只要求模型提供非空自检结论。保护项是否满足、图片是否足够相似，当前仍需要模型比较和用户验收。
- PNG 读取函数检查文件存在和扩展名，随后编码原始字节；它没有解码输入图片校验内容，也没有缩放或裁剪。真实渲染测试会独立解码输出 PNG 并检查像素。
- Context 按任务范围加载完整源码、原始图片和结果。仅通过历史结果提到的候选，不会自动展开其源码和图片；需要查看这些制品时应显式选为任务输入。
- 业务黑板不是模型对话历史，`run.json` 也不是可直接恢复全部 Agent 执行的 checkpoint。
- 现有生成入口是同步流程。Context middleware 有异步钩子，不能据此认定整个生成循环已支持异步运行。

以上是现有能力范围，不作为本轮新增改造要求。

## 对后续多 Agent 的结构建议

| 什么时候 | 建议 | 为什么 |
| --- | --- | --- |
| 接入分析或评审角色时 | 增加 `agents/analysis.py`、`agents/review.py` 及各自的 Context 模块 | 角色编排和选材策略保持对应，同时复用同一套业务记录 |
| 第二套实际中间件出现时 | 再考虑将 `middleware.py` 拆成 `middleware/` | 当前两个类都服务生成流程，暂时没有必要预建通用策略框架 |
| 多个任务并行产出时 | 由主流程统一接收、登记结果，并明确冲突处理 | 当前黑板函数返回独立新状态；不同任务的返回快照没有自动合并机制，最后一次赋值不能代表汇总 |
| 候选和历史材料实际变大时 | 在各 Agent 的 Context 中分别定义选材与内容预算 | 当前完整加载策略适合小范围任务，尚未实现按 token 或图片数量裁剪业务材料 |

当前无需把所有顶层文件都改成文件夹，也无需引入统一 Agent 基类、Context 工厂或黑板数据库。
