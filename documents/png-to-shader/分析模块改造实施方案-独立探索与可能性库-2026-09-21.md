## 2. 改造目标与非目标

### 2.1 目标

1. 主 Agent 建立统一视觉对象，子 Agent 独立探索组成方式，主 Agent 整理可能性库。
2. 模型只读写当前职责所需的业务内容，运行记录由后端维护。
3. 通过公共组成、共享候选、按需读取和增量整合减少重复表达。
4. 保留不同机制、适用范围、局部优先级及选择前提，供后续编码和渲染比较。
5. 将结构合法、材料已呈现、分析已交付和视觉效果已验收分别记录。

### 2.2 本次不做

- 不新增独立拆图 Agent、Review Agent 或综合 Agent；仍只有主 Agent 与探索子 Agent 两类角色。
- 不接入分析到生成的自动调度，不在分析阶段自动编写 Shader 或渲染。
- 不建立通用约束求解器，不枚举局部候选的笛卡尔积。
- 不新增数据库、向量检索、通用 Agent 编辑框架或新的外部依赖。
- 不借改造修改现有模型选择、并发、重试、测量额度或输出预算默认值。
- 不给草图数量、候选数量或文字长度新增未经讨论的业务硬上限。
- 不将当前测量能力删除，也不默认把测量和裁剪扩展为子 Agent 标准输入。

“输入输出更小”是待验证目标。三库结构本身仍可能很大，不能仅凭字段减少宣布 token 或质量改善。

## 4. 目标流程与请求边界

```text
用户要求 + 固定原图字节
        ↓
主 Agent：首次视觉分析
        ↓ 提交 visual_outline
后端：校验、保存统一元素及实例组
        ↓
主 Agent：制定探索方向并派发
        ↓
多个新的独立子任务：三库探索报告
        ↓
后端：校验、隔离局部 ID、保存不可变原报告
        ↓
主 Agent：查看目录、读取相关对象、提交整合修改
        ├─ 新的可取证缺口 → 中性探索方向 → 新子任务
        └─ 可以交付 → 后端组装最终四库及运行包装
```

### 4.1 主 Agent 首次视觉分析

业务输入仅含 `user_request`，另附完整原图和必要尺寸说明。暂不提供子报告、候选目录、任务列表或预设视角目录。

业务输出为 `visual_outline`：

- `elements`：`id`、`name`、`scope`、`salient_features`，必要时含 `instance_groups`。
- `relations`：参与元素/实例组及可见关系描述。

元素按类别组织；特征可以为空；歧义保留在描述中。初稿不包含机制候选或物理成因。后端在提交成功后再允许派发探索，避免正常路径在没有统一元素身份时启动子任务。

本版建议沿用首批至少两个独立探索方向的现有多视角边界；不固定要求使用全部预设，也不要求每个方向产出相同数量的候选。

### 4.2 探索子 Agent

标准文本业务输入恰好为：

```json
{
  "user_request": "用户原始要求及明确约束",
  "visual_outline": {"elements": [], "relations": []},
  "exploration_direction": "针对原图提出的中性探索切入点"
}
```

该示例只表示输入形状，不表示空初稿足以派发。完整原图必须作为独立多模态图像块提供。

子 Agent 正常业务输出恰好含 `sketch_library`、`feature_library`、`relation_library`。没有内容的库用空数组，对象内部空的可选字段省略。三库全空不自动认定成功；确有未解问题或无法开展时通过控制反馈记录，不编造候选。

每次派发创建新的独立历史。任务内部允许多轮分析和修复；不得传入兄弟报告、主 Agent 完整分析历史或已有候选的转述。主 Agent 可以传达“需要探索的问题”，不能把先前答案包装成问题前提。

### 4.3 主 Agent 组织与整合

稳定业务输入为用户要求、原图、统一初稿。动态材料包括报告/库目录、按需读取的条目，以及后端已保存的整合结果。

模型不默认读取完整任务记录、提交版本、日志或重试过程。必要的来源句柄、运行限制提醒、错误路径和短回执属于控制材料，与业务对象分开。

首次观察和整合是同一个主角色的不同阶段。本版建议使用不同提示词与工具集合，在阶段边界由后端基于已接受产物重新建立消息列表。主调用计数跨阶段累计，不因更换消息列表或 Agent 图实例而重置。

预设视角只在组织探索时作为简短参考提供，不进入子 Agent 的完整目录输入。探索派发以 `exploration_direction` 为主要模型参数，运行 ID、用途标签与配置快照由后端维护。

## 5. 业务数据模型

### 5.1 三库的职责

| 结构 | 保存内容 | 不承担的内容 |
| --- | --- | --- |
| `sketch_library` | 整体组成、涉及元素、特征与关系引用、具体未解问题 | 不重复展开每个局部机制，不要求整图方案 |
| `feature_library` | 外观与位置、相关元素、形成候选 | 不将候选机制写成已确认外观 |
| `relation_library` | 组织关系或有向依赖、端点、成立方式候选 | 不把所有关系视为事实，不替代选择前提 |
| `Candidate` | 机制、简短理由与局限、可选 `requires` | 不要求概率、排名、唯一答案或完整渲染计划 |

草图只维护正向引用，元素不反向维护 `sketch_ids`。同类实例共享公共组成，只有有意义差异才细分实例组或提交初稿问题。

局部候选不同但整体组成未实质变化时，共用一张草图；只有部件划分、组织方式或关键依赖发生实质变化时再增加草图。

### 5.2 关系与选择前提

- `organization` 表达排列、连接、遮挡等组织，端点不携带因果方向。
- `dependency` 允许元素、特征、关系作为端点，至少一个影响源和一个受影响对象；实例组只附在元素端点上。
- `requires` 指向某个特征或关系的候选集合；单条内为“至少一个”，多条之间为“全部满足”。
- 草图引用的多个候选表示备选范围。需要同时使用的机制应明确写成组合候选。
- 没有前提声明或没有建立适用关联，不代表所有组合已经验证兼容。

### 5.3 ID 与来源

统一元素和实例组 ID 来自主 Agent 初稿；草图、特征、关系、候选使用子报告内部 ID。后端以报告身份隔离局部 ID，给主 Agent 返回可定位的句柄，模型不必自行拼接全局名称。

原报告不可变。后端保存原条目到最终条目的来源映射；主 Agent 新增的机制标记为主 Agent 新增，不能伪装成某个子报告已提出的内容。

最终业务对象恰好四个数组：`elements`、`sketch_library`、`feature_library`、`relation_library`。版本、来源、失败任务与预算属于后端包装，不扩充模型四库正文。

## 6. 本版接口建议与待冻结项

以下建议是为闭合协议提出的第一版选项。评审时应逐项保留、调整或替换；在相应问题解决前，不将不完整 Schema 宣布为可交付协议。

| 问题 | 本版建议 | 需要验证或确定的边界 |
| --- | --- | --- |
| 简单元素组成无存放位置 | 允许只有名称、元素引用和一条组成描述的最小草图；无需特征/关系引用，也不强制每个简单元素都产出草图 | 这一建议扩大草图的使用范围，需确认是否符合期望；不能沿用旧 `elements.composition` 却不说明接口变化 |
| 没有草图承载的未解现象 | 最终元素增加可选 `unresolved: string[]`，只记录该元素仍未被解释的具体现象 | 跨元素问题由主 Agent 指定主要关联对象并描述其他参与者，避免复制；若表达不清，应重新讨论字段，而非强塞单元素 |
| 子 Agent 发现初稿遗漏或分类问题 | 增加窄的控制反馈入口，提交位置、问题、受影响的已有元素；不让子 Agent 输出新元素表 | 问题可在子任务继续探索时上报；后端在批次安全边界交给主 Agent 处理 |
| 无法形成任何候选 | 允许报告无法完成探索的具体原因，由后端保存未完成状态和问题 | 不以三库空数组冒充有效探索，也不强制伪造草图 |
| 优先级 | 最终草图引用采用可选 `candidate_refs` 的局部优先级及理由，缺省表示未排序 | 子报告仍可使用无排序的 `candidate_ids`，后端适配；首版不引入跨对象的草图总榜 |
| `applies_to` 重叠 | 首版允许同一条目按互不重叠的实例组分别引用；拒绝同一草图内含义冲突的重叠声明 | 省略范围表示当前草图中的条目范围；不能与覆盖同一范围的第二条声明静默叠加；不新增单实例 ID |
| 测量与裁剪 | 保留主 Agent 现有工具及缓存，取到的材料按需进入主请求；子输入首版不加入 | 不将测量结论借初稿改写为已确认的机制；如需子任务使用图像证据，另定可选输入契约 |

初稿修订另外遵循以下建议：

1. 原元素和组 ID 不得被悄悄改成另一个对象的身份；修订记录由后端保存。
2. 新增不冲突的元素可追加；已有报告仍保留原版本绑定。
3. 拆分、合并或重定义元素时，主 Agent 明确给出受影响范围；不让后端按名称推断迁移。
4. 简单一对一映射可以机械替换；一对多、范围不清或会改变机制含义的迁移必须逐项处理，不能复制候选到所有新对象。
5. 有未解决迁移时保留可用结果和问题状态，不能把存在悬空引用的工作集合发布为完整四库。

## 7. 主 Agent 整合协议建议

### 7.1 采用“默认保留 + 明确修改”

本版推荐增量整合。后端先将有效子报告纳入按命名空间隔离的候选工作集合，不自动作语义去重。主 Agent 不必重新输出未改动正文。

正常工具操作建议按业务表达，而不是开放任意文件写入：

| 操作 | 模型负责 | 后端负责 |
| --- | --- | --- |
| 查看目录 | 选择要理解的对象或范围 | 列出可发现的条目、机制差异和句柄 |
| 读取对象 | 选择草图、特征、关系或候选 | 返回正文及必要引用对象，记录实际呈现 |
| 合并同义条目 | 指明来源、共同含义、需要保留的不同候选 | 分配/沿用规范 ID，合并来源并替换所有相关引用 |
| 调整适用引用 | 指定草图、对象范围、保留候选和局部优先级 | 校验归属、范围和前提，再保存 |
| 新增或修订内容 | 写有意义的新组成、新候选或必要文字修订 | 保存作者来源、版本及引用，不改写原报告 |
| 完成交付 | 声明已完成必要整理，保留未解问题 | 校验并导出最终四库及真实运行状态 |

具体工具名称和参数在协议冻结阶段确定。首版不提供以“低优先级”“未使用”为理由的候选删除操作；合并重复条目属于保留语义与来源的归并。

### 7.2 合并是完整业务操作

合并特征时，不允许通过覆盖整个 `candidates` 数组而静默丢掉来源候选。主 Agent 应说明哪些候选重复；后端保留未参与归并的候选，并重写草图引用及 `requires`。

合并关系还需要处理参与端点，合并候选需要检查机制、前提和适用语义。相似名称不构成合并依据；前提不同或会丢失关键差异时保留分开的候选。

一次修改先作用于临时副本，完成归属、引用和直接前提校验后才发布。失败只返回具体路径和原因，不发布部分替换结果。原报告、旧版本及来源仍保留。

工具回执应短，返回受影响句柄和下一步必要信息，不把整个库再次返回。若请求响应不确定，依靠调用身份或操作回执核对已提交结果，不能通过重放操作创建重复条目。

### 7.3 语义读取与机械复用分开

后端直接保留某个原条目，不要求主 Agent 重写正文。但主 Agent 要对它作合并、实质修订或优先级判断时，必须已收到相关正文和必要前提。

程序维护“已入库、已呈现、已作整合判断”等不同状态。目录存在不证明已理解，后端组装成功不证明主 Agent 审阅了每个条目。

最终交付检查应确保每份有效报告的候选都已纳入，目录覆盖全部条目，并对任务关心的关键范围完成必要读取。若因预算无法完成必要整合，应保存可用集合并标记部分完成，不能把默认并集宣布为全面审阅后的结果。

## 8. 读取与上下文控制

### 8.1 目录不能隐藏独特候选

按报告和元素范围组织轻量目录，提供类型、名称、简短机制描述和可定位句柄。目录由已有内容生成，不另调模型产生多数意见摘要。

所有候选都应可发现，包括未被任何草图引用的条目。目录过大时分段读取并返回覆盖范围；不以排名截断，也不要求默认请求携带全库目录正文。

### 8.2 读取草图时返回有上下文的对象集合

读取草图应返回草图及其引用的特征、关系、保留候选与必要前提。关系端点和 `requires` 分开遍历，使用访问集合避免递归重复或循环。

一次返回放不下时拆成完整条目并附剩余句柄，不截断 JSON，也不把未返回依赖标记为完整呈现。传输大小保护沿用现有机制作为初始基线，必要调整应可配置并由真实请求验证，不转化为业务候选数量限制。

### 8.3 请求正文和历史共同治理

- 首次观察完成后，以已接受初稿进入组织探索/整合阶段，不继续携带首次提交的完整修复历史。
- 子任务内部保留自己的分析与必要纠错历史，禁止跨任务继承。
- 整合阶段以已经保存的工作集合为业务状态，围绕当前处理范围构造材料。
- 在整合操作已接受、无待修复提交的安全边界，可以重建消息列表；只保留必要控制摘要、待处理问题和当前选入材料。
- 重建消息不能拆散工具调用与返回配对，也不能丢弃尚未接受的修改或未解决错误。
- 后端累计的预算、事件、呈现记录和来源不随历史裁剪重置。裁剪过的正文需要时可重读，曾呈现不等于仍在当前请求里。

不使用额外摘要模型隐藏调用成本。该方案不承诺任意长运行都有固定上下文；记录真实请求大小，再调整材料选择。

## 9. 后端校验与运行边界

### 9.1 校验顺序

1. 校验 JSON、字段类型、必填内容和未知字段。
2. 校验报告内 ID 唯一及引用对象的身份、类型、归属。
3. 校验元素/实例组范围、组织与依赖端点、草图相关引用范围。
4. 校验候选前提在草图中可定位，且保留候选范围存在直接交集。
5. 对语义整合操作检查所需正文是否实际进入模型请求。
6. 在暂存结果上完成全部检查，接受后再更新业务状态与制品。

身份不合法时，不继续推导错误引用所对应的范围或兼容性。局部修复继续复用正常校验入口，不绕过业务检查。

### 9.2 前提检查的限度

直接前提检查不证明存在完整兼容组合；后续选定具体组合时仍需检查全部生效前提。本轮不穷举组合，不对关系反馈统一禁止环，不将结构校验当作机制真实性检查。

### 9.3 保留现有运行设施

保留原图字节固定、任务独立历史、批次内并发、协调器串行合并、模型调用与网络尝试分别计数、完整响应检查、失败保留和局部草稿修复。

主 Agent 各阶段共享现有主调用预算，追加探索及失败仍计入任务总数。运行额度属于后端控制；模型只在决策需要时收到简短剩余额度或收尾反馈。

提交修复可以携带必要的草稿身份和版本，但不把整份运行台账再次注入每轮业务上下文。历史运行和失败制品不删除。

## 13. 用量与质量观测

按首次观察、子探索、主整合三个阶段记录：

- 模型实际请求中的系统提示、工具 Schema、业务材料、工具历史的大小与图片数量。
- 服务返回的输入/输出 token、可用的缓存用量信息；缺失时标记不可用，不用估计值冒充服务计量。
- 单次最大请求、全运行累计用量、调用数、修复次数、报告读取次数和耗时。
- 元素、草图、特征、关系、候选数量，以及独特候选保留情况。

减少模型用量不能靠丢弃机制差异、隐藏未解现象或缩小任务目标实现。候选更多也不自动意味着探索更好，应由同图对照阅读判断是否存在实质差异和足够图像依据。

用量观测保留在运行记录中，不把这些统计字段重新要求 Agent 填写。
