# 探索型子 Agent 输入输出规范

日期：2026-09-20  
状态：本次讨论形成的目标规范；尚未接入当前模型工具、数据结构或执行流程。  
范围：单个探索型子 Agent 的业务输入与交付内容。  
设计依据：[讨论复盘与经验总结](探索型子Agent-讨论复盘与经验总结-2026-09-20.md)。

文中的“必须”指目标协议约束，不表示当前代码已执行该检查。字段名、引用端点类型和依赖方向是为落实已确定原则而作的具体格式约定。本文定义逻辑契约与合法 JSON 示例，不包含已经接入运行时的 JSON Schema 文件。

## 1. 角色与完成标准

子 Agent 负责基于用户要求与完整原图，独立探索元素的组成方式、特征形成方式和关系机制。

交付应使主 Agent 能理解：有哪些元素类别、哪些整体组成值得尝试、每种组成保留哪些局部可能性，以及哪些依赖只在某些解释下成立。

子 Agent 不负责选出唯一正确机制，不承担跨报告综合、实际渲染、全局追踪或最终视觉验收。允许报告只含一个合理草图或一个候选，不为凑数添加分支；也允许明确保留无法解释的问题。

## 2. 输入规范

### 2.1 核心材料

| 材料 | 内容 | 边界 |
| --- | --- | --- |
| `user_request` | 用户要求与明确约束 | 保留原意，不把模型判断升级为用户要求 |
| 完整原图 | 实际图像内容 | 作为多模态图像块传入，不用文件路径或文字描述代替 |
| `visual_outline` | 主 Agent 的初步视觉元素分析 | 包含类别、位置、显著特征与可见关系，允许质疑和重新分类 |
| `exploration_direction` | 本次探索切入点 | 引导发散，不预设答案；2D、3D、美学等预设只作参考 |

文本部分只使用上述三个 JSON 字段；原图是同一请求中的独立图像块。图像尺寸可作为必要的图像说明提供，不要求子 Agent 输出运行身份或原图数据。

### 2.2 初稿粒度

- `visual_outline.elements` 按类别描述，每项包含 `id`、`name`、`scope`、`salient_features`。
- 有必要区分实例组时增加 `instance_groups`，每组包含 `id` 和 `description`。
- `visual_outline.relations` 每项包含 `participants` 与 `description`。参与者使用 `element_id`，必要时附 `group_id`。
- 初稿关系以图像组织线索为主，例如平行、接触、交叉、疑似遮挡。尚未确定的线索在描述中明确，不直接认定物理成因。
- 不预先提供实现草图、材料成因、其他子 Agent 的结论或待确认的标准答案。
- 同类先考虑公共组成，但允许子 Agent 发现例外、拆分类别或合并初稿对象。

### 2.3 独立性与非业务控制

每次派发启动一个新的独立探索任务，不继承其他任务的聊天、报告或主 Agent 的完整分析历史。主 Agent 可以将缺口转化为新问题，但不得在任务说明中复述其他报告以引导确认。

本任务内部可以保留自己的分析和字段修复历史。“原子性”不等于单次调用。

任务 ID、结果 ID、预算计数、提交版本和日志由后端维护。需要纠错时，只向模型返回必要的字段位置和具体错误；需要收尾时可以给简短指令。这些不是本规范的业务输入字段。

测量证据和裁剪材料是否扩展为可选输入，本次未确定，标准输入不默认加入。本文也不授权删除现有测量实现。

## 3. 输出顶层

输出是一份 JSON 对象，恰好包含四个数组：

| 字段 | 内容 |
| --- | --- |
| `elements` | 元素类别及必要的实例组、差异和简单组成 |
| `sketch_library` | 独立的整体组成草图库 |
| `feature_library` | 可见特征及其形成候选 |
| `relation_library` | 组织关系、影响关系和依赖及其候选 |

四个顶层键必须存在，没有内容的库使用空数组；对象内部无内容的可选字段省略，不输出 `null` 或占位字符串。交付有效分析至少需要一个元素；材料不足或运行失败由后端表达，不通过编造元素来满足结构。

实际交付使用纯 JSON 或等价的结构化工具参数，不在对象外附加 Markdown、解释段落或重复摘要。后端可以在业务对象外包裹运行身份与状态，但不能要求模型重复填写。

四个库均属于当前报告内部。不同子 Agent 之间的合并、去重、对齐和 ID 命名空间由主 Agent 与后端处理。

## 4. 元素与草图

### 4.1 元素类别

| 字段 | 类型 | 必填 | 含义 |
| --- | --- | --- | --- |
| `id` | string | 是 | 报告内元素类别 ID |
| `name` | string | 是 | 中性类别名称 |
| `scope` | string | 是 | 原图中覆盖的区域或实例范围 |
| `instance_groups` | array of `{id, description}` | 否 | 为表达关系而有必要区分的实例组 |
| `instance_variations` | string[] | 否 | 同类实例中有意义的差异 |
| `composition` | string | 否 | 简单元素的直接组成说明 |

元素以类别为单位，不逐根、逐孔或逐颗复制相同分析。重复结构默认共享组成，发现影响机制的差异时才重新分类。

简单元素使用 `composition`，不再为同一组成建立专属草图；需要比较复杂组成的元素由 `sketch_library` 解释，不在 `composition` 重述。简单元素仍可以参与跨元素草图，例如简单背景参与透明物体的折射解释。

复杂元素本身已识别、但无法提出可信草图时，允许暂时没有草图，不强制凑方案。主 Agent 不应把缺少草图自动理解为该元素已经得到解释。

### 4.2 组成草图

| 字段 | 类型 | 必填 | 含义 |
| --- | --- | --- | --- |
| `id` | string | 是 | 草图 ID |
| `name` | string | 是 | 区分整体组成方式的名称 |
| `element_ids` | string[]，非空 | 是 | 草图涉及的元素类别 |
| `composition` | string[]，非空 | 是 | 部件与整体组织方式 |
| `feature_refs` | FeatureChoice[] | 否 | 本草图采用的特征范围及保留候选 |
| `relation_refs` | RelationChoice[] | 否 | 本草图采用的关系范围及保留候选 |
| `unresolved` | string[] | 否 | 本草图仍未解释的具体问题 |

只有整体部件划分、组织方式或关键依赖发生实质变化时，才增加草图。亮边或暗部的局部做法不同，优先维护在候选库，不展开全部组合。

草图可以涉及多个元素，但不默认扩大为整图方案。仅由草图维护 `element_ids`，元素不反向维护 `sketch_ids`。

`composition` 可以描述候选中的部件，不意味着这些部件都是图像中已确认的独立元素。若确实需要程序化引用某个部件，应先明确其稳定身份；本版不为所有实现部件增设第五个库，不允许引用未声明的部件 ID。

## 5. 特征库

| 字段 | 类型 | 必填 | 含义 |
| --- | --- | --- | --- |
| `id` | string | 是 | 特征 ID |
| `name` | string | 是 | 特征名称 |
| `element_ids` | string[]，非空 | 是 | 特征关联的一个或多个元素类别 |
| `appearance` | string | 是 | 原图中需要解释的现象与位置，允许表达观察歧义 |
| `candidates` | Candidate[]，非空 | 是 | 该特征的形成可能性 |

特征描述外观，候选描述机制。例如“条带边缘较亮”属于 `appearance`，“渐变、细亮线或曲面高光”属于不同候选。

仅观察到现象而还没有机制时，不编造空洞候选；可以先在元素差异或草图 `unresolved` 中记录。一个机制若由多种操作共同组成，可写为一个组合候选，不假装这些操作都是互斥方案。

## 6. 关系库：包含元素关系、特征依赖和跨层依赖

| 字段 | 类型 | 必填 | 含义 |
| --- | --- | --- | --- |
| `id` | string | 是 | 关系 ID |
| `name` | string | 是 | 关系名称 |
| `kind` | `organization` / `dependency` | 是 | 组织关系或有方向的影响依赖 |
| `participants` | Participant[]，至少两项 | 是 | 关系端点及必要的方向 |
| `description` | string | 是 | 要解释的关系或待探索的影响，不把推测写成已证实事实 |
| `candidates` | Candidate[]，非空 | 是 | 关系可能怎样成立 |

Participant 的字段：

| 字段 | 类型 | 必填 | 含义 |
| --- | --- | --- | --- |
| `kind` | `element` / `feature` / `relation` | 是 | 端点类型 |
| `id` | string | 是 | 对应库中的 ID |
| `group_id` | string | 否 | 仅元素端点允许，且必须属于该元素 |
| `role` | `source` / `target` | 条件必填 | 依赖关系的影响源与受影响对象 |

`organization` 用于排列、连接、遮挡等组织，参与者不填写 `role`。`dependency` 必须至少包含一个 `source` 和一个 `target`，用于描述影响方向；同一端点不能在同一关系中同时担任两个方向。若存在反馈，可分别描述两个方向，不以一条无方向文本替代。

端点身份是类型、ID 和可选实例组的组合。两组同类条带是两个不同端点，不需要拆成两种元素。

三类有效表达：

- 元素到元素：例如一组条带对另一组的作用。
- 特征到特征：例如某个空间候选中，轮廓弯曲影响亮边分布。
- 跨层：例如条带的前后关系影响交叉暗部，此时源端点可以是 `relation`，目标端点为 `feature`。

关系库是报告内部的候选集合，不是全部已成立事实。具体适用范围由草图引用与候选前提确定。特征不再内嵌同一套关系正文。

## 7. 候选与引用

### 7.1 Candidate

| 字段 | 类型 | 必填 | 含义 |
| --- | --- | --- | --- |
| `id` | string | 是 | 候选 ID |
| `mechanism` | string | 是 | 形成方式或关系机制 |
| `reasoning` | string | 是 | 为什么值得尝试，以及当前局限；保持简短具体 |
| `requires` | Requirement[] | 否 | 采用本候选时必须满足的候选选择前提 |

不要求概率、置信分数、排名、唯一结论或完整渲染计划。`reasoning` 不应重复整段 `mechanism`，也不应填充与当前图像无关的通用知识。

### 7.2 草图引用

- FeatureChoice：`{"feature_id": "F1", "candidate_ids": ["F1-A", "F1-B"]}`。
- RelationChoice：`{"relation_id": "R2", "candidate_ids": ["R2-A"]}`。

两种引用的 `candidate_ids` 必须非空、无重复，并属于被引用条目。它表示保留的备选范围，不表示所有候选同时采用，也不表示已选定或验证。

如果后续确实希望叠加两个机制，应明确形成一个组合候选，而不是把备选列表悄悄解释成同时执行。

### 7.3 选择前提

Requirement：`{"kind": "relation", "id": "R2", "candidate_ids": ["R2-B"]}`，其中 `kind` 仅允许 `feature` 或 `relation`。

- 一个 Requirement 内的候选是“至少满足其中一个”。
- 多个 Requirement 之间是“全部满足”。
- 前提只在当前候选被采用时触发，不要求整张草图立即选择它。
- 没有声明前提，不代表全部组合已经验证兼容。

例如，空间投影候选要求空间前后关系；而“前后关系如何影响暗部范围”仍需在关系库中描述。两者不互相替代。

不再另设自由文本 `constraints` 作为第二套选择规则。无法可靠结构化的未决条件放入 `reasoning` 或 `unresolved`，不冒充可执行约束。

## 9. 引用与组合校验

后端应执行以下检查，模型不必额外生成校验台账：

1. JSON 合法，顶层键与字段类型符合规范；未知字段拒绝，必填文本非空。
2. 报告内声明的 ID 唯一，包括实例组和候选；不同子 Agent 的 ID 可以重复，由后端隔离报告命名空间。
3. 元素、特征、关系和实例组引用存在且类型正确；实例组必须属于对应元素。不得使用自然语言代替引用 ID。
4. `candidate_ids` 非空且属于指定特征或关系；同一草图内不重复声明同一特征或关系引用。
5. 草图引用特征所关联的元素，应包含在草图 `element_ids` 中。引用关系中的元素、特征和关系端点，也应在该草图的相关引用范围内；检查时需要避免递归遍历重复对象。
6. 依赖关系存在源与目标，组织关系不携带因果方向。关系描述可以是待探索假设，校验不判定其真实性。
7. 草图保留的候选若声明 `requires`，其前提项必须在草图引用范围内，且前提候选与保留候选范围至少有交集。缺少前提时，修改范围或移除当前不适用候选。

第 7 项是直接前提检查，不等于已经求解全部组合的可满足性。后续真正选定候选组合时，需要按所选项再次检查所有生效前提；本次不要求建立通用约束求解器，也不展开候选组合。

关系端点表达对象间的影响，可能构成反馈；候选 `requires` 表达选择前提。两者不能混成一个图后统一判定“有环即错误”。

校验通过仅说明结构可解析、引用可定位、直接前提未明显缺失，不证明机制正确、兼容组合全部可行或视觉效果已被接受。

## 10. 输出控制与职责分工

| 责任方 | 负责 | 不应转嫁给它的工作 |
| --- | --- | --- |
| 子 Agent | 独立观察、分类、提出草图与局部候选、表达已识别的关系和前提 | 全局状态、跨报告对齐、唯一答案、运行台账 |
| 主 Agent | 比较探索结果、保留分歧、整理类别和候选、决定进一步验证 | 不应通过把旧报告作为标准答案来限制独立探索 |
| 后端 | 图像传递、运行控制、JSON/Schema 与引用校验、存储和追踪 | 不凭结构合法推断视觉正确 |
| 后续实现与验证阶段 | 尝试具体候选组合、编码、渲染和比较 | 不把分析草图当作已验证的实现 |

精简规则：先公共组成再实例差异；只新增有实质区别的草图或候选；不重复初稿、整体摘要和同义解释；不要求固定候选数量；不设置本次尚未讨论过的硬性字数或数组上限。
