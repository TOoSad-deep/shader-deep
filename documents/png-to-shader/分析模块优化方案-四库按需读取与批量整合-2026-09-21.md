# 分析模块优化方案：四库按需读取与批量整合

日期：2026-09-21  
状态：方案已按审查意见修订，当前工作区已实现并通过无网络测试、静态检查；真实模型服务对照尚未执行。  
范围：主 Agent 的材料发现、按需读取、上下文保留、批量整合与结束判断。

审查修订：补齐比较目标与辅助材料的区分、整批最终状态校验、补读累计预算准入，并据此调整实施顺序和验收场景。下文描述目标契约，当前实现入口见 `apps/shader_deep/src/shader_deep/analysis/EXPLORATION.md`。

## 1. 本次修正的核心方向

**四个库逻辑独立，通过 ID 建立引用。主 Agent 根据当前整合问题读取相关 JSON 内容；后端维护引用、版本和处理进度。**

统一维护业务状态，不等于统一加载全部正文。是否把四个库存进同一个文件，也不决定模型每轮应该看到多少内容。

本方案替换[统一库与增量交付方案](分析模块优化方案-统一库与增量交付-2026-09-21.md)中以下做法：

| 原做法 | 本次调整 |
| --- | --- |
| 材料放得下就全量注入，超预算才分包 | 默认只有轻量索引；正文由主 Agent 按库、按 ID 批量选择 |
| 后端预先生成所有材料包并依次交给模型 | 主 Agent 围绕具体比较问题选材，后端负责读取和预算检查 |
| 读取一个条目时递归展开关联正文 | 默认保留引用 ID，必要正文通过显式请求补充 |
| 材料包处理完作为主要推进依据 | 记录整合范围及决定，区分读取、比较、保留和暂缓 |

继续保留已经实现的独立探索、直接入库、来源追溯、批量事务、版本校验、局部修复、测量与真实终态。与旧方案冲突的选材和上下文规则，以本文为准。

## 2. 四库与文件的关系

业务结构保持不变：

```text
AnalysisLibrary
├── elements
├── sketch_library
├── feature_library
└── relation_library
```

- `elements`：统一视觉元素与实例组身份。
- `sketch_library`：组成方式，以及适用的特征、关系和候选引用。
- `feature_library`：外观特征及其形成机制候选。
- `relation_library`：可见组织或依赖关系及其形成机制候选。

候选仍属于对应特征或关系，不新增第五个候选库。库之间保持引用完整，但不因为存在引用就要求把相关正文一起放进上下文。

本版沿用一个版本快照保存完整四库，便于原子发布。后端解析 JSON 后按库和 ID 返回所需字段，不把整个快照文件交给模型。暂不增加物理文件拆分、数据库或通用文件系统工具。

原始子报告、历史版本、来源映射、提交回执和运行日志继续作为后端制品保存，不成为主 Agent 默认输入。

## 3. 职责与目标流程

| 责任方 | 负责的事情 |
| --- | --- |
| 探索子 Agent | 按统一初稿独立探索，一次提交本次三库；不读兄弟报告或已有机制 |
| 主 Agent | 根据索引选择比较范围，按需读取正文，判断重复与差异，批量提交决定 |
| 后端 | JSON 选取、身份与引用维护、实际呈现记录、事务校验、进度和最终导出 |

```text
独立探索结果入库
        ↓
主 Agent 获得原图、统一元素和轻量索引
        ↓
确定当前问题，例如“比较圆片外轮廓的几个特征”
        ↓
按库、按 ID 批量读取
        ↓
比较正文；确有需要时补读关联条目或测量
        ↓
批量提交合并、引用调整、新增或保留决定
        ├─ 参数或业务错误 → 保留当前材料和草稿，局部修复
        ├─ 需要语义判断的引用冲突 → 补读明确相关的条目
        └─ 成功 → 保存决定，释放本组正文，选择下一组
        ↓
主 Agent 声明没有剩余必要整合，后端检查并导出四库
```

“一组”指一次具体整合问题涉及的条目集合，不是一个库，也不是为了塞满请求预算划分的一段文件内容。跨库比较是允许的，但必须有当前任务需要。

## 4. 默认上下文：先提供索引

主 Agent 进入整合阶段时默认获得：

```text
用户要求 + 完整原图
统一元素与实例组
四库概览及轻量索引
初稿问题、失败任务、明确覆盖缺口
当前整合范围与简短进度
```

初稿或元素信息在一轮请求里只出现一份。默认不注入所有草图组成、候选机制、理由、测量正文或历史提交。

索引直接取自库中已有字段，不调用另一个模型生成摘要。索引用于发现对象，不作为修改判断的完整证据。

| 索引内容 | 示例 |
| --- | --- |
| 库类型、条目 ID 与名称 | `feature_library / F12 / 圆片外轮廓` |
| 所属元素或关系端点 | `element_ids: [E2]` 或参与端点 |
| 候选数量、引用数量 | `candidate_count: 3` |
| 当前处理状态 | 待处理、正在比较、已保留、已修改、暂缓 |

候选的完整 `mechanism`、`reasoning` 和依赖正文不进入默认索引。需要发现某个拥有者下的候选时，可以请求该拥有者的候选索引或正文。

索引较大时支持按库、元素、端点和状态过滤、分页。返回明确的剩余范围，不因当前页未展示就从任务范围中删除条目。后端分组仅表示适合共同查看，不表示已经判断语义相同。

## 5. 按需读取接口

建议提供两个读取入口。名称和最终 Schema 在实施时固定，以下示例不是现有工具承诺。

### 5.1 查询索引：`list_library`

支持选择库、元素范围、处理状态与分页位置，返回索引和继续查询的位置。候选较多时也可以限定拥有者。

索引中的已处理状态由后端根据接受的决定维护，不要求模型填写或重复复述整个台账。

### 5.2 批量正文：`read_library`

一次请求可以选取一个或多个库中的多个条目：

```json
{
  "comparison": {
    "question": "比较 F1 与 F2 是否描述同一外观特征，S2 仅用于理解引用场景",
    "target_ids": ["F1", "F2"]
  },
  "requests": [
    {
      "library": "feature_library",
      "ids": ["F1", "F2"],
      "include_candidates": false
    },
    {
      "library": "sketch_library",
      "ids": ["S2"]
    }
  ]
}
```

读取规则：

| 读取对象 | 默认返回 | 不自动返回 |
| --- | --- | --- |
| 元素 | 该元素的完整业务字段 | 所有指向它的特征、关系与草图 |
| 草图 | 组成、范围、引用及草图自身的未解问题 | 被引用特征、关系和候选的正文 |
| 特征 | 名称、外观、元素范围、候选 ID | 候选机制正文及引用者正文 |
| 关系 | 描述、类型、参与端点、候选 ID | 端点指向的业务正文及候选机制 |
| 显式选择的候选 | 机制、理由、`requires` 等完整候选字段 | `requires` 指向对象的正文 |

`include_candidates` 默认关闭；打开后读取选中拥有者下的候选。可增加 `candidate_ids` 进一步限定候选，只有在 `include_candidates=true` 时使用，并校验它们属于选中的拥有者。候选仍按原始身份引用，不变成独立业务库。

同一次请求中重复选择的正文只提供一份。连续补读会合并到当前组选材集合，不能用一个单值选择槽覆盖先前读取的条目。

### 5.3 比较目标与辅助材料

首次读取使用 `comparison.question` 和 `comparison.target_ids` 声明一个具体比较问题及目标，同时建立当前组，不增加单独的建组调用。目标可以是元素、拥有者、草图或明确的候选 ID；候选仍须通过所属库和拥有者读取，不因此新增候选库。接续已有必要工作时使用第 8.1 节的 `work_id` 代替新建 `comparison`，两者不同时填写。

后端分别保存三个集合：比较目标、已选取材料、实际呈现的字段与版本。读取目标之外的条目默认只增加辅助材料，不扩大比较完成范围或语义修改权限。例如上例中的 `S2` 不能因 `F1/F2` 的决定被接受而自动标为已比较。

同组后续读取省略 `comparison`，沿用原问题；需要处理新发现的引用冲突时，可用 `extend_target_ids` 显式扩大目标，再补读相关正文。不能在已有组中用新的 `comparison` 静默替换旧问题，也不能通过重复读取把辅助材料自动提升为比较目标。补读目标正文尚未呈现时，不得接受依赖它的决定。

比较拥有者身份与比较其候选是不同范围：目标为 `F1/F2` 时，只处置本次拥有者比较；目标为 `C1/C2` 时，只处置这两个候选的比较。不会把其他候选或与第三个条目的比较一并标记完成。现有条目的语义修改必须落在显式目标内；机械引用维护按第 6 节处理。新增条目由本批决定登记，不要求事先存在目标 ID，但其已有引用仍须满足材料前置条件。

### 5.4 补读的累计预算准入

每次读取先估算追加后的完整请求，再改变当前组选材。预算同时约束单次返回和当前组去重后的累计正文，并扣除固定上下文、已有历史、测量文本与图像、工具 Schema、输出及后续修复预留；不能把每次读取都当作拥有完整窗口额度的新请求。

后端只追加预算内的完整条目，不截断正文。回执分别列出已选取、重复选取和因预算未提供的 ID 及原因；候选未提供时列候选 ID，不能仅以拥有者 ID 掩盖部分缺失。已选取也不等于已呈现，仍须等待 Context Builder 将正文放入实际准备发送的请求。

连续或同轮多个读取调用串行更新同一累计预算。同版本重复读取不重复占用正文预算，也不计为新进展。预算拒绝不清空原组选材、不留下半个条目，且应保留足够空间发送简短反馈，使主 Agent 可以提交已有范围的合法决定、调整后续选材或明确暂缓；不能因为一次过量补读就直接让下一轮请求超限退出。

测量与裁剪选入当前组也共享该预算；无法选入的结果保留在后端制品中，不登记为已呈现。发送前的完整请求检查仍是最后防线。单个必要的最小判断集合确实无法容纳，或历史与修复已耗尽预留时，保存草稿及具体未完成比较范围，保留原库并交付真实的部分状态。

## 6. 引用展开与修改前置条件

**结构引用完整性由后端校验；只有需要模型作语义判断的内容，才要求进入模型请求。**

不能继续把整个递归依赖闭包作为每次修改的统一读取门槛。不同操作需要不同材料：

| 操作 | 主 Agent 必须获得的判断材料 | 后端处理 |
| --- | --- | --- |
| 合并特征或关系拥有者 | 成员自身的外观、范围、类型或端点等业务字段 | 保留所有候选，统一引用和别名；不顺便合并候选 |
| 合并机制候选 | 所选候选完整正文，以及影响等价判断的拥有者、适用范围和前提 | 检查归属、范围与前提兼容，拒绝不安全归并 |
| 调整草图中的候选选择 | 该草图、相关引用范围、被调整候选及必要前提 | 校验引用存在、候选归属、范围和直接前提 |
| 新增组成 | 新组成使用的已有条目中，形成当前判断所需的正文 | 分配新增 ID、校验组合引用和前提 |
| 机械重写已有引用 | 不要求重新阅读所有引用者正文 | 后端完整检查受影响对象；语义冲突另行反馈 |

例如，合并 `F1/F2` 的拥有者时，可以保留二者候选的完整并集；不要求先判断每两个机制候选是否相同。进一步合并其中的候选，才需要读取候选正文。

修改依据不足时，后端返回缺少的具体 ID、所需字段类别及原因，而不是要求重读整个库。不得为了绕过材料检查而把任意引用都认定为“纯机械变化”。

机械引用重写若产生重叠范围等冲突，整批不发布。返回有效的提交参数路径，并列明受影响的草图或条目 ID。主 Agent 可补读这些条目、扩展当前整合范围后一起修复，也可以撤销引发冲突的合并。

### 6.1 批量事务的校验时机

“一起修复”要求整批最终状态可被校验，不能只是多次已有单项操作的循环。当前实现的 `_stage_integration` 先逐项调用 `merge`，每次经 `_commit` 校验完整库，之后才执行 `reference_updates`；合并产生临时引用冲突时，会在同批修复执行前失败。本次实施必须改造这一暂存路径，不能只放宽读取前置条件。

目标执行顺序：

1. 在修改前校验参数、目标范围、已呈现字段及版本，并固定本批身份和判断依据。
2. 在私有副本中解析合并映射，应用合并、引用修复和新增；保留操作自身的归属、范围、前提兼容等检查。
3. 对全部操作形成的最终副本统一校验四库结构、候选归属、引用存在、范围重叠和直接前提等跨对象约束。
4. 全部通过后一次发布库、来源、别名、回执及工作进度；任一步失败都不发布。

暂存副本中由本批后续操作修复的跨对象临时不一致，不应在单次合并后提前触发整库失败；不能借此取消最终校验或放宽合并本身的适用条件。错误仍映射到本次提交参数路径，并给出受影响对象 ID。原有独立单项写入入口若保留，仍须在返回成功前校验其完整结果，不能全局关闭 `_commit` 的校验。

## 7. 当前组的上下文与版本

### 7.1 正文只在当前组驻留

首次批量读取按第 5.3 节建立比较组及后端工作身份，后续补读默认追加到这一组。有效决定覆盖当前比较目标并被接受，或明确暂缓后，才关闭当前组；下一次读取建立新组。不为开始一组比较增加额外的模型调用。

读取工具可以返回简短回执，实际 JSON 正文由 Context Builder 放入下一次请求。这样不会把大段正文既保存在工具历史、又重复注入业务上下文。

同一组内保留：

- 当前选择的完整正文与必要的关联材料。
- 本组使用的测量正文与实际裁剪图。
- 当前批量决定、工具反馈和局部修复历史。

正文按 ID 和版本去重。追加读取后，已有相关正文继续保留；提交被拒绝时不清空本组，不让模型重新列目录、重取材料和重做整组规划。

只有实际进入准备发送的请求，才登记相应字段和版本已呈现。后端生成了读取回执或缓存了文件，都不能代替这个条件；新读材料尚未呈现时，不能接受依赖它的修改。

### 7.2 组间保留状态，释放大正文

本组成功提交，或者明确暂缓后，后端保存决定和进度。下一组保留轻量索引、必要的既有决定、未完成范围及下一步信息，不继续携带上一组全部正文和修复对话。

不能在同一个模型历史中无上限累积所有已经读过的条目。需要回访旧条目时，按当前版本重新提供；不需要回访的内容仍完整留在库里。

### 7.3 材料变化只刷新受影响部分

当前读取集合绑定条目及所需字段的版本。其他条目变化不要求整库重读。

当前判断依据已变化时，拒绝旧决定，刷新受影响材料并保留旧草稿供参考。已处理范围的实质前提变化时登记复核任务；纯别名和机械引用重写不触发整组重新分析。

## 8. 批量决定与进度

继续使用 `submit_integration` 表达一组决定，复用现有业务字段；其处理范围绑定第 5.3 节的比较目标，不沿用旧材料包中“全部可写条目均已处理”的含义：

- `merges`：明确重复的成员。
- `reference_updates`：草图引用范围与局部优先级调整。
- `additions`：必要的新候选或组成。
- `unresolved`：按元素记录仍待验证的现象或机制问题。
- `outline_issue_decisions`：冻结初稿下的问题处置。
- `review_ids`：登记明确需要后续比较的条目范围；候选 ID 保持候选粒度，不自动提升为整个拥有者及所有候选。
- `deferred_work`：绑定当前组，记录本轮未完成的必要工作及原因，不能同时把该组声明为全部完成。
- `preserve`：明确保留当前组中未被修改的比较目标；无修改时表示保留整个比较范围，与修改一起提交时表示其余目标已比较并保留。不代表辅助材料或未展开内容也完成了比较。

提交身份、当前整合范围与版本由后端绑定。一次有效决定中的多个操作仍在副本上校验，全部通过后原子发布；失败不留下半成品，重复提交不重复执行。

### 8.1 工作记录与关闭规则

后端为每个比较问题保存稳定工作 ID、目标 ID、必要判断依据的字段与版本、决定、结果和复核来源。正文选取记录单独保存；辅助材料即使完整呈现，也不会因本组关闭而获得独立比较完成记录。无需模型重复提交这些后台字段。

一个组围绕一个问题提交整体结果。有效修改只记录实际修改范围，其余目标通过 `preserve=true` 批量声明已比较并保留；既未被修改、也未声明保留或暂缓的目标会使整批提交被拒绝，并返回具体 ID。该规则不要求逐项写无变化说明。`preserve` 仅在必要正文已呈现且没有未处置的冲突或修复时生效；不能用保留声明覆盖未呈现材料。

`deferred_work` 与 `preserve=true` 在本版中互斥：前者把本组整体工作结果记为暂缓，同时保留本批已原子发布的有效修改，不再猜测其余目标中哪些已比较。若要让不同问题分别获得独立结果，应建立不同组。这样可以继续复用布尔 `preserve` 和文本 `deferred_work`，而不引入无法由现有字段表达的任意混合处置。

`review_ids` 或实质前提变化产生的复核是独立的必要工作记录。首次读取可携带后端返回的 `work_id` 接续该范围，而非重复新建；已接受决定只能关闭其绑定的工作。其他组的 `preserve`、正文读取和条目别名变化不能消除这条待复核记录。所需判断依据变化时，按第 7.3 节刷新或重新登记复核。

仅依据索引而不展开的内容，在结束时登记为“未展开保留”，不通过 `preserve` 伪装成比较结果。索引中的状态是工作记录的摘要；同一条目既有已完成比较又有待复核范围时，必须显示待复核范围，不能用单个“已处理”状态隐藏剩余工作。

### 8.2 处理状态

处理进度应区分：

| 状态 | 含义 |
| --- | --- |
| 待处理 | 尚未决定如何处置的范围 |
| 正在比较 | 当前已选取并正在判断的范围 |
| 已比较并保留 | 已获得必要正文，判断应保留差异或无需修改 |
| 未展开保留 | 正文未经本轮比较，直接继承原内容，不宣称已经去重 |
| 已修改 | 批量决定已接受并发布 |
| 暂缓 | 必要工作未完成，保留具体原因 |

读取记录和整合状态分别维护。读过一个条目，不自动标记比较完成；索引中可以排除的无关范围，也不要求逐条读取正文。允许批量保留，不能要求模型逐项写无变化说明。

等待渲染才能区分的机制争议属于有效分析结果。因范围或前提不同而保留候选，也不自动构成未完成工作。`deferred_work` 只记录本轮确实尚未完成的必要比较，不能把所有不确定性都写成流程失败。

## 9. 完成条件与预算

按需选材后，需要主 Agent 明确表达本轮不再有必要的整合工作。恢复一个轻量结束请求，例如 `finish_analysis()`；它只请求后端检查和导出，不要求模型重写四库或再写总结。

后端检查：

1. 独立任务均已进入终态，并满足现有最小有效探索条件。
2. 当前组没有未提交的必要修改或悬而未决的修复。
3. 按后端工作 ID 检查已确定的必要整合、冲突处置和复核结果；读取、其他组的 `preserve` 及未展开继承不能关闭这些工作。
4. 四库结构和引用合法，未覆盖元素有具体缺口记录。
5. 失败子任务、初稿问题、预算退出和暂缓范围按实际情况影响交付状态。

完成不要求全部正文都被读取，也不宣称全库所有语义重复已经消除。未展开内容完整继承，并保留其未比较状态。存在未完成的必要工作时交付 `partial`，没有合法可用结果时保持失败或停止状态。

主动结束时若当前组仍有未提交决定或修复，返回具体工作 ID 和缺口，让主 Agent 提交、撤销无效草稿并明确处置原问题，或暂缓；不静默丢弃该组。预算耗尽、中断等无法继续交互的出口则由后端保存当前组和待复核记录，按实际缺口导出 `partial`。不存在必要工作记录的未展开内容不自动阻止完成。

预算约束当前组选材、测量、修复历史、工具 Schema、图像及输出预留。**可用上下文容量是上限，不是每轮需要填满的目标。** 不通过增加上下文窗口或删除候选来代替按需选材。

当前组调用次数、重复无进展、总调用与复核次数保持显式边界。单组预算耗尽时保存草稿和范围；不会因为其他组已完成就伪装整次成功，也不为了重试重新调用全部探索子任务。

## 10. 实施范围与顺序

| 阶段 | 主要改动 | 可验证结果 |
| --- | --- | --- |
| 1. 比较范围与状态 | 先调整 `materials.py` 的职责和会话状态，固定比较目标、辅助材料、工作身份与关闭规则 | 不再从已读集合或旧包全部可写范围推断比较完成；复核有明确归属 |
| 2. 读取与预算准入 | 修改 `library.py` 的索引和批量 JSON 选择，复用 `request_budget.py` 估算累计请求 | 没有隐式递归扩库；补读先检查总预算再追加；拒绝过量读取后仍能继续当前组 |
| 3. 按需上下文 | 修改 `exploration_session.py`、`context/exploration.py` 和整合提示词 | 初始请求只带索引；同组补读不覆盖；实际呈现与选取分开；组间释放正文 |
| 4. 事务与修改前置条件 | 改造 `library.py` 的暂存及最终校验路径，调整字段与版本检查 | 合并和引用修复能同批成功；最终不合法则全部回滚；机械维护不要求全库呈现 |
| 5. 结束与验证 | 接入 `finish_analysis` 的工作记录检查，更新回归测试，再做有界真实对照 | 必要复核未完成不返回完整交付；同时证明引用正确、来源可追溯与上下文受控 |

优先改造现有模块，不新增 Agent、数据库或通用调度框架。子任务输入输出、直接入库和最终四库 Schema 保持本版边界；物理文件拆分不列入本次必需改动。

## 11. 验收标准

| 场景 | 必须证明的行为 |
| --- | --- |
| 初始整合请求 | 含可用索引，不包含全部机制候选正文、原始报告副本或历史快照 |
| 批量读取 | 一次可选多个 ID；只返回选中的库条目与明确请求的候选 |
| 比较目标与辅助材料 | 比较 `F1/F2` 时补读 `S2`，提交保留后只关闭本次比较，不把 `S2` 标为已比较 |
| 候选局部比较 | 只比较 `C1/C2` 不关闭同一拥有者下其他候选的比较或既有复核；索引保留剩余范围 |
| 修改与保留混合提交 | 修改部分目标并用 `preserve=true` 保留其余目标时，只登记本组实际范围；遗漏处置、未呈现却保留、保留与暂缓冲突均返回明确错误 |
| 草图引用 | 读草图不会自动展开所有关联特征、关系、候选和前提 |
| 连续或同轮补读 | 预算内多份选材共同保留、去重且实际呈现，不发生最后一次覆盖前面内容 |
| 累计读取超预算 | 两次读取各自不过限但合计超限时，第二次仅追加能容纳的完整条目，明确列出未提供 ID；下一轮仍能收到反馈并提交或暂缓 |
| 拥有者合并 | 不读所有候选机制也能安全保留候选并集；不隐式合并候选 |
| 候选合并 | 未获得必要候选正文或适用条件时拒绝；不要求加载无关业务对象 |
| 引用冲突 | 后端自动改写引用；语义冲突返回精确影响范围，允许补读后局部修复 |
| 同批消除合并冲突 | 保留原合并成员，同时提交修复引用，最终状态合法则一次发布；不能只用撤销或更换合并成员证明修复有效 |
| 最终校验与回滚 | 同批后续修复仍不合法时，库、来源、别名、回执及工作完成状态均不发布；单项写入不绕过最终校验 |
| 同组修复 | 保留本组材料与决定，补丁指针指向真实提交参数 |
| 切换整合组 | 实际请求不继续携带已结束组的全部正文和修复历史；进度仍保留 |
| 材料过期 | 只刷新受影响的判断依据；旧决定不能靠替换 ID 自动被接受 |
| 未展开保留 | 内容不丢失，也不被标记为已完成语义比较 |
| 正常结束 | 不再检查全库逐项已读；检查必要任务、引用、覆盖与真实缺口 |
| 必要复核与提前结束 | 存在待复核工作时，读取材料或另一组提交 `preserve` 不能清除它；当前组未关闭时主动结束返回具体缺口，强制退出保存部分结果 |
| 超预算与中断 | 结果和草稿可追溯，终态准确；不删除候选或无限重复读取 |

先用网络免费的模拟模型请求验证实际进入上下文的内容，再使用固定的同一组探索报告比较整合行为，减少子任务随机性和重复成本。真实模型调用仍需独立记录失败、截断和中断。

对照指标至少包含：完整/部分交付状态、主模型轮次、批量读取次数、实际提供的正文量、重复读取量、修复次数、上下文峰值、提供方返回用量、必要任务完成情况和来源追溯。不能只用“调用变少”证明优化成功，也不把单元测试通过等同于真实流程验收。

审查阶段通过无网络最小复现确认了原事务对“同批合并与引用修复”的提前校验问题，随后进入实现。当前工作区已接入按需读取、比较工作记录、累计预算准入与整批最终校验。无网络请求回归与完整检查的结果单独记录；未进行真实模型服务对照，本节指标不等于真实流程质量验收。
