## 2. 第一步：明确引用类型，改善错误反馈

### 2.1 问题与最小改法

原 `SourceRef` 只有 `result_id` 和可选 `item_id`。同一个结构用于不同位置，但合法来源不同：关键观察与视觉事实只接受观察，其他综合条目还可以引用解释或报告新增视觉对象。本轮两图中，模型仍把视觉对象或解释用于只接受观察的位置；增加类型目录并不能代替位置校验。

首版沿用 `SourceRef`，只增加可选 `kind`，缺省为 `None`。类型覆盖当前已经允许的来源：`report`、`observation`、`interpretation`、`visual_element`、`visual_feature`、`visual_relation`。类型存在不代表所有目标字段都接受它。

程序从当前运行的真实记录生成引用目录，最小包含：

| 字段 | 用途 |
| --- | --- |
| `result_id`、`item_id` | 沿用现有来源身份；整报告引用的 `item_id` 为空 |
| `kind` | 真实条目类型，由程序提供 |
| `description` | 从已有名称或正文截取的短说明，不额外调用模型生成摘要 |

第四步按需读取报告时，再向同一目录补充 `file_path` 和 `pointer`；第一步不提前实现文件检索。

校验采用一张小的“引用位置 → 允许来源类型”表，避免提示词和多个校验函数各自维护不同规则：

| 引用位置 | 首版允许的来源 |
| --- | --- |
| `key_observations.source_refs` | 具体 `observation` |
| 视觉元素、特征、关系的 `source_refs` | 具体 `observation` |
| 综合假设、分歧、关系、未知项的 `source_refs` | 沿用当前允许的观察、解释、报告新增视觉对象或整报告 |
| `implementation_hints.source_refs` | 沿用上一行范围；实现草图通过关联的解释或整报告追溯，首版不扩展新的可引用类型 |
| 第三步的 `derived_from` | 具体 `interpretation` |
| 测量引用 | 继续使用 `evidence_ids`，不放入 `SourceRef` |

`VisualMapping` 已有 `kind`，继续专门表达视觉对象对齐；不要将其与观察来源混成一种映射。报告输入初稿中的对象也不能自动算作该报告新增产出。

### 2.2 兼容与错误反馈

- 旧记录缺少 `kind` 时，从实际目录解析，仍执行原来相应位置的校验；不批量重写历史报告。
- 新记录显式提供 `kind` 时，必须与真实条目一致。程序不能因为写了 `observation` 就把解释当作观察。
- 保留现有报告内唯一性规则。当前已经禁止观察与解释同 ID，也禁止新增视觉对象与这两类条目撞 ID。草图的 ID 目前只要求在草图内唯一，因此首版不把它加入通用来源目录，避免为旧数据增加歧义处理。无需新建全局实体数据库或另一套编号系统。
- 一次收集本次提交可独立检查的错误；某部分结构尚无效时，不继续臆测它的跨引用错误。反馈区分“已检查”和“仍待前置结构修正”，不承诺一次一定查出所有问题。

此前误实施后的彩色元件子报告在修正额外字段后，支持／反对引用冲突逐条暴露，耗尽了 3 次子调用；另有业务错误退化成空路径或整个 `/report`，不利于局部修复。最小修复是沿用现有校验入口和错误结构，聚合同一校验阶段内可独立检查的问题，并保留具体字段位置，不增加校验服务或另一个修复 Agent。

复用 Pydantic 的 `loc` 转换 JSON Pointer，业务校验直接提供相同的 `path`、`code`、`message`。嵌套业务错误被 Pydantic 包装时，保留其内部路径并只补一次外层 `/report` 或 `/summary`，不能将整组错误压成一条 `value_error`。例如两条解释各有支持／反对冲突，应一次收集各自的 `/report/interpretations/<index>/supporting_observation_ids`、`opposing_observation_ids` 字段错误；列表本身可整体替换，无须强行猜测应删除哪一个语义立场。视觉对象的本地引用错误也应指向其实际 `element_ids`／`feature_ids` 字段，不能只返回空路径。

引用错误附相关报告内少量候选及其类型，不自动选择替代项。错误多时本地保存完整已检出列表，工具返回前几项和 `remaining_errors`；该数只表示已检出但未展示的条数，`0` 不表示后续业务校验已完成。结构尚未通过时，在现有反馈文字中说明后续校验尚未执行，不臆测跨引用问题，也不新增校验状态机。模型修正当前问题后重新校验，再返回尚存错误；完整错误文件供人工诊断，不另加错误查询工具。

例如反馈应能说明：`/summary/key_observations/2/source_refs/0` 需要观察，但 `R2/H6` 实际是解释，并给出该报告的可用观察。程序不自动猜测替换成哪个观察。

### 2.3 派发参数顺手收紧

保留 `run_analysis_batch` 和当前静态请求结构。上下文由会话明确提供首批前/首批后的阶段、当前合法 `purpose` 和必需字段；已有首批任务后，应使用 `supplement` 或 `verify`，并填写 `gap`、`expected_evidence`。业务拒绝也返回这组具体要求。

首版不动态替换工具 schema。当前工具与执行白名单在循环初始化时绑定，仅为这一条错误引入动态工具构造并不划算。若阶段说明和结构化反馈仍明显不足，再单独评估按阶段提供不同 schema。

只针对两图中反复出现的误用，在已有提示词补充以下短说明，字段以实际 schema 为准，不维护另一份完整 schema：

| 高频误用 | 必要的结构说明 |
| --- | --- |
| 把 `features`、`relations` 放在子报告顶层，或添加 `features_note` | 新增视觉对象位于 `report.visual_additions.elements/features/relations`；额外说明使用既有文字字段，不创造字段 |
| 给 `VisualRelation` 添加 `region`／`region_box` | 关系用 `id`、`element_ids`、`description` 及继承的证据字段表达；该类型没有区域字段 |
| 给观察或 `visual_additions` 添加 `uncertainties`，或把 `source_refs` 放在报告顶层 | 不确定性放入报告或解释已有的 `uncertainties`；来源引用放入实际支持该字段的具体条目 |
| 追加任务漏写视角 | `preset_id` 与 `lens` 恰好提供一个；追加任务同时保留已有 `purpose/gap/expected_evidence` 要求 |

例如视觉事实的来源可写成 `{"result_id":"R2","item_id":"O3","kind":"observation"}`；这些 ID 必须由目录取用。把真实类型为 `visual_element` 的条目改标成 `observation` 仍然非法，已经读过该条目也不能改变这一点。

### 2.4 第一步验收标准

同一报告的多个独立引用冲突能被一次收集；嵌套错误与视觉本地引用错误能定位到可修复字段；反馈截取不丢失完整本地列表，也不把未执行的校验称为通过。旧数据省略 `kind` 仍按真实类型解析，显式错误类型不能靠改标签或读取材料绕过校验。复用现有引用用例即可，不为每个误用字段增加测试。

## 3. 第二步：完整 JSON 提交失败后，允许局部修复

### 3.1 正常路径保持简单

正常情况下仍调用 `finish_analysis(summary, text)` 或 `submit_analysis_report(report, summary)` 一次提交完整内容。不强制所有报告先按章节分多轮写入。

只有语法合法、但结构或业务校验未通过的提交，需要转成可修复草稿：

```text
完整且合法的 JSON 参数
  → 保留本任务待校验提交
  → 原 schema 与业务校验
      → 通过：沿原工具逻辑提交正式结果
      → 未通过：返回草稿版本、错误路径和原因
          → 模型只提交局部修改
          → 应用到草稿副本，再走相同校验与提交逻辑
```

草稿是程序保存的待校验数据，不是 `ResultRecord`，不进入有效报告列表。一个任务只保留一份当前待校验提交，不建草稿数据库、多分支版本库或分章节事务系统。

### 3.2 必须接在正确位置

误实施前的 `AnalysisLoop.wrap_tool_call` 会先执行 `TypeAdapter(...).validate_python(...)`。很多错误在这里就被拒绝，尚未进入提交工具函数。因此只在 `finish_analysis` 内保存失败报告是不够的。

为上述两个提交工具增加一个窄的提交尝试 helper：在原始参数严格 JSON 解析通过后，由 `wrap_tool_call` 的提交分支把参数交给它，在 schema 校验之前保存参数对象。完整提交与局部修复共用这个 helper，完成“保存参数 → schema 校验 → 原业务提交 → 登记错误或结果”。其他工具继续走现有 handler。

这里不能只靠 loop 捕获异常或检查 `ToolMessage.status`：旧主提交工具会把异常包装为 `status="invalid_summary"` 的普通 JSON 回执，外层消息不一定是错误状态。重接时应让 helper 直接调用 `_finish` 或拆出的子报告提交函数，统一接住 schema 与业务拒绝，避免两条路径重复保存或漏记错误。

草稿中保存的是工具的完整参数，包括外层的 `text` 或 `summary`，避免修复正文时丢失外层参数。原工具名称、参数形状和成功回执保留；只是把内部提交尝试集中到同一小段逻辑。

草稿最小保存任务 ID、原提交工具名、递增版本、参数对象和最近校验错误。它属于分析会话/子任务执行状态，不扩展通用黑板。随现有运行制品保存，子任务按自己的任务 ID 使用独立位置；这也不等于已经支持从中断处恢复模型会话。

### 3.3 一个局部修复入口即可

增加共用的 `repair_analysis_submission` 工具，参数为草稿标识、期望版本和修改列表。首版只提供两个操作：

| 操作 | 语义 |
| --- | --- |
| `set` | 添加或替换对象字段，或替换已有数组位置的值 |
| `remove` | 删除已有字段或数组位置 |

路径使用简单 JSON Pointer，支持字段名、数组位置和必要的 `~0`、`~1` 转义。数组需要复杂重排时替换对应数组即可；不实现完整 JSON Patch 的 `move`、`copy` 等操作，不引入表达式或代码执行。

示意参数：

```json
{
  "draft_id": "A1-submission",
  "expected_revision": 2,
  "changes": [
    {
      "op": "remove",
      "path": "/summary/key_observations/2/uncertainties"
    },
    {
      "op": "set",
      "path": "/summary/key_observations/2/source_refs/0",
      "value": {
        "result_id": "R2",
        "item_id": "O3",
        "kind": "observation"
      }
    }
  ]
}
```

上述 ID 仅为示意，实际值必须来自运行目录；示例中的额外 `uncertainties` 字段也必须确实存在于待修复草稿，才可删除。历史两图中曾出现删除不存在的 `element_ids_extra` 路径，整组修改因此未应用。模型应围绕返回的真实错误路径修改，不顺手清理臆测字段；`remove` 不存在的路径继续视为错误，不静默忽略。

修改按列表顺序应用到副本；任一操作路径错误或版本过期时，整组修改不改变当前草稿。补丁参数错误定位到 `/changes/<index>/path` 等实际参数，并在消息中说明失败的目标 Pointer；报告校验错误则继续使用完整提交对象下的 `/report/...` 或 `/summary/...`，不要混淆这两种路径。修改操作成功后保存新版本，即使仍有校验错误也保留此次有效编辑，供下一轮继续修复。

修复后自动调用原提交逻辑：主任务仍经 `_finish`，子任务仍经原报告登记逻辑。只有原 schema、引用、回读和业务规则全部通过，才创建正式结果；不另加一次“提交草稿”的模型调用。

各任务维护自己的草稿；捕获参数、校验和业务提交共用该任务的串行边界，而不是在锁外保存草稿再调用带锁工具。复用主会话锁，子任务的两类提交入口共用一个局部锁即可。helper 已持锁时直接调用不重复加锁的业务函数，避免嵌套获取现有非重入 `Lock`。

共用 helper 在取得任务锁后，首先检查是否已经提交成功；这个检查必须早于保存完整参数、推进草稿版本或应用补丁。主任务已经有 `summary_result`、或子任务已经有有效提交时，返回已有结果的 `already_finished` / `already_submitted` 回执，不再修改草稿或登记结果。原检查位于工具包装层，改成直接调用底层业务函数时要一并迁入共用入口，不能仅依靠下一轮模型调用的 `done()`。这样同一模型响应中的“完整提交＋修复”或两个完整提交也只会产生一个结果。

新的一次完整提交替换当前待校验内容并推进版本，旧版本不能再覆盖它。模型调用与网络重试继续按原规则计数，修复不重新派发子任务或重放测量，也不重置子调用额度。局部修改减少重传内容，不保证减少模型轮次；历史子任务曾在 3 次逻辑调用后留下未通过草稿；本次主、子默认均不限调用，显式有限模式仍按所设额度计数。

必须区分“补丁已应用并保存草稿”和“修复后正式提交成功”。后者才表示原 schema、来源合法性、实际回读和业务规则全部通过。成功事件复用第六步的 `submission_saved`，补记实际调用工具 `invoked_tool` 与原完整提交工具 `submission_tool`；只有 `invoked_tool="repair_analysis_submission"` 且 `accepted=true` 才计为一次成功局部修复。草稿版本增加、补丁合法或完整重交成功均不能代替这一证据。保存归属由共用入口在原任务锁内随回执返回，事件不能靠锁外前后快照差分推断，避免并行终态重复调用冒领其他提交的成功。

### 3.4 非法 JSON 单独处理

“协议要求 JSON”不代表每次返回的参数字符串都是合法 JSON。缺逗号、字符串未闭合等错误尚不能可靠定位为对象路径。

首版保持现有严格解析与有限尾部恢复：无法解析时给出语法位置和短片段，请模型重新提交合法对象；不把底层部分解析结果当作完整报告。已有可解析草稿也不被这次非法文本覆盖。不增加通用 JSON 猜补器或另一个修复模型。

`run_analysis_batch` 和 `measure_reference` 不接入自动重放式修复。它们有任务和测量副作用，第一步的参数提示、诊断已可改善常见错误；本步先集中解决两类大报告的重交成本。

### 3.5 第二步验收标准

合法 JSON 的 schema／业务错误能保存完整参数并只修指定字段；未改字段保留。非法 JSON 不覆盖已有草稿；无效路径、过期版本及跨任务草稿不产生部分修改或正式结果。修复后仍不合法的草稿可继续修，首次成功后的同批重复完整提交或补丁只返回原结果，不再修改草稿或计成功事件。完整提交与局部修复共用原校验，不绕过来源合法性和第四步的实际可见性。以已有提交用例检查这些行为，不增加分章节写入流程或补丁操作大全。

## 4. 第三步：建立最小假设继承关系

### 4.1 只记录有用的关系

`source_refs` 继续表示陈述的依据。另在 `AnalysisSummary` 增加默认空的 `hypothesis_links`，每项包含：

- `hypothesis_id`：当前综合假设的 ID。
- `derived_from`：来自哪些子报告解释，引用类型仅允许 `interpretation`。

采用独立的关系列表，是为了不更换当前 `hypotheses` 中的 `SourcedStatement` 类型；已有 JSON 和 Python 对象仍按原方式使用。一个综合假设可关联多条原始解释，一条原始解释也可关联多个综合假设。

例如 `H-A ← R1/I1、R2/I3` 已经能表达合并，不必再写一遍 `status="merged"`。程序根据关系反向计算“哪些解释已关联、哪些尚未关联”，不要求模型抄写全部原始条目。

### 4.2 不强制增加一套处置台账

首版不要求每条解释必须填写“保留、合并、暂存、舍弃”及长理由。否则会把本次优化变成新的形式填报和纠错负担。

- 未关联只表示“未建立到当前综合假设的继承关系”，不推断它被否定或有意舍弃。
- 确需说明某个替代方向的局限、分歧或后续验证，复用 `disagreements`、`open_questions`。
- 原始报告始终保留；完成反馈显示未关联条目数量和可查看位置，不自动将它们删除。
- 新字段为空的旧报告表示未提供继承信息，不补造历史映射。
- 本步新增校验只拒绝来源类型、目标假设 ID 和归属等关系错误，同时沿用原业务校验及第四步的实际可见性要求；不因尚有未关联解释就机械地拒绝报告或改成 `partial`。

这一步解决合并关系可追溯，不宣称程序已经证明“所有重要替代解释都被保留”。将来确实需要逐条处置时，再增加那部分契约。

### 4.3 本轮发现与第三步验收标准

此前误实施后的两图分别有 6／2 条子报告解释未建立继承关系，而综合假设均有对应的继承条目。不能据此认定全部替代解释已经保留或未关联解释已经被否定；本轮不增加逐条处置台账。

最小改法仍是同一份 `hypothesis_links` 加程序派生的未关联清单。继承来源先通过第一步的真实类型、身份和归属校验，再按第四步确认正文实际可见。有效子报告中的未关联解释应保留且可追溯；失败草稿不能进入有效解释清单。实现草图和渲染检查点继续关联具体综合假设，不接入生成调度。

验收应能区分跨报告同名解释，支持多来源合并，正确显示未关联项；非法或未读的继承来源不能提交。缺失子任务由执行状态确定并保留 `partial`，不因综合报告已提交而改称全部完成，也不因存在未关联项而额外判为 `partial`。
