## 2. 第四步：主 Agent 通过文件逐步读取报告

### 2.1 复用现有 SDK，应用层只补业务需要

当前 SDK 的 [`create_deep_agent`](../../libs/deepagents/deepagents/graph.py) 默认使用 `StateBackend`。它保存 Agent 状态中的文件，不会自动读取本地运行目录。[`FilesystemBackend`](../../libs/deepagents/deepagents/backends/filesystem.py) 可绑定本地目录，并以 `virtual_mode=True` 使用虚拟路径；它的 `download_files(paths)` 通过同一套路径解析加载原始字节，返回 [`FileDownloadResponse`](../../libs/deepagents/deepagents/backends/protocol.py) 的 `content/error`。该方法可以直接用于本地 JSON 文件读取，不需要新增 IO 框架。

首版采用以下组合：

1. 协调器将有效子报告写入本次 `run-*` 的 `reports/` 目录。
2. 主会话创建指向该目录的 `FilesystemBackend`，使用虚拟路径。
3. 在 `session.tools()` 加入 `read_analysis_file(file_path, pointer="")`，内部调用 Backend 加载字节，UTF-8 解码并 `json.loads`，只返回指定章节或条目，以及对应的来源标识和 `complete` 标记。空 pointer 表示整份文件。
4. 继续使用 `AnalysisLoop` 已有的模型可见工具列表和执行白名单。子 Agent 不获得该工具，也不共享主 Agent 的报告目录。

这一层只负责把文件读取与本模块的回读记录衔接。pointer 由索引提供，例如 `/analysis_detail/interpretations/2`；复用前一份方案局部修复所需的简单 JSON Pointer 解析函数，不实现新的搜索语言或 JSONPath 表达式。程序在本地解析完整文件，不等于把完整文件发给模型。首版由索引提供确定路径，不需要额外开放 `ls`、`glob`、`grep` 或 Shell。

没有直接使用内置 `read_file` 的原因是回读记录。当前 [`FilesystemMiddleware`](../../libs/deepagents/deepagents/middleware/filesystem.py) 会对正文格式化和截断；应用不能仅凭 `success` 就认定整个文件已呈现。薄工具复用 Backend 的存储与路径能力，以完整 JSON 条目作为呈现单位，避免维护行覆盖区间、修改 SDK 私有方法或解析展示字符串。确有纯文本阅读需要时，再开放原生按行工具。

`FilesystemBackend` 仍支持写操作，但模型只获得上述只读工具；写入报告由协调器负责。虚拟根仅指向报告材料目录，不包含 `.env`、整个仓库或其他运行。沿用 Backend 已有路径处理，不额外实现一套通用沙箱。

### 2.2 文件与索引保持简单

建议目录如下，文件名由程序生成：

```text
run-*/
  reference.png
  run.json
  reports/
    <result-id>.json
  evidence/
    ...
```

每个报告文件对应一个不可变 `ResultRecord`，保留原始字段和条目 ID。报告登记后立即落盘，不由模型改写。`run.json` 仍是完整业务快照；独立文件是方便读取的材料副本，不新增第二份可编辑业务状态。

主请求默认提供程序生成的报告索引：`result_id`、`task_id`、视角、已有的短摘要、虚拟路径，以及条目 ID、类型和 pointer。短摘要复用 `ResultRecord.summary`，不调用模型再摘要。条目目录复用前一份方案的引用目录，不并行维护另一套身份表。文件使用现有 JSON 序列化即可，无需自定义排版或行范围索引。

索引是定位工具，不再次塞入全部观察和解释正文。来源标识与条目类型足够定位时，不额外生成长描述。可用报告清单较小时直接放在请求中即可，无需专门创建“索引管理器”。

### 2.3 默认请求、按需读取与历史的分工

主 Agent 的默认请求保留：

- 当前目标、任务情况和可用报告索引。
- 当前视觉结构，以及按版本标识去重后的初稿/任务结构映射；不重复展开相同快照。
- 前三步已有的草稿状态、校验错误和假设处理进度。
- 当前预算与实际参考图。

首版只把**文本子报告正文**改成按需读取。测量数值和裁剪图继续按现有方式进入请求，保持 `presented_evidence` 的真实多模态语义，不同时迁移图片工具。完整原图仍使用启动时固定的字节；路径文本不算图像输入。

主 Agent 看目录后可以读取有关观察、解释或建议的 pointer，再进行判断和引用。读取结果进入工具历史；下一次请求不再通过 `related_results` 全量复制同一批报告。继续使用 `_with_context()` 的请求级注入方式，保持工具调用与响应配对。

当前自动模型摘要已关闭；本轮不重新打开，也不另做历史压缩器。若后续实际出现历史超窗，再单独处理历史裁剪或摘要及其调用计数。首版只能承诺“去掉每轮全量注入、支持局部取用”，不能承诺任意长运行都有固定上下文大小。

### 2.4 来源合法性与实际可见性分别校验

本轮暴露的问题是：把“不存在／类型错误的来源”和“合法但未读的来源”混在一起，会先返回误导的未读错误；对任务绑定初稿又一律要求读报告文件，会拒绝本已注入的快照。最小修复是在原提交路径中明确顺序：先在临时结果上校验来源身份、类型与归属，再检查实际可见性，全部通过后才发布正式结果。失败保留草稿和准确错误，不向黑板发布半成品。

两类校验复用同一条目目录和第一份方案的结构化错误：独立错误尽量聚合，并返回提交载荷中的准确 JSON Pointer；结构错误阻止后续校验时说明该层尚未执行，不把“暂未检查”写成合法或已读。无需增加新的引用系统。

将报告级 `presented` 的含义拆清楚即可，不引入复杂阅读状态机：

- **已知**：索引中存在该报告和条目，允许选择要读取的材料；不保证该条目适用于当前字段或属于当前任务。
- **来源合法**：来源身份存在，类型符合字段约束，归属在任务允许范围内。目录只能帮助定位，不能代替这层校验。
- **已呈现**：条目的完整正文确实保留在准备好的模型请求中。这是实际阅读记录，不改变条目的真实类型或某字段允许的来源范围；提交引用必须同时通过来源合法性和可见性校验。磁盘存在、读取成功或返回路径均不等于已呈现。

文件和 pointer 使用目录登记的报告、章节或条目位置。工具从实际选中对象计算所包含的完整条目身份，完整返回时才附上 `complete=true`；仅返回章节索引或错误时不附任何已读来源。读取整个章节可以登记其中完整返回的条目，读取单条时只登记这一条。前一份方案的 `hypothesis_links.derived_from` 同样只能引用已呈现的解释。

所有具体 `source_refs` 都遵守这条规则，不限于关键观察。引用整报告（`item_id` 为空）要求整报告正文实际呈现；只读过某个条目就引用该条目。视觉映射指向报告新增对象时，检查该对象正文已通过文件回读进入模型请求；指向任务绑定初稿时，检查该任务对应版本的快照是否实际注入，不要求从报告文件重复读取，也不能用另一个版本或任务的快照代替。`source_result_ids` 仍列全可用报告，但文档中明确它是材料范围，不表示这些报告的每个条目都已阅读或采用。

整报告资格不要求一次返回全文：可以由全部顶层章节先后完整呈现累计取得。复用已呈现 pointer 的覆盖集合；较大章节按条目读取时，完整覆盖其全部子项后才算该章节已读。只读取可引用条目目录中的几项，不自动等于读完整份报告。这是固定 JSON 对象的覆盖判断，不增加行区间追踪或单独的阅读状态机。重复或重叠读取已经覆盖的内容，不重复增加已读材料，也不计作第六步的有效进展。

返回内容过大时，明确要求选择更小章节或单条 pointer，给出已有目录中的可选位置；不静默截断后标记整条已读。回读信息先作为待呈现材料，在下一次模型请求实际包含对应正文时更新资格；避免同一批工具调用中“刚读完文件但模型尚未收到内容”就提交结果。工具返回与请求之间如果发生 SDK 长输出外置，也不得把被替换为路径的正文计为已呈现。读取大小限制与现有外置阈值对齐，以一个聚焦用例核对最终请求，不重写 SDK 的外置机制。

因此报告回读登记应从无参的 `session.context()` 移到 `AnalysisLoop` 准备本轮消息后的小回调：按工具调用 ID 对照待呈现内容，确认实际正文仍在，再登记条目。不能仅在读取工具执行时直接放行后续引用。现有测量和图片保持原请求注入路径。

配套调整现有检查：

| 检查入口 | 调整方式 |
| --- | --- |
| `AnalysisSession.context()` | 不再把目录里的全部报告直接加入 `presented`；测量暂沿用实际注入后的记录 |
| `_require_visual_presented()`、综合引用校验 | 使用前一份方案的明确条目身份，检查所引用条目已实际呈现 |
| `_finish()` | `source_result_ids` 继续声明全部可用报告范围；不再要求所有报告全文都读完。关键引用与 `hypothesis_links.derived_from` 检查必要原文已读，不能只凭目录声称继承了某条假设 |
| `_measure()` | 去掉“所有报告已回读后才允许测量”的全局前置条件。主 Agent 可针对已经读到的问题补测，测量归属、预算、缓存和证据回读检查继续生效 |
| `_validate_batch_plan()` | 追加子任务仍显式选报告与证据；所选报告至少已有正文条目进入主请求，结构中的具体来源另按条目校验。任务的 `gap` 说明为何选入，不新增派发依据字段。子任务输入仍冻结为明确选入的报告 |

前一份方案通过 `hypothesis_links` 记录实际继承关系，程序反向列出未关联原始解释。未关联不等于已舍弃，也不因未关联就自动拒绝提交或改为 `partial`。渐进披露与这一规则一致：读取并关联真正需要继承的解释；未读且未关联的条目保留在来源材料与未关联清单中，不虚构处置结论。

## 3. 第五步：用简单提示安排取证余量

### 3.1 保留一个总预算，先做软性安排

问题在于前置阶段容易把唯一测量额度全部用完，而有价值的取样修正往往在子报告返回后才出现。当前 `ReferenceMeasurements.measure()` 的规格去重和缓存已经合适，不需要改成两个预算池。

首版只做三处调整：

1. `AnalysisSession.context()` 在已有 `measurements_remaining` 旁提供总数、已使用数量和当前阶段：首批前是基础观察，首批后是复核。阶段由已登记子任务推导，不由模型填报。
2. 主提示词要求先测影响初始拆分的关键问题，为子报告后的定向复核留余量。例如总额度为 8 时，首批前通常先做 2—3 项有明确用途的测量；这只是行动指导，不是新的硬上限。
3. 测量回执同时给出实际剩余额度。已有规格命中缓存仍不扣独立测量额度，原图归属与方法信息不变。

不增加“申请释放额度”工具，也不要求用户批准每次跨阶段取证。若前置阶段确实更需要测量，主 Agent 可以继续使用总预算；软指导不保证后续余量。此前误实施后的磨砂圆实际为首批前 7 项、首批后 1 项，彩色元件为 4 项加 4 项，不能据此声称已可靠预留。最小修复仍是把阶段、剩余数和用途提示写清楚；不增加双预算池、预留参数、自动调度或独立 Agent。

### 3.2 先说明下一步能获得什么，不建缺口工作流

复用已有 `EvidenceRequest.question/why_it_matters/measurement`、追加任务的 `gap/expected_evidence` 和综合 `open_questions`。提示词要求说明问题属于哪种情况：

- 原图上还能取证：明确区域、方法，以及结果可能改变哪条判断。
- 需要渲染比较：进入假设对应的 `render_checkpoints`，不继续消耗图像测量额度。
- 缺少其他输入：保留为未知项，说明需要的输入。

本轮先将这一要求落实在既有文字字段，不强制新增 `Gap` 实体、缺口 ID、状态机和调度器。对已解决问题，在综合或草稿中合并更新；对待渲染问题保留对应假设。只有后续确有程序消费者需要按类型调度时，才增加结构化分类字段。

### 3.3 源码落点与最小验证

### 4.2 复用事件文件，区分草稿保存与最终修复成功

误实施前，工作线程内部有自己的 `AnalysisExecution`，但 `_run_batch()` 要等它返回后才合并，运行中可能仍看到旧的 `pending`。方案用离散事件补运行可见性，不重写调度器。现场已存在相应事件文件；后续修正复用它，不另建事件系统。

事件写入使用一个小的会话函数，在运行目录追加 `events.jsonl`。事件仅包含时间、任务 ID、主/子角色、模型逻辑轮、阶段和必要的短结果，例如：

- 任务开始、任务完成或失败。
- 模型请求开始、请求结束或重试。
- 工具被拒绝，以及错误类别和位置。
- 新证据、已读材料或有效草稿保存。
- 最终提交或停止原因。

复用已有 `RequestAttempt`、`ToolFeedback` 和第一份方案的结构化错误信息，不在事件中重复保存大报告、完整工具参数或模型连接配置。不按 token 写事件，也不新增常驻监控服务。CLI 的最终 JSON 继续独占 stdout；查看运行进度可读取事件文件，必要的简短诊断仍走 stderr。

工作线程通过可选回调发出事件，使用独立的小写入锁串行追加。回调不修改共享黑板，不调用整份 `session.save()`，也不获取批次期间持续持有的 `session.lock`，避免主线程等待子线程、子线程又等待主锁。结果仍由协调器合并，`run.json` 仍是业务快照；事件文件提供进行中的状态，二者不宣称跨文件事务。

修正前的成功保存事件缺少实际调用工具名，无法区分完整重交和局部修复。最小修复是在现有 `submission_saved` 中补 `invoked_tool` 与 `submission_tool`：前者为本次实际调用工具（例如 `repair_analysis_submission`），后者为草稿对应的原完整提交工具（主 `finish_analysis` 或子 `submit_analysis_report`）。保留已有任务、角色、逻辑调用轮、`draft_id`、`revision` 和 `accepted`，不复制完整参数。

| 情况 | 事件与含义 |
| --- | --- |
| 完整重交通过全部校验并正式提交 | `submission_saved`，`invoked_tool` 等于原提交工具，`accepted=true` |
| 局部修复后通过全部校验并正式提交 | `submission_saved`，`invoked_tool=repair_analysis_submission`，`accepted=true`；这才计一次成功局部修复 |
| 草稿合法写入或修改，但仍有 schema／业务错误 | `submission_saved`，`accepted=false`，并沿用拒绝反馈记录剩余错误；不计为最终修复成功 |
| 路径、版本或操作无效，补丁未写入 | 仅 `tool_rejected`，保留原草稿；不新增成功保存事件 |
| 终态后重复提交，只返回原结果回执 | 不新增保存／成功修复计数，不将重复回执当成新提交 |

`accepted=true` 只表示正式结果通过全部校验且已提交，不代表视觉效果验收，也不代表整次运行所有子任务成功。第 6 节历史两图日志缺少 `invoked_tool`，不能事后用版本数推算所有成功局部修复，历史记录保持原样。每次保存的元信息在原任务锁内随提交回执返回，事件不再通过锁外快照差分推断，防止并行终态重复回执冒领成功。

### 4.3 只识别可明确判定的重复无进展

本次主、子模型调用默认均不设固定次数上限，网络重试与测量仍按上表受限。次数长本身不是错误；连续修正不同问题或读入新材料不应仅因累计逻辑调用数而停止。

首版的主任务可选 `max_repeated_no_progress` 默认 `0`，表示不自动停止，本次不改该设置，也不扩展到子任务。显式设为正值时，才对以下模式停止：同一工具、同一类及位置的错误、规范化后相同的提交内容，连续达到阈值，且期间没有新增有效材料。它是已有的条件停止机制，不是主、子模型调用总次数上限。

“有效进展”只取已有可观测变化：新的报告或证据、首次完整读入的条目、路径与版本合法且确实改变内容的草稿修改。草稿修改写入不代表整份报告已通过业务校验。仅刷新时间、读取相同段落、命中同一测量缓存或保存内容不变的新草稿版本不计进展。比较修复请求时以修改后的提交内容为准，忽略草稿版本号等运行元数据；否则版本递增会掩盖完全相同的失败。错误和参数只在内存中形成简短指纹，事件不落完整参数。

满足停止条件时复用执行状态 `stopped`，设置独立 `stop_reason="no_progress"`，保存草稿与已完成材料，CLI 返回未完成。它与 `model_limit`、网络失败和成功交付分开。默认关闭时仍可从事件看到重复拒绝，但程序不会伪称自己已经终止了无限循环。

首版不做语义相似度、LLM 停滞评审、自动换模型或错误恢复规划。它能识别确切重复，不能承诺识别所有绕圈；两种不同错误交替出现等情况先保留诊断。

### 4.4 取消和恢复不纳入本轮

当前 `run_analysis_task()` 有最终落盘，但并无从 `run.json` 恢复运行的入口，并且会拒绝已有子任务的主任务。[`save_run`](../../apps/shader_deep/src/shader_deep/artifacts.py) 明确不保存模型对话状态。不能把业务快照叫作完整模型检查点。

以下能力不作为第四至六步首版完成条件：

| 后续小步 | 最小方向 | 必须说明的限制 |
| --- | --- | --- |
| 友好取消 | 识别中断，停止新增请求与派发，保存已经接收的结果；在请求和任务边界检查取消标志 | Python 线程与正在进行的同步网络请求不能保证立即终止；现有 `ThreadPoolExecutor` 退出可能等待进行中任务 |
| 从业务材料重新综合 | 读取旧运行的固定参考图、有效子报告、证据和草稿，建立新的综合执行，记录来源运行 | 这是新模型历史下的继续综合，不恢复中断推理；不自动重跑子任务，也不覆盖旧运行 |

取消与恢复需另行确认范围，不在实施六步时顺手追加。恢复入口还需明确加载契约；本方案不引入跨进程任务队列、线程强杀或通用 checkpoint 系统。
