# 分析模块优化方案：统一库与增量交付

日期：2026-09-21  
状态：方案已实施并完成本地验证；真实两图验证及已知限制见第 11 节。  
范围：子 Agent 的探索交付、统一库维护、主 Agent 的材料输入与批量整合。

## 1. 本次明确的核心边界

**子 Agent 的任务始终是独立探索。“增量”指探索完成后的交付形式，不指基于其他探索结果继续分析。**

子 Agent 只接收用户要求、完整原图、主 Agent 的初步分析和本次探索方向。它不读取统一库中的已有候选，不接收其他子 Agent 的报告，也不负责避免内容重复。

探索完成后，子 Agent 通过一次工具调用，将新增草图、特征、关系及候选交给后端。后端处理 ID 和引用并加入统一库；主 Agent 后续直接操作库中的条目，负责内容去重与整合。

| 责任方 | 负责 | 不承担 |
| --- | --- | --- |
| 子 Agent | 独立探索，提交本次新增内容 | 阅读兄弟报告、跨任务去重、全局 ID 分配 |
| 后端 | 唯一 ID、引用转换、校验、入库、来源与进度 | 根据名称或主观评分自动合并不同机制 |
| 主 Agent | 判断语义重复、整理组成和适用关系、维护局部优先级 | 逐条搬运数据、维护运行台账、反复重写整库 |

本方案延续[整体流程与主 Agent 输入输出规范](分析模块-整体流程与主Agent输入输出规范-2026-09-20.md)中的统一元素、子三库和最终四库边界，调整[此前实施方案](分析模块改造实施方案-独立探索与可能性库-2026-09-21.md)中的材料获取与逐项整合方式。

发生冲突时，以本次明确的“独立探索、增量交付”职责为准。不沿用让子 Agent 阅读已有候选后执行增量完善任务的提议。具体工具名和参数形状属于本版接口建议，仍需在实现时固定为 Schema。

## 2. 始终维护一个统一库

```text
AnalysisLibrary
├── elements
├── sketch_library
├── feature_library
└── relation_library
```

主 Agent 初步分析后写入统一元素表，三个候选库最初为空。子 Agent 的交付和主 Agent 的整合都更新同一份业务状态，最终交付就是该库的一个版本。

“一个库”指一份权威业务状态，不要求物理上只能有一个文件。后端可以保存原始提交、来源映射、版本快照和运行日志，但这些制品不成为要求模型再次阅读、填写和维护的业务对象。

现有代码已有 `LibraryStore`，因此重点是改造交付接口和数据流，不是再增加一个同等职责的库。

## 3. 目标流程

```text
用户要求 + 完整原图
        ↓
主 Agent 初步分析，建立统一元素并制定探索方向
        ↓
后端启动多个独立子任务
        ↓
每个子 Agent 完成探索，调用增量交付工具
        ↓
后端处理 ID、引用和校验，整批加入统一库
        ↓
本轮子任务全部进入终态，后端记录成功、失败与初稿问题
        ↓
后端组织绑定版本的整合材料
        ↓
主 Agent 提交一批整合决定
        ↓
后端在副本上校验并应用整批修改
        ├─ 有错误 → 保留本批材料与决定，局部修复
        ├─ 还有材料包 → 刷新受影响材料，提供下一包
        ├─ 最小完整材料仍超预算 → 记录未完成范围，继续其他包
        └─ 已无可执行材料 → 检查任务、覆盖与缺口，按实际状态导出四库
```

保留主 Agent 和探索子 Agent 两类角色，不为预处理、读取或总结新增 Agent。

本版采用“并行探索、串行整合”：子提交可以随完成随入库，但本轮全部子任务成功、失败或取消后才生成整合材料。整合期间不接收新的探索批次，以缩小并发边界；前一材料包的修改仍会影响后续包，按第 6.3 节刷新。

## 4. 子 Agent：输入独立，交付直接入库

### 4.1 输入

标准业务材料保持为：

- `user_request`：用户原始要求及明确约束。
- 完整原图：实际多模态图像内容。
- `visual_outline`：主 Agent 的初步视觉分析，提供统一元素、实例组和可见线索。
- `exploration_direction`：本次探索切入点，不预先指定机制答案。

探索任务绑定派发时的初稿。统一库随后增加了哪些候选，不会自动成为其他子任务的输入。

本版在派发后冻结本轮元素与实例组身份。子任务仍可报告初稿遗漏或分类问题，反馈和处置规则见第 8.3 节；不能为了通过引用校验把遗漏对象挂到不相关的已有元素。

任务内部允许多轮分析与格式修复。独立性不等于强制一次模型调用完成。

### 4.2 增量交付工具

建议将交付接口表达为：

```text
submit_exploration(
    sketch_library=[本次新增草图],
    feature_library=[本次新增特征及候选],
    relation_library=[本次新增关系及候选]
)
```

一次工具调用代表一次完整探索交付。子 Agent 不需要逐项调用“新增特征”“新增候选”“修改引用”等工具，也不需要额外提交摘要或元素表。

后端在工具内部执行：

1. 校验本批字段、局部 ID 和引用。
2. 为新增 ID 分配唯一命名空间。
3. 同步转换本批内部引用，包括草图引用、关系端点及 `requires`。
4. 将整批内容加入统一库，保存原始提交与来源。
5. 入库成功后返回简短回执，结束该子任务。

回执只需说明已入库及必要统计，不再次返回整批正文。入库尚未完成时不能返回成功。无效提交保留为草稿，反馈准确的参数路径以便局部修复。

原始提交可以作为后端制品保存；主 Agent 后续操作的对象是统一库中的条目，不需要先逐份打开子报告。

## 5. ID 与并行提交

### 5.1 后端分配唯一身份

| 子任务局部 ID | 入库后的示例 ID |
| --- | --- |
| A1 的 `S1`、`F1`、`C1` | `A1:S1`、`A1:F1`、`A1:C1` |
| A2 的 `S1`、`F1`、`C1` | `A2:S1`、`A2:F1`、`A2:C1` |

任务前缀由后端生成并保证在本库中唯一。子 Agent 只需保证自己这一批的局部 ID 不冲突。

- 初稿已有的元素和实例组 ID 原样沿用。
- 新增草图、特征、关系和候选使用局部 ID，后端统一转换。
- 同批中的前向引用也必须统一解析，不能按数组位置边读边随意替换。
- 两个任务提交相同内容，仍保留为不同来源的条目，等待主 Agent 判断。

不要求模型查询“哪些 ID 已被使用”，也不增加供模型维护的全局来源台账。

### 5.2 提交幂等与短写锁

同一任务的同一成功提交重复到达时，返回原回执，不重复加入库。无效草稿可以修复；已经接受的提交不能被另一份内容静默覆盖。

子任务可以并行探索，提交时由后端协调串行更新。写锁只覆盖必要的校验与提交临界区，不能在等待整个子任务批次完成期间持有该锁。

一批内容要么完整发布，要么保留原库并返回错误。模型不负责处理其他任务写入期间的运行状态变化。

## 6. 后端预处理主 Agent 的输入

预处理目标是组织现有内容，减少模型获取和管理材料的操作。

| 预处理工作 | 做法 | 边界 |
| --- | --- | --- |
| 去掉传输冗余 | 省略可选空字段与运行记录，同一条目正文在包内只出现一次 | 不删除不同来源中的独特候选 |
| 建立比较范围 | 按元素范围、条目类型和关系端点组织相关内容 | 分在一起不表示已经认定语义相同 |
| 补齐关联材料 | 提供理解草图所需的特征、关系、候选及相关前提 | 不只交给模型孤立 ID |
| 维护身份映射 | 必要时提供简短别名，并绑定原始条目 | 模型不用复制长运行身份或维护别名表 |
| 管理处理进度 | 记录材料包、已接受决定和待处理范围 | 进度由后端维护，不靠模型从聊天历史猜测 |

后端不根据名称相似就合并机制，不按票数、优先级或主观可信度淘汰候选。

### 6.1 优先整包，必要时分包

材料能放进一次请求时，直接提供完整整合材料。超过实际请求预算时再分包，尽量把需要共同比较的条目放在一起。

每个包明确本包可修改的条目和必要的只读关联材料。跨包问题需要有明确承载位置，不能通过切断引用或省略关键前提来缩小输入。

分包保护的是单次传输量，不是候选数量。不截断条目、不为缩短正文删除独特机制，也不展开所有局部候选的笛卡尔积。

不能把“分包处理完成”自动解释为“所有跨包语义重复均已消除”。仍不能可靠判断的内容可以保留，并记录未完成的整合范围。

请求预算必须覆盖系统提示词、工具 Schema、用户要求、原图与测量图像、本包正文、控制信息、修复历史及输出预留，不能仅按库正文字符数判断。预算和估算余量显式配置；每次实际请求前重新检查，新增测量和修复上下文也计入预算。

最小可处理单元是一次判断必须共同呈现的完整条目及必要关联材料。若该单元本身超预算，本版不截断、不用摘要冒充已呈现正文，也不循环尝试相同分包。后端保留原内容，记录条目、待完成判断与 `input_budget_exceeded` 原因，将该范围标为待后续处理，继续其他可执行包；本轮交付为 `partial`。修复历史增长导致无法继续时采用同一出口。

只有能证明判断相互独立时，才拆成分别可完整处理的单元。原始文本分片可用于保存或传输，但不能证明模型已在一次判断中获得全部必要材料。

### 6.2 主 Agent 默认输入

```text
用户要求 + 原图
统一元素
本次待整合的库内容
必要的只读关联条目
本包需要完成的整合任务
相关初稿问题、任务失败及覆盖缺口
```

`list_library`、`read_library_item` 不再构成正常整合流程。材料的选择、读取和分页由后端完成。

### 6.3 材料包版本与刷新

后端为每包保存包身份、包版本、生成时的库版本、可修改范围，以及全部判断材料的条目版本或内容哈希。版本绑定包括只读依赖、元素初稿和本包问题记录。模型只接收业务材料与必要回执；版本和提交身份由执行器绑定，不要求模型抄写台账。

材料“已提供”的依据是完整内容实际进入准备发送的模型请求，而不是后端已经生成了包。批量修改复用这一呈现边界，不再依赖模型调用读取工具。

前一包成功后，后端按以下规则推进：

1. 统一重写库内引用和别名，并找出正文、候选集合、范围或必要依赖发生变化的待处理包。
2. 仅重建受影响的包，更新其包版本；未受影响的包可以继续使用，不因全库版本递增而全部重做。
3. 提交时核对本包判断所依赖的版本。若已变化，拒绝发布旧决定，提供刷新后的材料与变更说明；不能仅替换旧 ID 后直接接受旧判断。旧决定保留供参考，但须基于新材料重新确认。
4. 已接受的决定不因后续机械引用改写而重新执行。若后续操作改变了既有判断的实质前提，生成明确的复核范围，不静默沿用旧结论。

新增候选或组成通过结构校验后直接入库。若新增内容及其必要依据已在本包完整处理，不自动再生成一包；涉及未提供的比较对象或新的整合缺口时，登记新的待处理范围。新增范围去重后加入队列，受本轮总预算约束，预算不足则记录为未完成。结束依据是更新后的队列与缺口记录，而不是最初材料包的数量。

“只读关联材料”限制的是模型新增的语义修改，不禁止已接受合并所必需的机械引用重写；若涉及关联条目的语义选择或冲突裁决，必须纳入可修改范围并提供相应材料。

## 7. 主 Agent：批量修改统一库

主 Agent 负责判断同义现象和重复机制、整理草图适用范围、维护局部尝试优先级，以及提出必要的新组合和未解问题。

不同机制继续保留；优先级不表示真伪或已经选定；未被当前草图引用的候选也继续存在。

### 7.1 批量整合接口

建议使用 `submit_integration` 提交本批决定，字段按实际变化填写：

| 字段 | 用途 |
| --- | --- |
| `merges` | 将明确重复的条目归并 |
| `reference_updates` | 调整指定草图的引用范围或局部优先级 |
| `additions` | 新增必要的候选或跨报告组成 |
| `unresolved` | 保留具体未解问题 |
| `outline_issue_decisions` | 对初稿问题记录暂缓修订或有依据的不采纳，不修改本轮元素身份 |

没有变化的部分省略，未提到的条目和字段保持原样。允许明确接受本包原样保留，不强迫每包产生合并。

以下仅为合并部分的接口示例，不是已经接入运行时的完整 Schema：

```json
{
  "merges": [
    {"kind": "feature", "members": ["A1:F1", "A2:F3"]},
    {"kind": "candidate", "members": ["A1:C2", "A2:C7"]}
  ]
}
```

模型只指明合并成员，不同时维护 `source_ids` 与 `target_id`。保留 ID 由后端按稳定规则选择，并统一重写引用。

成员合并仍需满足类型、归属、适用范围和选择前提等约束。合并特征或关系时保留其中不同的候选；不能通过替换整个候选数组静默丢失内容。不同组成应新增为另一种可能性，不能覆盖掉原结构。

### 7.2 整批应用

1. 核对包身份、相关材料版本与提交回执；验证语义操作在本包允许范围内，且模型已实际获得判断材料。
2. 检查合并分组和引用调整是否冲突。
3. 在临时副本上生成归并映射，处理拥有者、候选和相关引用。
4. 应用新增内容、范围和局部优先级变化。
5. 完成整库的结构、引用、范围与直接前提校验。
6. 整批通过后一次保存版本、来源、提交回执和处理进度，再刷新受影响的待处理范围。

同一批中的多个合法操作必须能共同完成。不能在第一个操作成功后就阻止剩余操作，再要求模型重新规划。

成功提交的重放返回原回执，不重复执行新增或合并；同一提交身份携带不同内容时明确拒绝覆盖。校验失败不推进包进度。库修改、回执与包进度按同一发布边界保存，避免恢复或重试时出现“内容已改但包仍未处理”的重复执行。

关系中的反馈和候选选择前提分别处理，不因出现环就一律判错；本次不建立通用约束求解器，也不证明所有候选组合都能实现。

## 8. 上下文、修复与结束

### 8.1 批内保留上下文

同一批整合过程中保留材料和已生成的决定。校验失败时，返回与提交参数一致的错误路径，例如 `/merges/1/members/0`，只修复这批决定。

不重新列目录，不重新读取整库，不因某一个条目修改成功就清空主 Agent 历史。同一有效包内保留修复上下文；整批成功后推进下一包，超预算、修复耗尽或无进展时则保存草稿和未完成范围后推进。材料版本已变化时按第 6.3 节刷新，不能把过期决定当作普通参数错误修复。

提交修复复用现有草稿能力，不另建一套让模型维护的工作台账。

### 8.2 测量与补充探索

测量保留为必要的补充能力。确实需要比较多个区域时，应将本批需要的测量结果及对应图像一起提供，不能使用会被后续选择覆盖的单个 `selected_evidence`。

整合阶段不再开放自由派发探索任务的工具。需要进一步探索的缺口先明确记录，由外层流程决定是否开始新一轮独立探索。新子任务仍遵守相同输入边界，不接收已有机制结论或兄弟报告。

### 8.3 初稿问题的反馈与处置

保留子任务的初稿问题反馈能力。后端保存问题身份、派发时的初稿版本、来源任务、相关元素或区域及具体描述。即使子任务没有成功提交三库，问题也必须随失败记录进入主 Agent 的整合材料，不能依赖成功报告承载。

本版不在整合阶段修改元素或实例组身份，也不执行跨版本引用迁移。主 Agent 在批量决定中引用问题身份，选择以下处置：

| 处置 | 条件与结果 |
| --- | --- |
| 不采纳 | 提供针对原图、初稿或本包材料的具体理由；保存原问题和理由，不声称进行了修订 |
| 暂缓修订 | 确认需要补充观察、修订或当前无法判定；记录受影响范围与下一步，问题保持未解决，本轮为 `partial` |

遗漏对象没有元素 ID 时，缺口按图像区域和问题身份保存于交付运行记录，不伪造元素引用。合法且不依赖该修订的子任务内容仍可入库；无效草稿保留为制品，不混入有效四库。

后续若另行启动修订轮次，先形成新初稿版本，再派发独立探索。本次不承诺自动续跑或复用旧报告；旧结果保留原版本和来源。未来支持复用时，必须先定义身份映射、引用迁移与重新校验规则。这是本版有意限定的实施边界，取代本轮中途修订元素的做法。

### 8.4 后端推进完成

取消“所有库条目必须逐项调用读取工具”的门槛。修改判断所需的正文由材料包保证提供；原样保留的内容由后端继承。

后端保留当前任务与覆盖检查，并根据以下条件决定交付状态：

1. 本轮派发的全部子任务已进入终态。保持现有首批至少两个独立任务、至少一份可用报告的有效交付门槛；失败或取消的任务单独记录，不能因其没有产生材料包而被遗漏。
2. 更新后的材料队列已无未登记的工作。包括新增内容或前提变化带来的处理范围；每个范围都有已接受决定、明确原样保留或未完成记录。
3. 已接受决定全部应用，四库结构、引用、范围与直接前提校验通过。无效草稿不能当作最终库输出。
4. 每个统一元素有相关草图、特征或关系覆盖，或者有具体缺口记录。引用覆盖仅表示已形成相关候选，不证明视觉解释正确；没有覆盖的元素不能静默遗漏。
5. 初稿问题、任务失败、超预算材料与必要整合缺口均已记录，并影响对应状态。

| 交付情形 | 结果 |
| --- | --- |
| 子任务全部成功，必要整合完成，元素均有候选覆盖，无待修订初稿问题 | `completed`；可保留等待编码、渲染区分的机制争议，不要求候选收敛 |
| 存在可用且合法的四库，但有任务失败或取消、未覆盖元素、待修订初稿问题、超预算范围或必要整合未完成 | `partial`；同时交付现有库和具体缺口 |
| 无有效报告、未满足最小探索门槛，或无法形成合法可交付库 | 不生成成功交付；保存草稿和原因，按现有运行契约标记失败或停止 |

主 Agent 明确保留原样只结束已获得充分材料的当前判断；不能用该决定关闭未提供的材料、未执行的必要比较或未解决的初稿问题。已充分比较但机制仍有歧义属于分析结果，未能完成比较属于整合缺口。

满足相应条件后由后端导出当前四库与独立的运行状态、失败任务和缺口记录，不要求主 Agent 重写整库或额外生成重复总结。运行记录由后端组装，不成为要求模型重复维护的第五个业务库。

同一错误、同一输入反复出现且没有进展时，应结束该批并保留问题，避免无限重试。阈值和预算需要显式配置；本方案不擅自新增固定候选数量或字数上限。

超时、异常和主动中断都要落盘终止原因及最后一个已发布版本；有合法可用结果时标明部分交付，不能把退出后的运行状态留在 `running`。已提交批次保留，未发布批次保留草稿；所有包处理完也不能掩盖失败任务或未完成范围。

结构合法、整合已完成和视觉效果已验收仍是不同状态。

## 9. 实施范围与顺序

沿用当前模型传输、四库数据结构及独立探索原则，优先在现有应用内完成改造，不新增通用 Agent 框架或数据库。

| 阶段 | 修改内容 | 交付条件 |
| --- | --- | --- |
| 1. 单包闭环 | 复用已有探索与统一入库能力，提供完整单包材料、批量决定及后端结束检查 | 无需列目录或逐项读取；合法批次共同生效，失败不发布；超预算明确退出；结果状态准确 |
| 2. 交付可靠性 | 子提交工具直接接入统一库，补齐短写锁、幂等回执、任务终态和初稿问题传递 | 并行子任务独立交付；成功回执代表已入库；重复提交和中断不造成重复或半成品 |
| 3. 多包推进 | 增加分包、相关版本检查、受影响包刷新、新增范围及超预算出口 | 前包修改不导致后包依据旧材料提交；已接受决定不重复执行；无法处理的范围明确保留 |
| 4. 完整验证 | 验证修复、测量、覆盖、缺口和中断状态，再运行两张参考图 | 批内修复不重做无关分析；多测量完整呈现；失败不会伪装完成；真实运行数据可对照 |

直接入库改善提交可靠性；减少主 Agent 轮次的主要改动是“材料包 → 批量决定 → 后端结束”。因此先以现有报告入库路径验证这一闭环，再替换子提交路径。所有阶段完成前，不宣称本方案全部落地。

主要改动落在 `analysis/exploration_worker.py`、`analysis/exploration_session.py`、`analysis/library.py`、`analysis/exploration.py`、`context/exploration.py` 和整合提示词。必要时新增一个职责单一的预处理模块。

具体 Schema 参数名、预算数值、分组算法、版本存储形式和修复阈值在实现前固定。版本刷新、最小材料超预算出口、本轮初稿冻结与状态判定按本文执行，不再作为未定职责留给实现自由推断。本文不把这些规则表述为已经实现。

## 10. 验收标准

| 验收项 | 需要证明的行为 |
| --- | --- |
| 子任务独立性 | 实际请求不包含其他子 Agent 的报告或库中已有机制 |
| ID 唯一 | 两个子任务使用相同局部 ID，入库后仍能正确区分，引用不串任务 |
| 内容保留 | 同义内容可分别入库，后端不擅自作语义去重 |
| 提交可靠 | 重复成功提交不重复入库，无效批次不部分发布 |
| 批量整合 | 同一决定中的多个合法合并与引用调整全部执行 |
| 候选边界 | 不同机制、未修改、未引用和低优先级候选均保留 |
| 材料充分 | 正常整合不需要模型自行列目录、分页或逐条取正文 |
| 证据完整 | 同批多个测量结果均进入模型请求，不互相覆盖 |
| 修复与进度 | 修复针对当前决定，已接受修改不会因重试重复执行 |
| 包版本 | 前包合并使后包依赖或候选集合变化时，后包刷新；旧决定拒绝发布；无关包不重做 |
| 新增范围 | 本包内完整处理的新增内容不循环排队；需要其他材料的新增判断进入待处理范围，不能提前完成 |
| 超预算出口 | 单条目连同必要关联内容超预算时保留原文、记录缺口、继续其他包并输出 `partial`；修复增长超预算同样处理 |
| 初稿问题 | 没有成功报告的子任务，其初稿问题仍被呈现；暂缓修订保持未解决，不产生虚假修订记录 |
| 任务与覆盖 | 两个任务中一个失败时不得交付 `completed`；无候选覆盖的元素必须记录具体缺口 |
| 状态区分 | 已完成比较但机制待渲染验证不阻止完成；未执行的必要比较不能靠原样保留伪装完成；无有效报告不能成功 |
| 恢复与中断 | 成功提交重放不重复执行；中断保存最后发布版本与未发布草稿；退出后状态不得仍为 `running` |
| 正常结束 | 动态新增的必要范围也有明确结果；可执行材料处理完后交付，失败和无进展状态准确保存 |

目标是让模型调用与“探索任务、整合批次”对应，而不是与每个条目的读写对应。单包材料争取一次有效整合决策完成；大输入按材料包处理，另计必要纠错。

实际收益需要用相同两张参考图核对完整交付、候选保留、模型轮次、读取工具次数、修复次数、上下文峰值和提供方用量。模型轮次与工具调用次数分别统计；不在没有对照数据时承诺固定减少比例。

本节以上定义目标契约；具体实现与验证范围以第 11 节及源码为准。


## 11. 实施与验证记录

实施日期：2026-09-21。三个 sub agents 分别负责批量库事务、材料组织、子任务入库与补充测试，主线程负责主流程集成、请求预算和真实验证。

### 11.1 已接入行为

- 初稿与 `directions` 同次提交，后端派发独立探索。整合阶段没有派发、逐条读取或 `finish_analysis` 工具。
- 子任务直接提交顶层三库；回调确认入库后结束。成功提交幂等，失败草稿与初稿问题保留。
- `submit_integration` 一次发布多个合并、引用更新、新增及问题处置。库快照同时保存回执和接受进度，模型不维护版本台账。
- 材料包绑定完整正文版本，前包变动刷新受影响材料，已完成判断的实质前提变化触发复核。过期决定交由后端刷新，不反复修复旧参数。
- 本包测量自动共同呈现；额度耗尽后仍可通过 `read_measurements` 批量复用已有证据。只有正文和实际裁剪图都进入请求，才登记呈现。
- 本轮初稿冻结。未覆盖元素、失败任务、暂缓修订、超预算或未完成比较均保留并影响 `partial`；可用库不因中断被丢弃。
- 探索取消会阻止新的逻辑请求、网络重试与未发布提交；已经在途的同步请求需返回或超时后才能释放线程。

公开 `run_analysis` / `run_analysis_task` 签名不变。`run_exploration` 新增带默认值的 keyword-only `commit_report`、`should_stop` 参数，原调用方式兼容。工具参数按本方案升级，旧的 `{report: ...}` 子提交形状不属于新主流程。

### 11.2 请求预算与实际边界

材料成本包含 JSON 正文嵌入消息后的转义开销。`integration_history_tokens` 默认 16384，为决定和局部修复历史预留估算空间；`request_token_margin` 保留编码与估算余量。完整请求仍在实际发送前核对。

主请求按每字符一个估算 token，并预留图像、输出和历史；这不是提供方 tokenizer 或真实上下文窗口声明。超过预算时保存缺口，不删候选。工作线程仍使用独立调用预算，不套用主整合包的请求预算。

材料划分按类型和范围组织，不保证识别全部跨包语义重复。记录、版本和草稿可供追溯；本次没有实现从任意快照恢复完整模型历史的公开入口，也没有自动修订初稿并续跑的流程。
